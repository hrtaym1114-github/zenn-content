「うちのアプリには脆弱性がない。でも、裏のAPIはどうか」。公開アプリを持っているチームなら、10月の情報漏えいの報道が続く中で一度は気になったはずです。

2026年10月13日、NICTの脅威情報分析チームLETTICEが「A2B攻撃」の注意喚起を出しました。この記事は、その注意喚起の「確認・点検・緩和」をチームでそのまま回せるチェックリストに書き直したものです。攻撃の再現方法や具体的な入力値は書きません。

## A2B攻撃が指す範囲（NICTの定義）

**NICT**: A2B攻撃（App-to-Backend Attack）は、一般に公開されているAndroidアプリを解析し、その結果を使って、アプリの裏側のバックエンドサーバを攻撃する手法です。今回確認された攻撃では、Google Playの日本地域で公開されているアプリから、接続先・APIの構成・パラメータ・応答の構造などを調べ、サーバごとに合わせた攻撃を組み立てています。

**NICT**: 特徴は、不特定多数に同じ攻撃をばらまくのではなく、対象サーバごとに攻撃内容を変えている点です。アプリ自体に脆弱性がなくても、バックエンドAPIの認証・認可や入力値検証に不備があれば漏えいにつながります。認証が要らないAPIだけでなく、ログイン後に使えるAPIも対象になり得ます。

**NICT**: 同じ問題はiOSアプリやWebサービスのバックエンドAPIでも起こり得る、とも書かれています。ただし「A2B攻撃」として確認・命名されたのは、公開Androidアプリを起点にした攻撃です。

**NICT**: 主に狙われている脆弱性として、SSRF、RCE、SQLインジェクション、IDOR（BOLA）の4種類が挙げられています。

**補足**: この記事では、A2Bを「アプリ経由の攻撃全般」には広げません。チェックリストの対象は「公開アプリが話しているバックエンドAPIと公開ホスト」です。

## 前提: 解析されることは止められない

**NICT**: 公開アプリが解析されること自体を完全に防ぐのは難しく、アプリの内部構造やAPI仕様が知られてもバックエンドが安全であるよう設計・運用することが重要、としています。恒久対策では、攻撃者がアプリを通さずAPIを直接操作できることを踏まえ、アプリ側の制御に頼らずサーバ側で認証・認可・入力値検証を行うこと、とあります。

**補足**: 点検の会議では、最初に「アプリの中にあるものは全部読まれている」という前提をそろえておくと、後の議論が速くなります。難読化はこのチェックリストの対象外です。

## ステップ1: 侵害の確認

### NICT

- [ ] APIとインターネットに公開しているホストを列挙した（アプリが使うAPI、サブドメイン、旧バージョンのAPI、検証環境、クラウド上の公開サービスを含む）
- [ ] **2026年8月以降**のアクセスログ・APIログ・認証ログを確認した（可能ならそれ以前も）
- [ ] 注意喚起PDF「6. IoC」に載っているIPアドレス等との一致を調べた
- [ ] IoC以外の不審な操作がないか確認した
  - 認証なしでの大量の情報取得
  - 連番IDなどを使ったアクセス
  - 他会員の情報の閲覧・変更
  - 認証トークンの不審な発行
  - 管理機能の利用
- [ ] 不審なアクセスがあった場合、認証の成否・アクセス先データ・取得や変更の有無・認証情報の悪用について影響範囲を調べた

**NICT**: IoCとの一致だけで侵害を断定することはできず、ログや通信内容と合わせて判断するよう書かれています。IoCは一部のみ掲載とされているので、最新の値は必ずPDFを参照してください。

### 補足

- 列挙の出発点として、ストアで公開中のアプリの全バージョンが接続している先を、自社のソースコードと設定から洗い出すと漏れが減ります。古いバージョンを使い続けている利用者がいる限り、旧APIも生きています。
- ログの保存期間が8月までさかのぼれるかを、最初に確認してください。さかのぼれない場合は、その事実自体を記録に残しておきます。

## ステップ2: 脆弱性の点検

### NICT

- [ ] **認可不備（IDOR/BOLA）**: 会員IDなどの識別子を変えると、他者・他テナントの情報を閲覧・変更できないか
- [ ] **認証・セッション管理**: トークンの不正発行・偽造、他者の認証情報の取得、認証回避ができないか。固定された認証情報や暗号鍵が露出していないか
- [ ] **SQL／NoSQLインジェクション**: 外部入力でデータベースの情報を不正に取得・変更できないか
- [ ] **SSRF**: URL取得・画像処理・文書変換などの機能から、内部ネットワーク、クラウドのメタデータサービス、ローカルファイルへアクセスできないか
- [ ] **クラウドサービス・ストレージの設定**: S3、GCS、Firestoreなどに、認証なしや本来許可していない権限でアクセスできないか
- [ ] **コード実行・ファイル操作**: 危険なデシリアライズ、任意ファイルの書き込み・上書き、不適切な管理機能の公開がないか

### 補足

- 点検はAPIのエンドポイント単位で表にすると、担当と抜けが見えます。列の例: エンドポイント／認証の要否／識別子を受け取るか／外部URLやファイルを受け取るか／触るデータストア／担当／点検日。
- 「識別子を受け取るか」「外部URLを受け取るか」の列に印がついたものから順に見ると、NICTが挙げた4種類（IDOR、SSRFなど）に優先度を合わせやすくなります。
- アプリに埋め込まれている鍵や接続情報は、すでに読まれている前提で棚卸しします。
- 自社で判断できない場合は、NICTも書いている通り、社内のセキュリティ担当・開発運用の委託先・専門事業者に相談します（NICTは個別システムの診断・相談には対応していないと明記しています）。

## ステップ3: 暫定的な緩和策

### NICT

業務への影響を考えながら、必要に応じて実施するもの、とされています。

- [ ] 国外からのアクセスや不要なアクセス元からの通信を一時的に制限する
- [ ] 不要な公開API・管理機能・検証環境へのアクセスを停止または制限する
- [ ] アクセス頻度や連続的な識別子の指定を監視し、必要に応じてレート制限やWAFでアクセス制御する
- [ ] 認証情報やトークンの漏えい・悪用が疑われる場合は、無効化・再発行する
- [ ] 脆弱性が見つかったら速やかに修正する
- [ ] すぐ直せない、または重大な脆弱性の有無を確認できず、暫定的な制限でもリスクを許容できる水準まで下げられない場合は、該当APIや機能、必要ならサービス全体の一時停止を検討する

### 補足

- 「国外アクセスの制限」は、海外の利用者や海外リージョンからの正規の通信（外部サービスのWebhookなど）を止めることがあります。入れる前に、正規の通信元を一覧にしておきます。
- 認証情報を再発行するときは、旧バージョンのアプリに埋め込まれたものがないかを先に確認します。再発行で古いアプリが動かなくなる場合は、その影響も判断材料に入れます。
- 一時停止の判断基準（誰が、何を見て決めるか）は、点検を始める前に決めておくと迷いません。

| ステップ | NICTの要点 | 決めておくこと（補足） |
|---|---|---|
| 1. 侵害の確認 | 公開API・ホストの列挙、8月以降のログ、IoCと不審操作、影響範囲 | ログの保存期間、旧バージョンの接続先 |
| 2. 脆弱性の点検 | IDOR/BOLA、認証・セッション、SQL/NoSQL、SSRF、クラウド設定、コード実行・ファイル操作 | エンドポイント表と担当 |
| 3. 暫定的な緩和策 | アクセス制限、不要API停止、レート制限・WAF、認証情報の再発行、修正、一時停止の検討 | 正規の通信元一覧、停止の判断者 |

## おわりに

NICTの注意喚起は「アプリは読まれる。だからバックエンドで守る」という一点に集約されます。チェックリストのNICT項目は、自社の状況に合わせて削らずにそのまま使い、補足は必要なものだけ取り入れてください。内容は2026年10月13日時点の注意喚起（Rev 1.1）に基づいています。更新があればNICTの原文を優先してください。
