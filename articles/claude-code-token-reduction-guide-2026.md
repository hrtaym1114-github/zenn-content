## はじめに：トークン消費、気にしていますか？

Claude Code を日常的に使っていると、ある日突然「Usage limit reached」の壁にぶつかる。Pro プランでも Max プランでも、ヘビーに使えば上限は意外とすぐ来る。

実は、Claude Code のトークン消費の大半は **私たちが意識していない場所** で発生している。

- Claude の「丁寧すぎる」出力（敬語、前置き、補足説明）
- `git status` や `npm test` の冗長なコマンド出力
- 毎セッション読み込まれる肥大化した CLAUDE.md

これらを最適化するだけで、トークン消費を **60〜90% 削減** できる。

本記事では、以下の 3 つのアプローチを組み合わせた実践的な最適化ガイドを紹介する。

| アプローチ | 対象 | 削減率 |
|-----------|------|--------|
| 1. プロンプト最適化（genshijin） | Claude の出力トークン | 約 80% |
| 2. RTK（CLI プロキシ） | コマンド出力トークン | 60〜90% |
| 3. CLAUDE.md / 設定最適化 | 入力トークン | 約 40% |

## アプローチ 1：プロンプト最適化 —「原始人口調」でトークン 80% 削減

### 元になったアイデア

英語圏で話題になった「caveman coding」（原始人のように簡潔に応答させるプロンプト手法）を、日本語向けに最適化したのが **genshijin メソッド** だ。

@mikana0918 さんの [Zenn 記事](https://zenn.dev/mikana0918/articles/7ad57493a04f88) で詳しく解説されているこの手法は、**Claude の出力文体を制御する** ことでトークン消費を構造的に削減する。

### なぜ日本語は特にトークンを浪費するのか

日本語には英語にない構造的な冗長性がある。

- **敬語体系**：「設定されています」→「設定」で 5〜6 トークンが 1〜2 トークンに
- **助詞の連鎖**：「することができるようになります」→「できる」
- **クッション言葉**：「ちなみに」「まあ」「えーと」— 情報量ゼロで各 1〜2 トークン消費
- **ぼかし表現**：「かもしれません」「と思われます」— 曖昧さを加えるだけ

BPE トークナイザにおいて、これらは各 1〜2 トークンを消費しながら **情報量はほぼゼロ** という、極めて非効率な存在だ。

### 実測値：通常 vs caveman vs genshijin

| モード | トークン数 | 削減率 |
|--------|----------|--------|
| 通常（敬語あり） | 1,483 | — |
| caveman（英語最適化） | 476 | 68% |
| **genshijin（日本語最適化）** | **296** | **80%** |

caveman が取りこぼした 32% のうち、genshijin はその約半分を回収している。

### Before / After

**通常モード（1,168 トークン）**：
> CORSエラーとは、Cross-Origin Resource Sharingの略で、ブラウザのセキュリティ機能の一つです。異なるオリジン間でリソースを共有する際に発生します。解決方法としては、サーバー側でCORSヘッダーを適切に設定する必要があります。具体的には、以下のフレームワークごとの設定例をご紹介します...

**genshijin モード（217 トークン）**：
> CORS エラー原因…サーバ側 CORS 設定なし
> 解決：`Access-Control-Allow-Origin` ヘッダ追加
> 確認：DevTools Network タブ → preflight request 有無

技術的な正確さは維持したまま、装飾だけが除去されている。

### 導入方法

CLAUDE.md に以下を追加する：

```markdown
## 出力ルール
- 体言止め・短文で応答。敬語不要
- クッション言葉・ぼかし表現を使わない
- 「することができる」→「できる」のように冗長表現を圧縮
- 技術的正確さは維持。省略するのは装飾のみ
```

より強力に制御したい場合は、プロジェクトの CLAUDE.md に genshijin ルールセットを直接記述する方法もある（詳細は [元記事](https://zenn.dev/mikana0918/articles/7ad57493a04f88) を参照）。

## アプローチ 2：RTK でコマンド出力を 60〜90% 圧縮

### RTK とは

[RTK（Rust Token Killer）](https://github.com/rtk-ai/rtk) は、AI コーディングエージェントのトークン消費を削減する CLI プロキシだ。Rust 製のシングルバイナリで依存関係ゼロ。Claude Code だけでなく、Cursor、Windsurf、Copilot など主要な AI コーディングツール 10 種に対応している。

### 動作原理

RTK は 4 つの戦略でコマンド出力を圧縮する。

1. **スマートフィルタリング**：コメント、空行、ボイラープレートを除去
2. **グループ化**：ファイルをディレクトリ別に、エラーを種類別に集約
3. **トランケーション**：関連コンテキストを保持しつつ冗長部分をカット
4. **重複排除**：同一パターンのログ行を折り畳み、出現回数をカウント

Claude Code に統合すると、`git status` → `rtk git status`、`npm test` → `rtk npm test` のように、コマンドが透過的に RTK 経由に書き換えられる。

### コマンド別の削減効果

30 分セッションでの実測例：

| 操作 | 実行回数 | 標準トークン | RTK 後 | 削減率 |
|------|---------|------------|--------|--------|
| `ls` / `tree` | 10 回 | 2,000 | 400 | **80%** |
| `cat` / `read` | 20 回 | 40,000 | 12,000 | **70%** |
| `grep` / `rg` | 8 回 | 16,000 | 3,200 | **80%** |
| `git status` | 10 回 | 3,000 | 600 | **80%** |
| `git diff` | 5 回 | 10,000 | 2,500 | **75%** |
| `cargo test` / `npm test` | 5 回 | 25,000 | 2,500 | **90%** |
| **合計** | | **~118,000** | **~23,900** | **~80%** |

特にテストランナーの出力が **90% 削減** されるのが大きい。テスト→修正→再テストのサイクルはトークン消費の最大要因の一つだ。

### インストール手順

```bash
# macOS（Homebrew）
brew install rtk

# macOS / Linux（クイックインストール）
curl -fsSL https://raw.githubusercontent.com/rtk-ai/rtk/refs/heads/master/install.sh | sh

# Cargo 経由
cargo install --git https://github.com/rtk-ai/rtk

# Windows（プリビルドバイナリ）
# GitHub Releases から rtk-x86_64-pc-windows-msvc.zip をダウンロード
```

### Claude Code への統合

```bash
# フック + RTK.md をインストール（推奨）
rtk init -g

# Claude Code を再起動
# → 以降、Bash コマンドが自動的に RTK 経由に書き換わる
```

`rtk init -g` は Claude Code の PreToolUse フックを設定し、Bash コマンドを透過的に RTK コマンドに書き換える。ユーザー側の操作は不要で、Claude Code はこれまで通り `git status` と指示するだけでよい。

### 効果の確認

```bash
# 統計サマリーを表示
rtk gain

# 過去 30 日のグラフ
rtk gain --graph

# まだ最適化されていないコマンドを検出
rtk discover
```

## アプローチ 3：CLAUDE.md と設定の最適化

### CLAUDE.md のダイエット

CLAUDE.md はセッション開始時に **毎回** 読み込まれる。つまり、ここに書かれた 1 行 1 行が、毎セッションのトークンコストに直結する。

**目安：200 行以内に収める。**

具体的な最適化ポイント：

```markdown
# やめるべきこと
- 長い説明文や背景情報（別ファイルに分離）
- 使わなくなったルール（定期的に棚卸し）
- 具体例の過剰な列挙（代表例 1〜2 個で十分）

# やるべきこと
- 箇条書きで簡潔に記述
- 参照が必要な詳細はファイルパスで指定
- プロジェクト固有のルールのみ記載
```

**階層的な CLAUDE.md の活用**：

```
~/.claude/CLAUDE.md        ← 全プロジェクト共通（出力ルール等）
./CLAUDE.md                ← プロジェクト固有（コーディング規約等）
./src/CLAUDE.md            ← ディレクトリ固有（モジュール説明等）
```

共通ルール（genshijin の出力ルール等）はグローバルに、プロジェクト固有のルールはローカルに配置することで、無駄な読み込みを減らせる。

### .claudeignore で不要ファイルを除外

Claude Code がコンテキストに読み込むファイルを制限する。

```plaintext
# .claudeignore
node_modules/
dist/
build/
*.lock
*.log
.next/
coverage/
```

### /compact の戦略的な活用

`/compact` はコンテキストウィンドウを要約・圧縮するコマンドだ。auto-compact（コンテキスト容量 95% で自動発動）を待つのではなく、**能動的に使う** のがポイント。

**compact すべきタイミング**：
- 探索フェーズが終わり、実装に移る前
- 機能の実装が一段落したとき
- 大きなコンテキストスイッチの前

**compact を避けるべきタイミング**：
- マルチファイルリファクタリングの途中
- デバッグセッションの最中
- 関連する連続的な変更の途中

`/context` コマンドで現在の容量を確認し、**60% 程度で proactive に compact する** のが理想。95% の auto-compact は「緊急避難」であり、その時点で既に出力品質は劣化している。

### Extended Thinking の制御

デフォルトでは thinking トークンが最大 31,999 トークン消費される。タスクの複雑さに応じて制御する。

```json
// ~/.claude/settings.json
{
  "env": {
    "MAX_THINKING_TOKENS": "10000"
  }
}
```

- 単純なタスク：Option+T（macOS）/ Alt+T で thinking 自体を OFF
- 中程度のタスク：10,000 トークンに制限（hidden cost 約 70% 削減）
- 複雑なアーキテクチャ設計：デフォルトのまま

### サブエージェントモデルの最適化

Task ツール（サブエージェント）のモデルを軽量なものに変更する。

```json
// ~/.claude/settings.json
{
  "env": {
    "CLAUDE_CODE_SUBAGENT_MODEL": "haiku"
  }
}
```

サブエージェントはファイル探索や情報収集に使われることが多く、Haiku で十分な場合がほとんどだ。これだけでサブエージェントのコストが **約 80% 削減** される。

## 3 つを組み合わせた効果

それぞれのアプローチは独立しており、併用できる。典型的な 30 分セッションでの理論的な削減効果を計算してみる。

### トークン消費の内訳（最適化前）

| カテゴリ | トークン数 | 割合 |
|---------|----------|------|
| CLAUDE.md + システム入力 | 30,000 | 15% |
| コマンド出力（ls, git, test 等） | 118,000 | 59% |
| Claude の応答出力 | 52,000 | 26% |
| **合計** | **200,000** | **100%** |

### 最適化後

| カテゴリ | 最適化前 | 最適化後 | 手法 | 削減率 |
|---------|---------|---------|------|--------|
| CLAUDE.md + システム入力 | 30,000 | 18,000 | アプローチ 3 | 40% |
| コマンド出力 | 118,000 | 23,900 | RTK | 80% |
| Claude の応答出力 | 52,000 | 10,400 | genshijin | 80% |
| **合計** | **200,000** | **52,300** | **3 手法併用** | **約 74%** |

**74% のトークン削減** — つまり、同じセッション時間で約 4 倍の作業ができる計算になる。

テスト実行が多い開発セッション（テストランナー出力 90% 削減の恩恵大）では、**80〜90% の削減** も十分現実的だ。

## まとめ

| アプローチ | 難易度 | 効果 | 導入時間 |
|-----------|--------|------|---------|
| genshijin（プロンプト最適化） | 低 | 出力 80% 削減 | 5 分 |
| RTK（CLI プロキシ） | 低 | コマンド出力 60〜90% 削減 | 5 分 |
| CLAUDE.md / 設定最適化 | 中 | 入力 40% 削減 | 30 分 |

3 つとも「導入して損はない」最適化だ。特に genshijin と RTK は 5 分で導入できて効果が即座に体感できるので、まずはこの 2 つから試してみてほしい。

トークン消費の削減は、単なるコスト節約ではない。コンテキストウィンドウが圧迫されにくくなることで、**Claude の出力品質自体が向上する**。限られたコンテキストに本当に必要な情報だけを詰め込むことで、より的確な応答が得られる。

節約と品質向上を同時に実現できる — それがトークン最適化の本質だ。
