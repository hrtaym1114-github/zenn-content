## この記事で分かること

Claude Code のトークン代に怯えて「削減ツール」を探すと、いま日本語圏でもこの4つが必ず出てきます。

- **rtk**（Rust Token Killer）
- **headroom**（44.3k⭐、Netflixのエンジニア発）
- **lean-ctx**
- **h5i**

そして全部が「**最大90〜99%削減**」と謳っています。ここで多くの人がこう詰まります。

> 「で、結局どれを入れればいいの？ 全部？ どれか1つ？ 重複しない？」

結論を先に言うと、**この4つは競合していません。圧縮する“レイヤー”が違うので、正しくは「積層（layer）」して使います。** rtk と headroom は同時に入れて両方効きます。

この記事は、4ツールを「同じ土俵の比較」ではなく「**役割分担の地図**」として整理します。読み終えると、あなたの使い方（コードベース中心か、長時間セッション中心か、監査ログが要るか）に応じて、**入れるべきツールと入れる順番**が決まります。

:::message
**対象読者**: Claude Code / Cursor / Codex を日常的に使い、トークン消費（＝API代 or レート上限）に困っている人。「削減ツールが多すぎて選べない」状態の人。
:::

## ★ なぜ混乱するのか — 「最大99%削減」が4回出てくる理由

4つすべてが「最大99%削減」と言えるのは、**測っている対象が違うから**です。同じ数字でも、削っている場所が別物なのです。

LLMエージェントに送られるトークンは、ざっくり4つの層に分けられます。

1. **シェル出力層** — `git diff` `git log` `grep` `ls -R` などコマンドの巨大な標準出力
2. **ファイル読み込み層** — `Read` でソースを丸ごと読む、同じファイルを何度も読み直す
3. **会話コンテキスト層** — 長時間セッションで膨れ上がる過去のやり取り全体
4. **記録・監査層** — 圧縮した元データを後から完全復元できるか（provenance）

「最大99%削減」という同じ言葉が、**1の話なのか3の話なのか**で意味がまったく変わります。ここを混同したまま「どれが一番削れる？」と比較すると、永遠に答えが出ません。

4ツールはそれぞれ**別の層**を主戦場にしています。だから比較ではなく地図なのです。

![Claude Codeトークン削減ツール4兄弟の役割分担マップ。シェル出力層=rtk/h5i、ファイル読み込み層=lean-ctx、会話コンテキスト層=headroom、記録・監査層=h5i](/images/claude-code-token-tools-guide-2026/concept_token-tools-map.png)

| ツール | 主戦場の層 | ひとことで言うと |
|--------|-----------|----------------|
| **rtk** | ① シェル出力層 | コマンドの標準出力を圧縮 |
| **lean-ctx** | ② ファイル読み込み層 | 関数シグネチャ抽出・再読込キャッシュ |
| **headroom** | ③ 会話コンテキスト層 | 会話履歴全体をML圧縮（可逆） |
| **h5i** | ④ 記録・監査層 | 圧縮＋git保存で完全復元 |

> 💡 この表が頭に入れば、もう「どれか1つ」で悩む必要はありません。**自分のボトルネックがどの層か**を決めるだけです。

## 前提知識 — そもそもなぜトークンを削るのか

トークン削減が効く理由は2つあります。

1. **コスト**: API従量課金なら、入力トークンがそのまま課金額。長いコンテキストを毎ターン送るのは高い。
2. **精度（コンテキスト劣化）**: コンテキストが膨れると、モデルが本当に重要な情報を見失う「lost in the middle」が起きる。**削減は節約だけでなく、回答品質の維持でもある**。

ここが重要で、これら4ツールの良いものは「ただ消す」のではなく「**消しても答えが変わらない**」ことを設計目標にしています。実際、後述の headroom は標準ベンチ（GSM8K等）で**圧縮しても正答率が落ちない**ことを示しています（※2026年6月時点の公開ベンチ）。

## 核心 — 4ツールが「競合しない」の実例

一番効くのは、**層をまたいで積む**ことです。代表例が `rtk + headroom`。

- `rtk` が **コマンド実行の瞬間**に巨大な `git diff` を圧縮する（① 入口で削る）
- `headroom` が **セッション全体**で過去の会話を圧縮し続ける（③ 蓄積を削る）

両者は削る場所が重ならないので、**足し算で効く**。これが「競合ではなく積層」の意味です。

逆に、同じ層を狙うツール同士（例: シェル出力層の rtk と h5i）は**役割が近い**ので、片方を選ぶ判断になります。h5i は「圧縮＋gitで完全復元（監査ログ）」が主目的なので、**純粋な削減なら rtk、復元可能な記録が要るなら h5i** という棲み分けです。

> ⚠️ ここが整理のキモ: **競合するのは「同じ層」のツールだけ**。違う層なら積めます。

## 5つの「層別ベンチ」— どの層で何%削れるのか

公開ベンチと各公式READMEから、層ごとの削減率の代表値をまとめます（※すべて2026年6月時点・出典は各リポジトリ／公開ベンチ。**自分のワークロードで必ず再計測**を）。

![層別トークン削減率の棒グラフ。lean-ctx再読込99.9%、h5i git log -p 99.8%、rtk git diff 99%、rtk grep 97.6%、lean-ctx関数抽出96%、headroom会話93%、headroomコード検索92%、rtk git log 84%、headroom Issueトリアージ73%。同じ「最大99%」でも削る層が違うことを示す](/images/claude-code-token-tools-guide-2026/statistical_token-reduction-by-layer.png)

1. **シェル出力層（rtk）**: `git log` で約84%、`git diff` で約99%、`grep` で約97%。巨大で反復的な出力ほど効く。
2. **シェル出力層（h5i）**: `git log -p` で約99%、`grep` で約94%。ただし `ls -laR` のような小さい出力では**オーバーヘッドでむしろ増える**ことがある。
3. **ファイル読み込み層（lean-ctx）**: 関数シグネチャのみ抽出で約96%、同一ファイルの再読込キャッシュは**ほぼゼロ（十数トークン級）まで圧縮**。一方 `git diff` は意図的に**素通し（0%）**。
4. **会話コンテキスト層（headroom）**: 約30万トークンの会話で約93%削減。GSM8K（算数）で正答率劣化なし、TruthfulQA はむしろ微改善との報告。可逆圧縮（CCR）で元データはローカル保持、必要時に復元。
5. **実ワークロード（headroom 公式）**: コード検索92%、SREデバッグ92%、Issueトリアージ73%。標準ベンチ（GSM8K/SQuAD/BFCL等）では19〜32%圧縮で精度維持。

> 同じ「99%」でも、`git diff`（rtk/h5i）と再読込キャッシュ（lean-ctx）と会話圧縮（headroom）では**まったく別の節約**だと分かります。

## 公式の考え方 — headroom が「可逆」にこだわる理由

headroom が他と一線を画すのは **CCR（可逆圧縮）** です。圧縮してLLMに渡すペイロードは情報を間引いていますが、**元データはローカルにそのまま残り**、モデルが「やっぱり詳細が要る」となったら `headroom_retrieve` で完全復元できます。

これは「**lossy（不可逆）に削ると、後でモデルが困る**」という失敗を避けるための設計です。トークン削減ツールの最大のリスクは「削りすぎて答えが劣化する」こと。可逆性はその保険になります。

加えて headroom は **CacheAligner** でプレフィックスを安定させ、**KVキャッシュのヒット率**を上げます。これは「削減」とは別軸で、キャッシュが効くと**さらに実コストが下がる**という二段構えです。

## やりがちなアンチパターン 6選

トークン削減ツールでハマる典型を挙げます。

1. **「一番削れるツール」を1つだけ探す** — 層が違うので「一番」は存在しない。ボトルネック層を特定するのが先。
2. **小さい出力にも圧縮をかける** — `ls` 程度の小出力は、圧縮オーバーヘッドで**逆に増える**ことがある（h5iの例）。閾値を設ける。
3. **不可逆圧縮で重要情報を消す** — エラーログやスタックトレースを要約しすぎてデバッグ不能に。**可逆（CCR/h5iのgit保存）を選ぶか、対象を選別**する。
4. **diff を圧縮対象から外し忘れる / 逆に潰しすぎる** — lean-ctx は diff を素通しにする思想。**diffは情報密度が高いので潰し方に注意**。
5. **キャッシュを壊す圧縮をする** — プレフィックスが毎回変わる圧縮をすると KVキャッシュが効かず、削減と引き換えにキャッシュ割引を失う。
6. **「導入したら終わり」で計測しない** — 削減率はワークロード依存。**自分のログで before/after を測る**まで効果は分からない。

## 判断フロー — あなたはどれを入れるべきか

ボトルネック層から逆引きします。

- **`git diff` / `grep` / ログでコンテキストが爆発している** → まず **rtk**（最も簡単・効果大）
- **大きなコードベースを何度も読み直している** → **lean-ctx**（再読込キャッシュが劇的）
- **長時間セッションで会話履歴が重い／API代が高い** → **headroom**（会話層を圧縮、可逆で安全）
- **削った元データを監査・完全復元したい（チーム/規制）** → **h5i**（git provenance）

そして**積層の黄金パターン**は:

> **rtk（入口でシェル出力を削る）＋ headroom（セッション全体を削る）**

まずこの2つを積むのが、最小手間で最大効果のスタート地点です。

## まとめ

- Claude Code のトークン削減ツール4種（**rtk / lean-ctx / headroom / h5i**）は**競合ではなく、層が違う＝積層して使う**。
- 「最大99%削減」が4回出てくるのは、**削っている層が違う**から。同じ土俵で比べてはいけない。
- 選び方は「一番削れるツール探し」ではなく「**自分のボトルネック層から逆引き**」。
- 迷ったら **rtk（シェル出力）＋ headroom（会話コンテキスト）** の積層から始める。可逆性（CCR / git保存）で**削りすぎ事故**を防ぐ。
- 削減率はワークロード依存。**必ず自分のログで before/after を測る**こと。

トークン削減は「節約」であると同時に「**コンテキスト劣化を防いで精度を保つ**」施策でもあります。地図を持って、自分の層から積んでいきましょう。
