# はじめに

Claude Code や Codex を使い込むと、`CLAUDE.md` や `AGENTS.md` の周りにファイルが増えていきます。`.claude/rules/`、`.claude/agents/`、`.claude/skills/`、`.claude/commands/`、そして Codex 用の `.agents/skills/`。最初は1枚のメモだったものが、いつの間にか「エージェントが毎回読む設定の束」になります。

そして、その束は静かに壊れます。コマンドの名前を変えたのに、rules の中の古い名前はそのまま。使わなくなったエージェントの定義ファイルが残り続ける。「執筆は○○モデルで」と書いたモデル名が、もう既定値ではない。

人間なら「古いな」と読み飛ばせる記述も、エージェントは指示として読みます。存在しないファイルを探しに行き、廃止したコマンドを呼び、固定されたモデル名を前提に手順を組み立てます。

## この本で渡すもの

この本は「指示ファイルの書き方」の本ではありません。**書いたあとに腐らせない運用**の本です。

- 無料章（00〜03）: 指示ファイルが腐る仕組みと、既存の検知手段（手作業監査・リンクチェッカー・LLMレビュー・静的lint）の比較、公式ドキュメントが何を約束していて何を約束していないか
- 有料章（04〜07）: 筆者の個人運用リポジトリで実際に行った監査のログ、LLMなしの静的チェックを当てて出た **1,047件** の警告をどう仕分けたか、直し方と再発防止（rules層・hooks・CI）の手順、そのまま使えるチェックリスト

## 前提と、書かないこと

- 題材は筆者（hrtaym1114）が Claude Code と Codex の両方から使っている、個人の Obsidian Vault 兼エージェント作業場です。チーム開発の大規模リポジトリではありません。
- 数字は実際のコミットと、2026-10-12 に読み取り専用で実行した静的チェックの結果だけを使います。「何%改善した」のような効果測定はしていないので書きません。
- 内部のパスや個人的な情報は、一般化して書き換えています。
- 静的チェックには自作の [agent-docs-lint](https://github.com/hrtaym1114-github/agent-docs-lint)（v0.1.0、2026-10-06）を使いました。これは実装の一例で、同じ考え方は数十行のスクリプトでも再現できます。本書の手順はツールに依存しません。
