# 指示ファイルが腐る4つの仕組み

指示ファイルの腐り方は、ほぼ次の4つに分けられます。どれも「書いたときは正しかった」ことが共通点です。

## 1. 参照先が消える（dead reference）

指示ファイルは他のファイルを指します。「詳細は `docs/xxx.md` を参照」「`/blog-write` を実行」「テンプレートは `prompts/yyy.md`」。参照先をリネーム・削除・移動しても、参照元は自動では直りません。

エージェントにとって、存在しないパスは「探すべきもの」です。見つからなければ似た名前のファイルを探し、それっぽいものを読んで進みます。エラーで止まらないので、気づくのが遅れます。

## 2. 固定値が古くなる（stale constants）

モデル名、プラン名、件数、サンプル数、日付つきの状態。「執筆は○○ 3.x Flash」「コマンドは約60本」「学習サンプル292件」のような記述です。

これらは書いた日の事実で、指示ではありません。けれど指示ファイルに書くと、エージェントは「いまの前提」として扱います。

## 3. 誰も呼ばない定義が残る（orphans）

試しに作ったエージェント、別のワークフローに置き換えたスキル、雛形ファイル。どこからも参照されない定義は、読み込まれれば文脈を消費し、名前が似ていれば誤って選ばれます。

## 4. 二重管理がずれる（mirror drift）

Claude Code 用の `.claude/skills/` と Codex 用の `.agents/skills/` のように、同じ内容を2か所に置く運用はよくあります。片方だけ直せば、もう片方は古いまま残ります。`CLAUDE.md` と `AGENTS.md` の両方に同じ方針を書いている場合も同じです。

## なぜ人間のドキュメントより腐りやすいのか

人間向けの README が古くても、読む人は文脈で補います。指示ファイルは違います。

- 毎セッション、全文が（あるいは条件つきで）読み込まれる
- 書いてあることは「従うべきこと」として扱われる
- 誤りに気づいても、エージェントは指示ファイル自体を直そうとはしない（頼まない限り）

つまり、腐った1行の影響は「読まれる回数」だけ繰り返されます。

Kevin Liao の [Agents Don't Need Memory. They Need Documentation.](https://liao.gg/blog/agents-dont-need-memory)（2026-10-03、10-05更新）は、エージェントに必要なのは記憶プラグインではなくドキュメントだと主張し、鮮度を保つ規律として「真実が変わったら追記せず書き換える」ことを挙げています。本書はその「書き換える」側の、地味な運用の話です。
