# 「1人総合商社」とは何か

## 仕組みは作れる。でも、回らない。

2026年2月、私は半自動投稿システムを完成させた。X.com、リベシティ、ブログ、note、Borders Daily。5チャネルへの投稿をAIで生成し、Vault内で管理し、適切なフォルダへ自動振り分けする仕組みだ。

ところが、投稿実績は **0件** だった。

仕組みは完璧だった。コマンドを叩けば投稿文が出てきた。ところが「最後の公開ボタン」を押す心理的な障壁が、思った以上に大きかった。「この投稿で本当にいいのか」「もう少し直したい」「タイミングが悪い気がする」——そうやって@TODOフォルダにドラフトが溜まり、結局1本も公開せずに3週間が過ぎた。

ジャーナリングでこのパターンを振り返ったとき、はっきり見えたことがある。

> **私の課題は「仕組みを作れるか」ではない。「仕組みを回せるか」だ。**

そして気づいた。問題は意志力でも時間でもない。**「1人で全部やる」前提が間違っている**のだ。

## 「1人で副業」は物理的に無理がある

副業で稼ぐと言うと、こんなToDoが並ぶ。

- ネタ収集
- リサーチ
- 執筆
- 編集・校正
- 図解作成
- SNS告知
- 効果測定
- 次の企画

これを本業のあとに、家事育児のあとに、全部1人でやる。「平日2時間しかない」「土日も家族の予定がある」——副業が続かない人の声の大半は、この**物理的な無理**に起因する。

巷の解決策は2つに分かれる。

1. **アウトソース**: クラウドソーシングや外注で人を雇う。お金がかかる。
2. **収益化を諦める**: 「趣味でいい」「楽しめればOK」と割り切る。

このどちらでもない第3の道がある。**AIエージェントを「組織」として設計する**ことだ。

## AI × 組織設計 = 「1人なのに10人分の体制」

エージェントとは、特定の役割と専門性を持つAI人格のことだ。たとえば「コンテンツ部門長」というエージェントを定義すると、そのエージェントは「コンテンツ戦略を立てる」「チャネル別ライターに指示を出す」「進捗を確認する」といった役割を持ち、その範囲で自律的に動く。

Claude Codeの Agent Skills 機能を使えば、これらのエージェント定義をプロジェクト内のファイルとして保存できる。一度書けば、何度でも呼び出せる。指示を出すと、その役割に従って動いてくれる。

私はこれを「組織」として設計した。

```
CEO（私）= 最終意思決定者
│
COO Agent（全部門の司令塔）
│
├── 📢 Content Marketing Div（コンテンツ部）
├── 🧠 Advisory Board Div（顧問団）
├── 🔬 R&D Division（研究開発部）
├── 👤 Career & Comms Div（人事・通信部）
└── ⚙️ Tech Infrastructure Div（情報基盤部）
```

会社員1人が、5部門の擬似組織を持っている状態だ。各部門にはさらに専門エージェントがぶら下がっており、全体で29人分の「役割」を持つ。

これが「1人総合商社」の正体である。

## 3ヶ月運用してわかったこと

2026年1月から運用を開始し、執筆時点（4月）で約3ヶ月が経過した。実数で言うと、こうなる。

| 指標 | 運用前（2025年12月） | 運用後（2026年4月） |
|------|---------------------|---------------------|
| カスタムコマンド数 | 5 | **68** |
| エージェント定義数 | 0 | **29** |
| 同時運用チャネル | 1（X.comのみ） | **5（X.com・リベシティ・ブログ・note・Borders Daily）** |
| 月間コンテンツ本数 | 4本 | **40本以上** |
| 1日の副業作業時間 | 2-3時間 | **平日 30分-1時間、休日 2-3時間** |

「仕組みは作れるが回らない」だった私が、半年で**40倍のアウトプット**を出すようになった。しかも、作業時間はむしろ減っている。

魔法ではない。エージェント組織が「決める」「動く」「報告する」を肩代わりするからだ。私は「最終確認」と「方向性の指示」だけをすれば良い。

## この本で公開する設計図

本書では、私が実際に運用している組織の**全設計図**を公開する。

- 5部門のエージェント構造とその設計思想
- 各エージェント定義ファイル（コピーして使える）
- 68個のカスタムコマンドの一覧と用途
- CLAUDE.md（プロジェクトの脳）の設計パターン
- Daily Kanban連携の仕組み
- ファイル所有権ルールによる排他制御
- 失敗談（仕組みが目的化した話、エージェントが暴走した話）

公開する理由はシンプルだ。**この本自体が、この仕組みで作られている**からだ。リサーチ、構成、ドラフト、図解、販促文——すべてエージェントが下書きを作り、私が確認している。

私が3ヶ月かけて試行錯誤した内容を、あなたは**完成形から始められる**。テンプレートをコピーして自分の文脈に合わせれば、最短1週間で「1人総合商社」を立ち上げられる。

## 本書の対象読者

本書は次のような人に向けて書いている。

- **副業を始めたい会社員** — Claude Codeを使っていて、複数チャネルを同時運用したいが時間が足りない人
- **AI活用を極めたい技術者** — Claude Code、CLAUDE.md、hooks、skills、Agent Teamsの実践的な設計パターンを知りたい人
- **個人で稼ぐ力をつけたいフリーランス** — 「仕組み化」で1人ビジネスをスケールさせたい人

逆に、次のような人には向かない。

- Claude Codeをまだ使っていない人（公式ドキュメントが先）
- 入門書を探している人（本書は「実運用」が前提の応用書）
- アプリ開発の自動化を目的にしている人（本書はコンテンツ運用が主軸）

## 「実運用3ヶ月」の生データを公開する

本書の差別化要因は、ただ1つ。**「実際に動いているシステムの全貌」が見えること**だ。

Claude Code関連の書籍・記事は2026年時点で増えている。しかし、その大半は「機能紹介」と「便利なプロンプト集」に留まっている。「実際にこう運用しています」「3ヶ月運用してこう失敗しました」「だからこう改善しました」——そういう運用記録は、ほぼ存在しない。

私が公開するのは、**模倣不可能な実運用データ**だ。

- どのエージェント定義が機能し、どれが空回りしたか
- どのコマンドが毎日使われ、どれが死蔵されたか
- 3ヶ月で何回 CLAUDE.md を書き直したか
- マネタイズの試行錯誤と、現時点での収益（正直に書く）

「Claude Codeでこういうことができます」ではなく「**Claude Codeで実際にこう運用しています**」を伝えるのが本書の役割だ。

## 章構成のガイド

本書は4部・12章で構成される。

| Part | テーマ | 章 |
|------|--------|----|
| **Part 0** | はじめに | Ch.00（本章） |
| **Part 1** | 設計編 — CLAUDE.mdで「脳」を作る | Ch.01〜03 |
| **Part 2** | 組織編 — エージェント組織を構築する | Ch.04〜06 |
| **Part 3** | 運用編 — 日常ワークフローを回す | Ch.07〜09 |
| **Part 4** | 拡張編 — さらに先へ | Ch.10〜11 |

読み方は人によって変わる。

- **「いますぐ動くものが欲しい」人**: Ch.03（カスタムコマンド）→ Ch.07（日常ワークフロー）から読み始めて、必要に応じて遡る
- **「設計思想から理解したい」人**: Ch.01から順に読む
- **「組織設計に興味がある」人**: Ch.04（エージェント組織パターン）からスタート

Appendixには「全コマンドリファレンス」「エージェント定義テンプレート」「CLAUDE.mdテンプレート」を収録した。コピー&ペーストですぐに動かせる。

## さあ、始めよう

「仕組みを作っても回らない」と感じている人へ。

問題はあなたの意志力ではない。**設計が間違っている**だけだ。1人で全部やる前提を捨てて、エージェントに「組織」として動いてもらえば、副業は回り始める。

私がそうだったように、あなたもこの設計図から始められる。

それでは、Part 1から具体的な設計に入っていこう。最初に取り組むのは **CLAUDE.md** ——プロジェクトの「脳」となるファイルの設計思想だ。
