# 「1人総合商社」とは何か

## この本は8ヶ月で3,385円を稼いだ

最初に、いちばん都合の悪い数字を出しておく。

私がAIエージェント組織を組んで副業を運用し、8ヶ月で得た売上は **3,385円** だ。内訳は本が2冊。1冊は今あなたが読んでいるこの本（1,900円）、もう1冊は別の本（2,000円）。手数料を引いた受取額の合計が3,385円である。月あたり約423円。時給に換算するのはやめておく。

Claude Code関連の本を開くと、たいてい「AIで月○万円」「作業時間が9割削減」と書いてある。この本にはそれが無い。**8ヶ月やって、まだ黒字とは呼べない。**

それでも私がこの設計図を売っているのは、稼げなかったことと**組織が動いていること**は別の話だからだ。

- 84個のカスタムコマンド
- 28個のエージェント定義
- 19個のGitHub Actionsワークフローが、私が寝ている間に走っている
- 1,377コミット。うち605コミットは本書の初版を書いた後に積まれたもの

このシステムは今日も動いている。私が「やる気」を出さなくても動いている。**回すことには成功した。稼ぐことにはまだ成功していない。** 本書はその両方を、数字ごと開示する。

初版（2026年5月）で私はこう書いた——「マネタイズの試行錯誤と、現時点での収益（正直に書く）」。この改訂版は、その約束を果たすために書いている。

## 仕組みは作れる。でも、回らない。

2026年2月、私は半自動投稿システムを完成させた。X.com、リベシティ、ブログ、note、Borders Daily。5チャネルへの投稿をAIで生成し、Vault内で管理し、適切なフォルダへ自動振り分けする仕組みだ。

ところが、投稿実績は **0件** だった。

仕組みは完璧だった。コマンドを叩けば投稿文が出てきた。ところが「最後の公開ボタン」を押す心理的な障壁が、思った以上に大きかった。「この投稿で本当にいいのか」「もう少し直したい」「タイミングが悪い気がする」——そうやって@TODOフォルダにドラフトが溜まり、結局1本も公開せずに3週間が過ぎた。

ジャーナリングでこのパターンを振り返ったとき、はっきり見えたことがある。

> **私の課題は「仕組みを作れるか」ではない。「仕組みを回せるか」だ。**

そして気づいた。問題は意志力でも時間でもない。**「1人で全部やる」前提が間違っている**のだ。

## 「1人で副業」は物理的に無理がある

副業で稼ぐと言うと、こんなToDoが並ぶ。

- ネタ収集
- リサーチ
- 執筆
- 編集・校正
- 図解作成
- SNS告知
- 効果測定
- 次の企画

これを本業のあとに、家事育児のあとに、全部1人でやる。「平日2時間しかない」「土日も家族の予定がある」——副業が続かない人の声の大半は、この**物理的な無理**に起因する。

巷の解決策は2つに分かれる。

1. **アウトソース**: クラウドソーシングや外注で人を雇う。お金がかかる。
2. **収益化を諦める**: 「趣味でいい」「楽しめればOK」と割り切る。

このどちらでもない第3の道がある。**AIエージェントを「組織」として設計する**ことだ。

## AI × 組織設計 = 「1人なのに10人分の体制」

エージェントとは、特定の役割と専門性を持つAI人格のことだ。たとえば「コンテンツ部門長」というエージェントを定義すると、そのエージェントは「コンテンツ戦略を立てる」「チャネル別ライターに指示を出す」「進捗を確認する」といった役割を持ち、その範囲で自律的に動く。

Claude CodeのAgent Skills機能を使えば、これらのエージェント定義をプロジェクト内のファイルとして保存できる。一度書けば、何度でも呼び出せる。指示を出すと、その役割に従って動いてくれる。

私はこれを「組織」として設計した。

```
CEO（私）= 最終意思決定者
│
COO Agent（全部門の司令塔）
│
├── 📢 Content Marketing Div（コンテンツ部）
├── 🧠 Advisory Board Div（顧問団）
├── 🔬 R&D Division（研究開発部）
├── 👤 Career & Comms Div（人事・通信部）
└── ⚙️ Tech Infrastructure Div（情報基盤部）
```

会社員1人が、5部門の擬似組織を持っている状態だ。各部門にはさらに専門エージェントがぶら下がっている。

これが「1人総合商社」の正体である。

## 8ヶ月運用してわかったこと

2026年1月から運用を開始し、この改訂版の執筆時点（8月末）で **240日** が経過した。実数で言うとこうなる。

| 指標 | 運用前<br>2025年12月 | 初版執筆時<br>2026年5月 | 改訂版<br>2026年8月 |
|------|------|------|------|
| カスタムコマンド数 | 5 | 68 | **84** |
| エージェント定義数 | 0 | 29 | **28** |
| スキル定義数 | 0 | 14 | **19** |
| 常駐ルール数 | 0 | 3 | **7** |
| GHA無人ワークフロー | 0 | 数本 | **19本稼働 / 11本廃棄** |
| 同時運用チャネル | 1 | 5 | **5** |
| 累計コミット | — | 772 | **1,377** |
| 累計売上 | ¥0 | ¥2,000 | **¥3,385** |

初版から3ヶ月で、コマンドは16個増え、エージェントは**1個減った**。

この「減った」がこの改訂版の主題のひとつだ。8ヶ月目のシステムは、5ヶ月目より**賢くなったのではなく、余計なものが剥がれた**。廃棄したGHAワークフロー11本が、そのまま私が捨てた仮説の数である。

## 初版から何が変わったか

本書の初版は「組織をどう組むか」の設計図だった。この改訂版では、そこに**3ヶ月間の実運用が突きつけた現実**を4章ぶん追加している。

### 追加章1: 常駐ルール層 — エージェントに「憲法」を与える

初版の設計には穴があった。エージェント定義とコマンドは「呼ばれたときに何をするか」しか書けない。**呼ばれていないときに守るべきこと**を書く場所が無かったのだ。

その結果、ファクトチェックを通過した記事が、堂々と古い情報を載せて公開された。正誤は検査されていた。しかし**「正しいが、古い」**を誰も見ていなかった。

いま私のVaultには7本の常駐ルールがある。全セッションに自動で読み込まれ、どのエージェントが動いても効く層だ。Ch.12ではこの層の設計と、7本それぞれが**どの事故を受けて生まれたか**を書く。ルールは思想からは生まれない。事故から生まれる。

### 追加章2: 無人運用 — 私が寝ている間に組織を動かす

初版の運用はすべて「私がClaude Codeを起動している間」に限られていた。半自動である。

現在は19本のGitHub Actionsワークフローが、私の関与なしに走っている。朝7時にトレンドを収集し、月曜8時に週次ニュースを投稿し、週末にエンゲージメントを分析する。ローカルではlaunchdが音声コンテンツを毎日生成している。

Ch.13ではこの無人層の作り方と、**無人化したからこそ起きた事故**を書く。たとえば「成果物が完成しているのに、失敗扱いになって消える」というGitHub Actions特有の罠がある。私は2回踏んで、2回とも生成物を失いかけた。復元方法も含めて書く。

### 追加章3: 自己改善ループが暴走した話

これがいちばん書きたかった章だ。

「投稿する→反応を測る→効いた型を学習する→次の投稿に反映する」。自動で賢くなるループを組んだ。理屈は正しい。ガードも入れた。サンプル数の下限も設けた。

**それでもループは暴走した。**

学習の原材料であるプロフィールクリックが、17投稿で累計**2件**しか無かったからだ。順位はほぼ偶然で決まり、同じテーマが「効いた投稿1位」と「効かなかった投稿2位」に同時に載る矛盾が出た。それを生成プロンプトが「学習結果を最優先」で読み込み、投稿は私の運用プロセスの話へ収束していった。リーチは中央値548から**36**へ落ちた（15分の1）。

私がこれに気づいたのは、システムのアラートではない。**人間に「全然面白くない」と言われたからだ。**

Ch.14では、疎なシグナルで学習するループが必ず持つこの構造的欠陥と、`evidence floor`（証拠の下限）という対策を書く。**証拠が足りないとき、システムは黙らなければならない。** ランキングは証拠がゼロでも1位を出してしまう。

### 追加章4: 収益の現実 — 3,385円の全内訳

冒頭に書いた数字の全貌を開示する。何を売り、何が売れず、何を封印し、その封印が**間違いだった**か。

たとえば私は2026年5月末に「Zenn Booksは書くな」と自分で決めている。工数が重く、途中で止まる形状だと判断したからだ。ところが**その時点で本は2冊とも公開済みで、すでに1冊売れていた**。3ヶ月後に振り返ると、この期間に現金を生んだのはZenn Booksだけで、代わりに主軸に据えた企画は着手すらされていなかった。

私は自分の実績を無視して、机上の判断で正解を封印していた。この種の失敗は仕組みでは防げない。**何を測っていたか**の問題だからだ。

X.comの数字も出す。30日で35投稿・4,687インプレッション、フォロワー純増 **0人**。この0人が何を意味していたかも書く。

## この本で公開する設計図

本書では、私が実際に運用している組織の**全設計図**を公開する。

- 5部門のエージェント構造とその設計思想
- 各エージェント定義ファイル（コピーして使える）
- 84個のカスタムコマンドの一覧と用途
- CLAUDE.md（プロジェクトの脳）の設計パターン
- 常駐ルール7本と、それぞれを生んだ事故
- GitHub Actionsによる無人運用と、その罠
- Daily Kanban連携の仕組み
- ファイル所有権ルールによる排他制御
- 8ヶ月ぶんの失敗と、収益の実データ

公開する理由はシンプルだ。**この本自体が、この仕組みで作られている**からだ。リサーチ、構成、ドラフト、図解、販促文——すべてエージェントが下書きを作り、私が確認している。この改訂版の数値集計も、エージェントが自分のVaultを数えて出した。

私が8ヶ月かけて試行錯誤した内容を、あなたは**完成形から始められる**。ただし、そのあと**あなた自身の失敗が始まる**ことも約束しておく。完成形は出発点であって、到達点ではない。

## こういう人が読むと元が取れる

「Claude Codeの記事は読んだ。機能はわかった。**で、実際どう運用しているんだ？**」

そう思ったことがあるなら、この本はそのために書かれている。

Claude Code関連の書籍・記事は2026年時点で相当増えた。しかしその大半は「機能紹介」と「便利なプロンプト集」に留まっている。「実際にこう運用しています」「8ヶ月運用してこう失敗しました」「だからこう改善しました」——そういう運用記録は、ほぼ存在しない。

理由は単純で、**書くには8ヶ月動かし続けるしかない**からだ。機能紹介は公式ドキュメントを読めば今日書ける。運用記録は240日待たないと書けない。

私が公開するのは、その240日ぶんの生データだ。

- どのエージェント定義が機能し、どれが空回りしたか
- どのコマンドが毎日使われ、どれが死蔵されたか
- 廃棄した11本のワークフローが、何を証明したか
- 自動化が静かに壊れたとき、どうやって気づいたか（そして、気づけなかったか）

逆に、次のような人には向かない。正直に書いておく。

- **Claude Codeをまだ使っていない人** — 公式ドキュメントが先。本書は「起動できる」前提から始まる
- **入門書を探している人** — 本書は実運用の応用書で、基本操作の説明はしない
- **「これを読めば稼げる」を期待している人** — 8ヶ月で3,385円の人間が書いた本である。稼ぎ方は書いていない。**回し方**が書いてある
- **アプリ開発の自動化が目的の人** — 本書はコンテンツ運用が主軸

## 章構成のガイド

本書は5部・16章で構成される。Ch.12以降が改訂版の新規章だ。

| Part | テーマ | 章 |
|------|--------|----|
| **Part 0** | はじめに | Ch.00（本章） |
| **Part 1** | 設計編 — CLAUDE.mdで「脳」を作る | Ch.01〜03 |
| **Part 2** | 組織編 — エージェント組織を構築する | Ch.04〜06 |
| **Part 3** | 運用編 — 日常ワークフローを回す | Ch.07〜09 |
| **Part 4** | 拡張編 — さらに先へ | Ch.10〜11 |
| **Part 5** | **改訂版追補 — 8ヶ月目の現実** | **Ch.12〜15** |

読み方は人によって変わる。

- **「いますぐ動くものが欲しい」人**: Ch.03（カスタムコマンド）→ Ch.07（日常ワークフロー）から読み始めて、必要に応じて遡る
- **「設計思想から理解したい」人**: Ch.01から順に読む
- **「組織設計に興味がある」人**: Ch.04（エージェント組織パターン）からスタート
- **「もう自分で組んである」人**: **Ch.12〜15だけ読めばいい**。あなたが次に踏む地雷が書いてある

## さあ、始めよう

「仕組みを作っても回らない」と感じている人へ。

問題はあなたの意志力ではない。**設計が間違っている**だけだ。1人で全部やる前提を捨てて、エージェントに「組織」として動いてもらえば、副業は回り始める。

そして8ヶ月後、あなたは私と同じ場所に立つ。**回っているが、まだ稼げていない**という場所だ。そこから先は、この本にも答えが無い。私もまだそこにいる。

だが少なくとも、**動かないシステムの前で意志力を責めている場所よりは、はるかに前**である。

それでは、Part 1から具体的な設計に入っていこう。最初に取り組むのは **CLAUDE.md** ——プロジェクトの「脳」となるファイルの設計思想だ。
