# CLAUDE.mdの設計思想

## まず、これが現実だ

Claude Codeを使い始めて1ヶ月。最初は「便利だ」と感じる。コードを書いてくれる。リファクタもする。質問にも答える。

ところが、しばらく使うと違和感が出てくる。

「`ls` の代わりに `Bash` で `ls -la` 走らせたのに、なんで `find` を使い始めたんだ」「あれ、フォルダ名を英語で書いてって言ったのに、また日本語で作ろうとしてる」「このプロジェクトのルールを毎回説明し直すの、しんどい」

毎回同じことを伝え直す疲れ。これがClaude Code、というかすべてのAIアシスタントを使い込んだ人が必ず通る通過儀礼だ。

CLAUDE.md は、この問題を真正面から解決するためのファイルだ。

## CLAUDE.md とは何か

CLAUDE.md とは、Claude Codeがプロジェクトに入った瞬間に自動で読み込む**プロジェクトルールの最上位ファイル**である。

`README.md` がプロジェクトの「使い方説明書」だとすれば、CLAUDE.md は **Claudeに対する「就業規則」** だ。

- どんなフォルダ構造を使っているか
- 命名規則は何か
- どのコマンドが用意されているか
- やってはいけないこと
- 期待する動き方

これらを1つのMarkdownファイルに書き、プロジェクトルートに置く。あとは Claude Code が自動で読み込み、その内容を前提として振る舞う。「毎回同じことを伝え直す」が消える。

## CLAUDE.md の3つの役割

私が3ヶ月運用してわかったのは、CLAUDE.md は次の3つの役割を兼ねるということだ。

### 1. プロジェクトの「脳」

最初の役割は「**プロジェクト全体の文脈をAIに渡す装置**」。

人間の脳に例えると、CLAUDE.md は**長期記憶**にあたる。Claude Codeはセッションが切れるたびに記憶がリセットされるが、CLAUDE.md は永続化された記憶として毎回読み込まれる。

「このプロジェクトは何をするものか」「どんな価値観で運営しているか」「過去にどんな意思決定をしたか」——これらを書いておくと、Claudeは毎回その文脈を持って入ってくる。

### 2. 「ルールブック」

2つ目の役割は「**禁止事項と必須事項のリスト**」。

たとえば私のVaultでは、次のようなルールを CLAUDE.md に明記している。

```markdown
## 作業範囲の制限（必須）

🔴 絶対に守るべきルール:
1. Vault（obsidian-1/）内でのみ作業すること
2. 禁止操作:
   - ファイルの削除（rm、unlink等）❌
   - フォルダの削除（rmdir、rm -r等）❌
3. 許可される操作:
   - ファイルの読み取り（Read）✅
   - 新規ファイルの作成（Write）✅
   - 既存ファイルの編集（Edit）✅
```

これだけで、Claudeは「ファイル削除しようかな」とは考えなくなる。安全性が劇的に上がる。

### 3. 「組織図と連絡先」

3つ目の役割は、Agent Skillsを本格的に使い始めると効いてくる「**どのコマンド・どのエージェントが何をするかの一覧**」。

```markdown
| コマンド | 説明 |
|---------|------|
| /daily | デイリーノート作成 + Kanban更新 |
| /weekly-review | 週次レビュー |
| /memo-to-inbox [ファイル] | メモをInbox形式に処理 |
```

これがあると、Claudeは「ユーザーが朝起きてきた」「『今日のメモ整理して』と言われた」というシグナルに対し、「`/memo-to-inbox` を使えばいいのか」と自分で判断できる。

組織で言えば「内線番号表」だ。誰がどの仕事をするか分かっていれば、無駄なやり取りが減る。

## 「最小限の脳」から「完全な脳」へ

CLAUDE.md は最初から完成形を目指さなくていい。むしろ**1日1行ずつ育てていく**のがいい。

私の経験では、CLAUDE.md は次の3段階を経て成長する。

### Stage 1: ミニマム（5-30行）

最初は次の4要素だけでいい。

```markdown
# CLAUDE.md

## このプロジェクトの目的
[何を作っているか、1文]

## 技術スタック
[使っている言語・フレームワーク]

## ルール
- [守ってほしいことを箇条書き]

## 禁止事項
- [絶対やってほしくないことを箇条書き]
```

これだけで「毎回同じことを伝え直す」の大半が消える。

### Stage 2: 運用ルール追加（100-300行）

しばらく運用すると、「あ、これも書いておけば良かった」が増える。

- フォルダ構造の説明
- 命名規則
- ファイル配置の判断フロー
- 関連ドキュメントへのリンク

このあたりまで来ると、CLAUDE.md は「**新人メンバーに渡すオンボーディング資料**」のような体裁になる。

### Stage 3: 組織化（500-3,000行）

Agent Skills を本格活用し始めると、CLAUDE.md は組織図を兼ねるようになる。

- 各エージェントの役割
- 部門ごとのファイル所有権
- コマンド一覧
- 朝/夕のワークフロー定義
- 外部システム連携情報

このStageまで来ると、もう「ルールブック」ではない。**プロジェクト全体の運用マニュアル兼組織図**になる。

私の現在のCLAUDE.mdは約3,000行ある。これは「肥大化して困った」のではない。「3ヶ月かけて自然に育った」結果がこの規模だ。

## 私のCLAUDE.mdの構造解説

参考までに、本書執筆時点でのCLAUDE.mdのアウトラインを紹介する。

```
1. セッション開始時の案内
2. 概要（Vaultの設計思想）
3. フォルダ構成
4. 命名規則
5. ファイル配置の判断フロー
6. 主要システムルール
7. Claudeコマンド一覧（68個）
8. Agent Teams コマンド
9. 図解・ビジュアル生成ルール
10. 1人総合商社 — エージェント組織図
11. Daily Kanban 連携
12. Notion連携・Google Analytics連携
13. コンテンツ戦略
14. 基本原則
15. AI支援のガイダンス
16. 作業範囲の制限（必須）
```

特徴は次の通り。

- **「セッション開始時の案内」を最初に置く**: 曖昧な入力で始まった時にClaudeが何をすべきかを最初に決める
- **判断フローを明示**: 「迷ったらここを見ろ」が分かるようにする
- **禁止事項を最後に置く**: 強い印象で締める（最後に読んだ内容ほど印象に残る）

## CLAUDE.md設計の5原則

3ヶ月の試行錯誤から導いた、CLAUDE.md設計の5原則を共有する。

### 原則1: WHY を書く、HOW は書かない

ダメな例:
```markdown
- 関数は20行以内
- 引数は3つ以内
- グローバル変数禁止
```

良い例:
```markdown
## コードレビューの哲学

このプロジェクトでは「読めば理解できる」を最優先する。
そのため、関数は短く、引数は少なく、状態は局所化する。
具体的な閾値は状況に応じて判断するが、迷ったら短い方を選ぶ。
```

WHYがあると、Claudeは閾値ギリギリのケースでも妥当な判断ができる。HOWだけだと、機械的にルールを適用して文脈を失う。

### 原則2: 否定形より肯定形

ダメな例:
```markdown
- ❌ コマンドの結果をユーザーに見せない
- ❌ 余計な説明をしない
- ❌ 確認を求めない
```

良い例:
```markdown
## 会話スタイル

- 簡潔に。タスクが終わったら成果だけ報告する
- 不明点があれば1つだけ質問する
- 危険な操作は実行前に確認する
```

否定形は「やらないことのリスト」だ。リストを暗記するだけで終わる。肯定形は「やるべきこと」を伝える。Claudeは判断できる。

### 原則3: 「迷ったら」を明示する

ルールの隙間で迷う場面は必ず発生する。その時の判断基準を書いておく。

```markdown
## ファイル配置の判断フロー

1. とりあえずメモ → 00_Memo/
2. 今週使う？ → 03_Input/
3. 3ヶ月後も参照する？ → 04_Memory/
4. 期限ありプロジェクト？ → 05_Output/Projects/
5. 期限なし継続活動？ → 05_Output/Areas/
6. **迷ったら → 01_Inbox/**（週次レビューで処理）
```

最後の「迷ったら」が一番重要。これがないと、判断不能の状態でClaudeが立ち往生する。

### 原則4: 例を入れる

抽象的なルールには必ず**具体例**を添える。

ダメな例:
```markdown
- ファイル名はハイフン区切り
```

良い例:
```markdown
- ファイル名はハイフン区切り
  - 良い例: `Cursor-キーボードショートカット.md`
  - 悪い例: `Cursor キーボードショートカット.md`（スペース）
  - 悪い例: `cursor_keyboard_shortcuts.md`（アンダースコア）
```

「これは良い」「これは悪い」のサンプルがあると、判断のブレが消える。

### 原則5: 重要度を明示する

すべてのルールが同じ重みではない。CLAUDE.mdが膨らんでくると、Claudeが「どれを優先すべきか」迷い始める。

```markdown
🔴 絶対に守るべきルール（破ったら停止）:
- ファイル削除禁止
- Vault外への作業禁止

⚠️ 強く推奨:
- 関数は短く保つ
- 命名は意味重視

💡 ヒント（参考程度）:
- リンクは1文に1-2個まで
```

絵文字でレベルを明示すると、Claudeは「赤いやつだけは絶対守る」と認識する。

## アンチパターン

逆に、CLAUDE.md でやってはいけないことも書いておく。

### NG1: 「丁寧に」「適切に」を使う

「丁寧にコメントを書いてください」「適切なエラーハンドリングを」——これらは**判断基準を放棄している言葉**だ。Claude（や新人エンジニア）は何が「丁寧」か分からない。

「コメントは WHY だけ書く。WHAT は書かない」のように、具体的なルールに置き換える。

### NG2: 矛盾するルールを残す

CLAUDE.mdが大きくなると、過去に書いたルールと最近のルールが矛盾し始める。

```markdown
（昔書いた）すべての関数にdocstringを書く
（最近書いた）コメントは WHY だけ
```

これは破壊的に困る。週次レビューのタイミングで矛盾を整理する習慣をつける。

### NG3: 一度書いて放置する

CLAUDE.mdは生き物だ。プロジェクトの実態が変われば、CLAUDE.mdも変わる必要がある。

私は週次レビュー時に必ずCLAUDE.mdを開き、「最近の運用と齟齬がないか」確認する。最低でも月1回はメンテナンスする。

## まとめ

CLAUDE.md は、Claude Codeを使い続ける上で**最も投資対効果の高いファイル**だ。

- 最初は5-30行のミニマムで十分
- WHY を書く、HOW は書かない
- 「迷ったら」を明示する
- 重要度をレベル分けする
- 月1回はメンテナンスする

次章では、CLAUDE.md の上に乗せる「**情報フロー**」の設計を扱う。フォルダ構成、命名規則、そして情報が**流れる**仕組みをどう作るか。「1人総合商社」が回り続けるための土台がここに集まる。
