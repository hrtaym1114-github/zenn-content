# 命名規則・フォルダ設計・情報フロー

## 「保存したのに見つからない」をなくす

Claude Codeを使い始めて、こんな経験はないだろうか。

「先週Claudeに書かせた要件定義書、どこに保存したっけ」
「2週間前に整理したリサーチメモが消えた」
「`output/` `outputs/` `out/` のどれが正解だ」

これは個人の整理能力の問題ではない。**フォルダ設計と情報フローが定まっていない**から起きる構造的な問題だ。

私は2年前、Obsidianを始めたとき、「フォルダはあとで考えればいい」と適当に始めた。半年後、約1,500ファイルのうち、半数は二度と開かなくなった。検索すらできない状態だった。

そこで私は、**人間の脳の情報処理を模倣する**フォルダ設計に切り替えた。これが「1人総合商社」の土台となる情報アーキテクチャだ。

## 設計思想: 「人間の脳のアーキテクチャ」

人間の脳には、ざっくり次の流れがある。

```
感覚入力 → 短期記憶 → 長期記憶 → 想起
```

これをVaultに当てはめると、こうなる。

```
00_Memo/      = 感覚入力（クイックキャプチャ）
01_Inbox/     = 短期記憶（整理待ち）
02_Daily/     = エピソード記憶（日付ベース）
03_Input/     = 短期記憶（今週〜今月の資料）
04_Memory/    = 長期記憶（カテゴリ分類）
05_Output/    = 行動・出力（プロジェクト・エリア）
99_Archive/   = 凍結記憶（過去年）
```

これに「ツール置き場」と「プロンプト置き場」が加わる。

```
06_Templates/ = テンプレート
07_System/    = ダッシュボード・スクリプト・設定
08_prompts/   = カテゴリ別プロンプト集
```

数字プレフィックスを付けているのは、**Finderやエディタのファイラーで上から自然な順序で並ぶ**ようにするためだ。`00_Memo` から `99_Archive` まで、情報の流れと番号の流れが一致している。

## なぜ「フラットで整理」では失敗するか

最初は「フォルダなんていらない、タグでいい」「Markdownファイルをフラットに置いて全文検索すればいい」と考える人も多い。私もそうだった。

ところが、これは**3つの理由**で破綻する。

### 理由1: AIにも文脈が必要

Claude Codeに「このプロジェクトのリサーチを進めて」と頼んだとき、AIはどこに保存していいか分からない。フラット構造だと、毎回「どこに置くべきか」を質問してくる。

フォルダが**意味のある階層**になっていると、Claudeは自分で判断できる。「これは今週使う一次資料だから `03_Input/Research/` だな」と。

### 理由2: 「迷ったら」の答えが必要

ファイルを保存するとき、必ず「どこに置くべきか迷う」瞬間が来る。フラット構造には**逃げ場がない**。フォルダ構造があれば「迷ったら01_Inbox/」というルールで一時退避できる。

これが情報フロー設計の本質だ。**判断を後送りできる仕組み**を最初から作る。

### 理由3: 「捨てる」が機能しない

フラット構造だと、ファイルは「ある」か「ない」しかない。間にグラデーションがない。

階層構造だと「最近使うか/長期保管か/凍結か」が明示的になる。`99_Archive/` に移動するだけで「使わない」がメタデータ的に表現される。削除しなくていい。

## PARA法 × Zettelkasten の統合

このフォルダ設計の元ネタは、2つの古典的な情報管理メソッドの統合だ。

### PARA法（Tiago Forte）

PARA は4つのフォルダで生活情報を分類するメソッド。

- **P**rojects: 期限とゴールがある活動
- **A**reas: 期限なしの継続活動
- **R**esources: 興味あるトピック
- **A**rchives: 終わったもの

私の `05_Output/` 配下は完全にこれだ。

```
05_Output/
├── Projects/
│   ├── @Active/      # 動いているもの
│   ├── @Planning/    # 計画中
│   └── @Completed/   # 終わったもの
└── Areas/
    └── [エリア名]/
        ├── @TODO/    # これから着手
        ├── @Doing/   # 作業中
        └── @Completed/  # 完了
```

`@` プレフィックスは「フェーズ」を示す。Finderで `Areas/` を開くと、`@TODO` → `@Doing` → `@Completed` の順で並ぶ。**Kanbanボードのカラムをフォルダで表現**している。

### Zettelkasten（Niklas Luhmann）

PARA は「活動の分類」だが、知識そのものの整理には弱い。そこでZettelkasten的な発想を加える。

Zettelkasten は「**ノードとリンクで知識ネットワークを作る**」メソッド。私の `04_Memory/` がこれを担う。

```
04_Memory/
├── _Master-Index.md       # マスターインデックス
├── AI/
│   ├── _AI-MOC.md         # AIカテゴリの目次
│   ├── Tools/
│   ├── Models/
│   └── Concepts/
├── Education/
├── Business/
├── Technical/
└── Personal/
```

各カテゴリの先頭に `_カテゴリ-MOC.md`（Map of Contents、目次）を置く。`_` プレフィックスでファイラー先頭に固定される。MOCはそのカテゴリの「玄関」だ。

知識ノート同士は `[[双方向リンク]]` で結ぶ。「Cursor」のノートから「VS Code」「Claude Code」「AI支援エディタ全般」へとリンクが張られていく。フォルダはルーズに置くだけで、リンクが本当の地図になる。

## 命名規則の哲学

ファイル名にも哲学がある。私のルールは次の通り。

### 1. 日本語OK、スペース禁止

```
✅ Cursor-キーボードショートカット.md
❌ Cursor キーボードショートカット.md（スペース）
❌ cursor_keyboard_shortcuts.md（英語化はやりすぎ）
```

日本語ファイル名はURLエンコード問題を起こさないか心配する人がいるが、Obsidian + Git + Claude Code の組み合わせでは問題なく動く。

### 2. 単語区切りはハイフン

スペースもアンダースコアも使わない。ハイフン一択。

**理由**: スペースはターミナルで escape が必要、アンダースコアはMarkdownの斜体記法と衝突する。ハイフンは何にも干渉しない。

### 3. 日付プレフィックスは `YYYY-MM-DD`

```
✅ 2026-05-16-週次レビュー.md
✅ YYYYMMDD_テーマ.md（場所によってはこれ）
❌ 5/16/2026-週次レビュー.md（スラッシュはファイル名に使えない）
❌ 16-May-2026.md（ソートが効かない）
```

`YYYY-MM-DD` だと**ファイラーで自動的に時系列ソート**される。これが致命的に便利。

### 4. フォルダ名は英語

```
✅ 04_Memory/AI/Tools/Cursor/
❌ 04_Memory/AI/ツール/Cursor/
```

フォルダ名は**コマンドラインで頻繁にタブ補完される**ので、英語のほうが速い。日本語入力切替のコストが累積する。

ファイル名は内容を表現するので日本語OK、フォルダ名はパス操作なので英語、という棲み分けだ。

### 5. MOC（目次ファイル）は `_` プレフィックス

```
04_Memory/AI/
├── _AI-MOC.md           ← 先頭に固定
├── Cursor.md
├── Claude-Code.md
└── ...
```

`_` から始まるファイルはASCIIソートで最上位に来る。「玄関にあるノート」を目立たせる古典的なテクニックだ。

## 情報フロー: 6ステップの判断フロー

ここまで設計しても、保存時に「どこに置くか」迷う瞬間は来る。その時の**判断フロー**を CLAUDE.md に書き込んでおく。

```markdown
## ファイル配置の判断フロー

1. とりあえずメモ → 00_Memo/
2. 今週使う？ → 03_Input/
3. 3ヶ月後も参照する？ → 04_Memory/
4. 期限ありプロジェクト？ → 05_Output/Projects/
5. 期限なし継続活動？ → 05_Output/Areas/
6. 迷ったら → 01_Inbox/（週次レビューで処理）
```

このフローには3つの設計意図がある。

### 意図1: 上から順に判断できる

「とりあえずメモか？」「今週使うか？」と上から順に Yes/No で判断していけば、必ず1つの答えに行きつく。**意思決定の認知負荷をゼロにする**設計だ。

### 意図2: 「迷ったら」のエスケープがある

判断不能のときは `01_Inbox/` に放り込めばいい。Inboxは**週次レビューで処理する前提**なので、判断を1週間先送りできる。

### 意図3: AIも同じフローで判断できる

このフローをCLAUDE.mdに書いておくと、ClaudeはVaultでファイルを作成するとき**自動的にこのフローに従う**。「どこに保存しますか？」と聞かれることが激減する。

## 情報は「流れる」ように設計する

このフォルダ設計の核心は「**情報は流れるべき**」という思想だ。

```
00_Memo/      → クイックキャプチャ（数秒〜数分）
   ↓ /memo-to-inbox コマンドで整理
01_Inbox/     → 整理済み下書き（1週間以内）
   ↓ 適切なフォルダへ振り分け
03_Input/     → 短期参照（今月以内）
   ↓ 重要なら昇格
04_Memory/    → 長期知識（3ヶ月以上参照）
   ↓ 使わなくなったら
99_Archive/   → 凍結（過去年単位）
```

ファイルは1箇所に永遠に居座らない。**水のように下流へ流れる**。これにより、Vault全体が新陳代謝する。

「整理が苦手な人」の多くは、この「流す」感覚を持たない。すべてを「**置く**」と思っている。だから永遠に整理しなければならない。

私は逆だ。**最初の30秒は `00_Memo/` に放り込むだけ**。そこから流すのは Claude Code の `/memo-to-inbox` コマンドが自動でやる。私の脳は「キャプチャ」と「最終判断」だけに使う。

## アンチパターン

ここまでで紹介した設計の**逆**をやると、Vaultが破綻する。

### NG1: フォルダ階層が深すぎる

```
❌ 04_Memory/AI/Models/Anthropic/2026/Claude/Versions/4.7/Documentation/
```

3階層以内にしないと、移動コストが高すぎて使わなくなる。タグやリンクで補完するのが正解。

### NG2: フォルダ名が日本語

```
❌ 04_メモリ/人工知能/ツール/
```

タブ補完が遅くなる。CLI操作で詰む。フォルダは英語、ファイル名は自由。

### NG3: 命名規則を「あとで決める」

「いったん `temp_新しいフォルダ_v2_最終.md` で保存しておこう」これが**一番の地雷**。半年後、`v2_最終` が何の最終だったか思い出せない。

CLAUDE.md に命名規則を最初に書き、Claude にも従わせる。

### NG4: フォルダ移動を恐れる

`03_Input/` から `04_Memory/` への移動は、リンク切れを起こすのでは？という不安がある。

Obsidian は**ファイル移動時にリンクを自動更新**する。Git追跡もリネームとして検出される。フォルダ移動は自由にやって良い。

## まとめ

情報アーキテクチャは「Vault全体の骨格」だ。一度決めると変えづらいので、最初に時間をかけて設計する。

設計原則:
1. **人間の脳のアーキテクチャを模倣する** — 感覚入力から長期記憶への流れ
2. **PARA × Zettelkasten** — 活動の分類と知識ネットワークの両立
3. **数字プレフィックス** — ファイラーで自然なソート
4. **「迷ったら」のエスケープを必ず作る** — `01_Inbox/`
5. **情報は流れる** — 1箇所に留まらせない

このフォルダ構造とCLAUDE.mdが揃うと、Claude Code は**プロジェクトの地理を把握した状態で動き始める**。次はこの上に乗せる「**カスタムコマンド**」だ。日常業務をワンコマンドで回す仕組みを、次章で設計していく。
