# カスタムコマンド（Skills）の設計

## 「毎日やること」を、ワンコマンドにする

朝、Vaultを開く。

```
/daily
```

これだけ打つと、Claude Code は次を**自動で**実行する。

1. 今日の日付を確認（曜日・週番号も）
2. デイリーノートを所定のテンプレートで作成
3. 前日のタスクから「未完了」を引き継ぎ
4. 今日のToTOP 3 Priorities を空欄で配置
5. Daily Kanban の「今日やる」カラムをリセット
6. 朝の振り返りプロンプトを表示

これまで毎朝15-20分かかっていた「朝の準備」が、コマンド入力後10秒で完了する。私が見て確認するだけだ。

これがClaude Code のカスタムコマンド——別名 **Skill** ——の威力だ。本章ではこの仕組みの設計思想を扱う。

## カスタムコマンドとは何か

Claude Code には、ユーザーが自分で定義できる「**Skill**」という仕組みがある。`.claude/commands/` または `.claude/skills/` というフォルダにMarkdownファイルを置くだけだ。

最小構成は次の通り。

```markdown
---
name: my-command
description: コマンドの説明
---

# my-command

このコマンドが起動されたら、次を実行する:

1. ステップ1
2. ステップ2
3. ステップ3
```

これを `.claude/commands/my-command.md` として保存する。すると Claude Code 内で次のように使える。

```
/my-command
```

Claude は Markdown 本文をプロンプトとして読み込み、その指示に従って動く。**毎回同じ指示を打ち直す必要がない**。

## Skillが解決する3つの問題

Skill を使う前と後では、Claude Code の使い心地が大きく変わる。それは Skill が次の3つの構造的問題を解決するからだ。

### 問題1: 「毎回同じ指示」の摩擦

「今日のデイリーノートを作って」「これに前日のタスクを引き継いで」「Kanbanも更新して」——これらを毎朝打つのは精神的にしんどい。

Skill にしておけば、ワンコマンドで全部終わる。**摩擦が消える**。摩擦が消えると、習慣が回る。

### 問題2: 暗黙知の言語化

「いつもの手順」「いつものスタイル」は、頭の中にあるうちは脆い。次のような瞬間にすぐ崩れる。

- 数週間サボると忘れる
- AIに頼むたびに微妙にブレる
- 他人に説明できない

Skill ファイルとして書き出すと、暗黙知が**外部化**される。あなたの頭から独立する。

### 問題3: AIの判断ばらつき

Claude Code は優秀だが、毎回少しずつ違う動き方をする。「今日は箇条書きで」「今日は表で」「今日は冗長に」——同じ指示でも応答が揺れる。

Skill に「出力フォーマット」を書き込むと、揺れが激減する。**期待値の一致**が起きる。

## 良いSkillの構造

3ヶ月で68個のSkill を書いた経験から、良いSkill には**5つの構造要素**があると分かった。

### 要素1: 明確な「起動条件」

そのコマンドはいつ叩かれるべきか？を最初に書く。

```markdown
## いつ使うか
- 朝、Vault を開いたとき
- 1日1回まで（複数回叩かれた場合は警告）
```

これがあると、Claude はユーザーが間違ったタイミングで叩いてもリカバーできる。

### 要素2: 実行ステップ

何をするかを番号付きで書く。曖昧な指示は避ける。

```markdown
## 実行ステップ

1. 今日の日付を `date '+%Y-%m-%d (%A)'` で確認する
2. 02_Daily/[年]/[年-月]/[年-月-日]/ フォルダが無ければ作成
3. テンプレート 06_Templates/Daily-Template.md をコピー
4. 前日のデイリーノートから未完了タスク（- [ ] で始まる行）を抽出
5. テンプレートに前日タスクを埋め込む
6. ユーザーに「TOP 3 Priorities を教えて」と質問する
```

「いい感じに作って」ではなく、**具体的なコマンド**まで書く。これがブレを消す。

### 要素3: 出力フォーマット

何を出力するかをサンプル付きで示す。

```markdown
## 出力フォーマット

ユーザーには次の形式で報告する:

✅ デイリーノート作成完了
📋 引き継ぎタスク: N件
🎯 TOP 3 Priorities: [未設定なら質問]
```

Claudeは出力例があると、それに合わせる。**書式の安定**が得られる。

### 要素4: 関連ファイルへの参照

Skill 内で読み込むべきファイルを明示する。

```markdown
## 関連ファイル
- 06_Templates/Daily-Template.md — 使うテンプレート
- 07_System/Dashboards/Daily-Kanban.md — 更新対象
- 02_Daily/[前日]/ — 前日のデイリーノート
```

Claude はこれを読んで、必要なファイルだけを開く。**不要な探索を抑制**できる。

### 要素5: アンチパターンの明示

「これだけはやらないでね」を最後に書く。

```markdown
## やってはいけないこと
- 既存のデイリーノートを上書きしない（あれば中断して確認）
- 前日タスクを「完了」マークに変えない（引き継ぎはそのまま）
- ユーザーに3回以上質問しない（短い対話で済ませる）
```

これがあると、暴走が止まる。

## 5つの設計原則

Skill を書き続けると、繰り返し効く原則が見えてくる。

### 原則1: 「毎日やる」ものから書く

最初に書くべきSkillは、**毎日叩くもの**だ。

私の場合は `/daily` だった。月に一度しか使わないSkillは、いざという時に使い方を忘れる。毎日使うSkillだけが、生活に馴染む。

頻度の低いSkillは、必要になってから書けばいい。「未来の自分が使うかもしれない」で書いたSkillは、99%死蔵される。

### 原則2: 1コマンド1責任

Skill には「**何をするか**」を1つだけ書く。複数の責任を持たせると、コマンドの意味が不明確になる。

```
❌ /daily-and-weekly-review-and-monthly-summary
✅ /daily
✅ /weekly-review
✅ /monthly-summary
```

複数の処理が必要なら、別Skillを連鎖させる。

### 原則3: 副作用を最小化する

Skillは「ファイル作成」「Kanban更新」など、**副作用**を伴う。副作用は予測可能にする。

- 既存ファイルを上書きしない（書く前に確認）
- 削除はしない（移動かアーカイブ）
- 同じコマンドを2回叩いても同じ結果になる（冪等性）

予測可能なSkillだけが、安心して任せられる。

### 原則4: 出力で動かす

Skillは「**ユーザーに何かをさせる**」のではなく、「**ユーザーが見るだけで進む**」のが理想。

```
❌ 「次に何をしますか？」と聞き続ける
✅ 必要な情報をすべて出力して、ユーザーは確認するだけ
```

「対話型」のSkillは便利に見えて、結局ユーザーの時間を奪う。「報告型」のSkillの方が長期的には使われる。

### 原則5: フィードバックループを内蔵する

Skillの最後に「**次に何を確認/実行すべきか**」を必ず書く。

```markdown
## このコマンドが終わったら
- 朝のTOP 3 Prioritiesを記入する
- 必要なら /daily-update で進捗同期
- 夕方には /daily-evening で振り返り
```

これがあると、Skill が**ワークフロー全体の中で位置付け**を持つ。単発で終わらない。

## 私の主要Skill 一覧（一部）

参考までに、私が日常的に使うSkill の一部を紹介する。

### Vault管理系

| コマンド | 説明 | 使用頻度 |
|---------|------|---------|
| `/daily` | デイリーノート作成 + Kanban更新 | 毎日朝 |
| `/daily-update` | 日中のタスク進捗同期 | 1日2-3回 |
| `/daily-evening` | 夕方の振り返り + 完了タスク更新 | 毎日夜 |
| `/memo-to-inbox` | メモをInbox形式に処理 | 不定期 |
| `/weekly-review` | 週次レビュー | 毎週金曜 |
| `/inbox-review` | Inbox整理 | 週1-2回 |

### コンテンツ制作系

| コマンド | 説明 |
|---------|------|
| `/blog00-planning` | 執筆計画生成（週次） |
| `/blog01-generate-article [キー]` | 記事生成 |
| `/x:x00-planning` | X.com投稿計画 |
| `/x:x01-generate-post [キー]` | 投稿文生成 |
| `/note:weekly-pick` | 週刊AI検証ピックアップ生成 |

### 組織運営系

| コマンド | 説明 |
|---------|------|
| `/coo-briefing` | 朝のブリーフィング |
| `/rd-status` | プロジェクトレビュー |
| `/email-check` | 返信が必要なメール特定 |

これらは「ワークフロー上の動詞」だ。「何をするか」が一語で伝わる。

## アンチパターン

Skill 設計でやってはいけないことを3つ挙げる。

### NG1: Skillに「意思決定」を持たせる

```
❌ /should-i-publish-this — 公開すべきか判断する
```

意思決定は人間の仕事だ。Skillは「**情報を整理して提示する**」までで止めるべき。「判断する」をSkillにすると、Claude が空回りする。

### NG2: Skillが他のSkillを「自動で」呼ぶ

```
❌ /daily が内部で勝手に /memo-to-inbox を呼び出す
```

Skillの連鎖は、ユーザーが明示的に叩く形に留める。自動連鎖は予測不能を生む。

### NG3: Skill名が抽象的

```
❌ /process
❌ /handle
❌ /run
```

何をするコマンドか分からない名前は、書いた本人でも忘れる。**動詞 + 目的語**で具体的に。

```
✅ /daily
✅ /memo-to-inbox
✅ /weekly-review
```

## まとめ

Skill は「**繰り返しを言語化する装置**」だ。

設計原則:
1. **毎日やるものから書く** — 死蔵Skillを作らない
2. **1コマンド1責任** — 名前が動詞 + 目的語で表せる
3. **副作用を最小化** — 上書きしない、冪等性
4. **報告型で動かす** — 対話型より長持ち
5. **次の動きを示す** — ワークフロー上に位置付ける

ここまでで Part 1（設計編）が完了した。CLAUDE.md、フォルダ構造、Skill の3つが揃ったとき、Claude Code は**プロジェクトの地理を把握し、毎日の動きを言語化された状態**で動き始める。

次の Part 2 では、ここに「**エージェント組織**」を被せていく。複数のAI人格を「部門」「役職」として設計し、人間の意思決定負荷を最小化する仕組み——「1人総合商社」の核心部分だ。
