# エージェント組織の設計パターン

## 仕組みは完成した。それでも、回らなかった。

Ch.03までで、Claude Code の中に「命令を書く場所」と「機能を呼び出す仕組み」は揃った。CLAUDE.md でプロジェクトの脳を作り、フォルダ構造で情報の流れを設計し、Skill（カスタムコマンド）で毎日の動作を言語化した。

これだけで十分動くはずだった。

ところが、実運用はそこで終わらなかった。

私は2026年2月、5チャネルへの半自動投稿システムを完成させた。X.com、リベシティ、ブログ、note、Borders Daily。それぞれのチャネル向けに投稿文を生成するコマンドを書き、Vault内のフォルダ構造で@TODO/@Doing/@Completedを管理し、適切なフォーマットに振り分ける仕組みを整えた。

仕組みは完璧だった。コマンドを叩けば投稿文が出てきた。

**投稿実績は0件だった。**

ドラフトは溜まる。@TODO/に並ぶ。「もう少し直したい」「タイミングが悪い気がする」——その心理的障壁が、思った以上に大きかった。3週間で1本も公開できなかった。

このとき、はっきり見えた。**問題は機能不足ではなく、組織不在だった**。Skill はあっても、「いつ叩くか」「誰が判断するか」「進捗を誰が見るか」が決まっていなかった。1人の私が全部抱えていた。だからボトルネックも私だった。

運用前と運用後、3ヶ月で何が変わったか。

| 指標 | 運用前（2025年12月） | 運用後3ヶ月（2026年4月） |
|------|---------------------|------------------------|
| Skill 数（カスタムコマンド） | 5 | **68** |
| エージェント定義数 | 0 | **29**（後に25へ収束） |
| 同時運用チャネル | 1 | **5** |
| 月間コンテンツ本数 | 4 | **40以上** |
| 副業作業時間 | 1日2-3時間 | **平日30分-1時間、休日2-3時間** |

増えたのは「人数」ではない。増えたのは、**役割・責任・連携の設計**だ。AI人格を「便利機能の寄せ集め」として並べるのではなく、部門と役職を持った「組織」として配置した。これが「1人総合商社」の核心である。

本章では、その組織の設計パターンを公開する。4部門＋COOの構造、レジストリ駆動型アーキテクチャ、State File、File Ownership Rule、コスト制御——どれも実運用3ヶ月で淘汰されて残った設計だ。仕組みを「作る」から「回す」へ。その分岐点が本章だ。

> **AI活用が止まる原因は、機能不足より「組織不在」である。**

## 1人総合商社の最小組織図

組織図を先に見せる。

```
CEO（ayumu）= 最終意思決定者
│
COO Agent（部門横断オーケストレーター）
│
├── 📢 Content Marketing Div（コンテンツ部）
├── 🔬 R&D Division（研究開発部）
├── 👤 Career & Comms Div（人事・通信部）
└── ⚙️ Tech Infrastructure Div（情報基盤部）
```

CEO は私（ayumu）。最終意思決定者で、これだけは AI に渡せない。COO は部門横断のオーケストレーター。朝のブリーフィングで全部門の状態を読み、その日の動きを提案する。私はその提案を見て「Go」「待って」「方向修正」を返すだけだ。

4部門の責務はこう分けた。

| 部門 | 主な責務 | 主要コマンド例 |
|------|---------|--------------|
| 📢 Content Marketing | コンテンツ企画・執筆・公開 | `/team-content-sprint`, `/x:x01-generate-post`, `/note:weekly-pick` |
| 🔬 R&D | プロジェクト管理・新規開発 | `/rd-status`, `/rd-new-project` |
| 👤 Career & Comms | メール・スキル・対外コミュニケーション | `/email-check`, `/career-skills-update` |
| ⚙️ Tech Infrastructure | Vault健全性・GHA・分析連携 | `/infra-health`, `/infra-gha-status` |

この分け方には1つだけ原則がある。**「人格」ではなく「役職」として分ける**ことだ。

「コンテンツ部の中の AI ライター」と書くと、その AI には個性や口調が必要に思える。だが、副業を回すうえで本当に必要なのは「コンテンツ生成という役割を担う場所」だ。場所が決まれば、そこに何度でも別の AI を当てはめられる。役職は組織の骨格で、人格は中身だ。骨格を先に設計すれば、中身は後から差し替えられる。

製造業のチーム運営でこれを毎日やってきた。14人のチームで「設計担当」「テスト担当」「文書担当」「品質保証担当」と役割を切り、人事異動で中身が入れ替わっても役割は残った。AI 組織も同じだ。役職を先に固定すれば、モデルが変わっても、プロンプトを書き直しても、組織の構造は崩れない。

> **AI人格は増やすのではなく、責任の置き場として配置する。**

なお、本書執筆時点（2026年5月）では、上記4部門に加えて **Advisory Board Div**（読者理解・批判検証・市場分析のための顧問団）が稼働している。これは後から「組織を強くする外部知性」として追加した部門で、Part 4 Ch.10 で扱う。本章では「最小構成」として4部門を扱う。

## レジストリ駆動型アーキテクチャ

組織図を書けば動くか、と言うとそうではない。**組織は「辿れる構造」になって初めて回る**。

最初、私は各部門のエージェント定義ファイルを `.claude/agents/` に並べていた。content-strategist.md、rd-lead.md、career-lead.md……。COOがブリーフィングを出すとき、これら全部を読みに行く。最初は5ファイルだったから問題なかった。

エージェントが20を超えたあたりで、ブリーフィングが壊れ始めた。COOがどのファイルを読めば良いのか分からなくなり、毎回違うエージェントを呼ぼうとする。読み込むファイルが多すぎてコストも跳ねた。

解決策は「**レジストリ**」だった。

```
.claude/agents/
├── coo.md                    # COO（全部門オーケストレーター）
├── org-registry.md           # マスター組織レジストリ ← COO が読む
│
├── content-strategist.md     # Content部門長
├── channel-registry.md       # チャネル定義 ← content-strategist が読む
├── channels/                 # チャネル別エージェント
│
├── rd-lead.md                # R&D部門長
├── project-registry.md       # プロジェクト定義 ← rd-lead が読む
│
├── career-lead.md            # Career部門長
├── comms-registry.md         # コミュニケーション定義 ← career-lead が読む
│
├── infra-lead.md             # Infra部門長
└── infra-registry.md         # インフラ定義 ← infra-lead が読む
```

`org-registry.md` だけが「マスター」で、ここに全部門の入り口が書いてある。COO はこれだけ読む。各部門の詳細は、部門長がそれぞれの registry を読みに行く。content-strategist は `channel-registry.md` を読み、そこから個別のチャネルエージェントを呼び出す。

これは製造業の BOM（部品表）に似ている。最終製品の構成を一覧するために、サブアセンブリを階層化する。レベル0が完成品、レベル1がサブアセンブリ、レベル2が個別部品。BOM さえ正しく書かれていれば、誰が見ても全体構造が辿れる。

レジストリ駆動の効き目は3つある。

**1. 一覧性**: マスターレジストリだけ見れば組織全体が把握できる。新しい部門を追加するときも、まずレジストリに登録するから「どこに置いたか分からない」が起きない。

**2. 探索性**: COOやエージェントが「次にどのファイルを読むべきか」を機械的に判断できる。曖昧な探索が消えるから、トークン消費が安定する。

**3. 保守性**: 部門を増減するとき、レジストリだけ書き換えれば良い。エージェント定義ファイル本体は触らなくて済む。

これは小さな違いに見えるが、エージェントが25を超える規模になると効いてくる。**「人を探す」のではなく「責任の所在を引く」設計**。これが組織を回す土台になる。

実際の `org-registry.md` の構造は次のような形だ。

```markdown
# Organization Registry

## 📢 Content Marketing Div
- **Lead**: content-strategist
- **Registry**: channel-registry.md
- **State File**: 07_System/State/content-state.md

## 🔬 R&D Division
- **Lead**: rd-lead
- **Registry**: project-registry.md
- **State File**: 07_System/State/rd-state.md

## 👤 Career & Comms Div
- **Lead**: career-lead
- **Registry**: comms-registry.md
- **State File**: 07_System/State/career-state.md

## ⚙️ Tech Infrastructure Div
- **Lead**: infra-lead
- **Registry**: infra-registry.md
- **State File**: 07_System/State/infra-state.md
```

COO はこれを読んで、「今日は Content 部門の state を見て、その後 R&D に進む」と機械的に動ける。指示は最小、構造で動く。

> **組織は「置く」だけでは機能しない。辿れる構造にして初めて回る。**

## COOが毎回読むもの──State Fileパターン

レジストリで構造を作っても、もう1つ問題が残った。**毎回ゼロから説明し直す**問題だ。

朝、COO に「ブリーフィングを出して」と言う。COO は「今、何の案件がアクティブですか？」と聞き返す。私が「先週やってた Zenn Book 執筆、まだ続いてる」と答える。COO が「優先度はどれくらいですか？」と聞く。私が「最優先」と答える。COO が「他に進行中の案件は？」と聞く。私が……

これでは秘書ではなく、伝言係だ。

解決策は「**State File**」だった。

```
07_System/State/
├── content-state.md          # Content部門の現状
├── rd-state.md               # R&D部門の現状
├── career-state.md           # Career部門の現状
└── infra-state.md            # Infra部門の現状
```

各部門の現在の状態をファイルに書き出しておく。COO はブリーフィング時にこれを読み込む。私が説明する必要はない。

`content-state.md` の構造はこんな形だ。

```markdown
# Content Marketing State

最終更新: 2026-05-18

## 進行中の案件
- Zenn Book「1人総合商社」執筆（最優先・Ch.04執筆中）
- note週刊AI検証ピックアップ（毎週金曜公開）

## 今週の重点
- Zenn Book Ch.04-06完成（Part 2完成で本書50%到達）

## 注意事項
- X.comはReduced運用（週2-3回告知のみ）
- noteフォロワー4週連続±0 — フォロー誘導CTAの再設計が必要
```

これがあると、COO のブリーフィングは「コンテンツ部門は Zenn Book Ch.04 が最優先で進行中、note は対策が必要です」と一発で出てくる。私が説明する手間はゼロだ。

State File は「**口頭引き継ぎできない AI 組織の朝会メモ**」だと考えている。人間の組織なら「先週の続きで」と言えば通じる。だが、AI には先週の記憶がない。毎回まっさらだ。だから「先週の続き」を毎回書き出しておく。

State File を書くのは誰か。**各部門長**だ。週次レビューや日次の `/coo-briefing` の最後に、部門長がその日の状態を書き戻す。私が直接書くこともある（重要な方針転換があるとき）。

ここで1つ重要な原則がある。**State File はエージェントの記憶置き場ではなく、組織の共通文脈の置き場**だ。エージェントが個別に覚えておくべき情報（例: ある記事の文脈、ある案件の細かい経緯）は別の場所に書く。State File は「組織として全員が知っておくべきこと」だけに絞る。

これを混ぜると State File が肥大化して、結局COOが読み切れなくなる。私が陥った最初の失敗がこれだった。「念のため書いておこう」と細かい情報を全部入れた結果、200行を超えるState Fileができあがり、COOがブリーフィングのたびに5秒固まるようになった。

絞った後、現在のState Fileは1部門あたり30-50行に収まっている。

> **優秀なエージェントより、引き継ぎ可能な状態管理のほうが再現性を生む。**

## AI同士をぶつけないための規律──File Ownership Rule

エージェントが25を超えたとき、別の問題が起きた。**ファイルの衝突**だ。

ある日、content-strategist が X.com 投稿ドラフトを `X-Twitter/@TODO/` に書いた。同じ時間、別のセッションで動いていた COO がブリーフィング結果として同じフォルダにメモを書いた。気づいたときには、ドラフトの一部が上書きされていた。

これは1人運営でも普通に起きる。複数のセッションを同時に走らせるし、`/team-content-sprint` のように並列で複数エージェントを動かすコマンドもある。「全員が全部触れる」設計は、自由ではなく事故の温床だ。

解決策は「**File Ownership Rule**」だった。各エージェントが書き込めるフォルダを宣言する。

| パス | 書込み許可 |
|------|-----------|
| `org-registry.md`, `07_System/State/`, `Org-Dashboard.md` | COO のみ |
| `channel-registry.md`, `02_Daily/`, `07_System/Dashboards/` | content-strategist のみ |
| `Libecity/@TODO/` | libecity-main のみ |
| `X-Twitter/@TODO/` | x-ai-lifestyle のみ |
| `Blog-Research/`, `Blog-Writing/@Doing/` | blog-ai-frontier のみ |
| `Projects/@Active/`, `@Planning/` | rd-lead のみ |
| `Email/`, `Personal/Career/` | career-lead のみ |
| `07_System/Reports/` | infra-lead のみ |
| `00_Memo/` | **絶対禁止**（ユーザーのみ） |

最後の `00_Memo/` だけは、どんなエージェントも触れない。ここはユーザーの「生の思考メモ」の場所で、AIに汚染されると思考が止まる。最も重要な聖域だ。

このルールを書いた効果は2つあった。

**1. 衝突がゼロになった**: 「誰が書くか」が決まっているから、同じファイルを別エージェントが書き換えることが構造的に起きない。

**2. デバッグが速くなった**: ファイルが壊れたとき、「これを書ける可能性があるのは誰か」が一覧で分かる。原因特定が秒で終わる。

導入のコツは、**ルールを最小化する**ことだ。最初、私は20個以上の所有権ルールを書いた。読みにくくて誰も守らなかった（私が）。圧縮して10個に絞ったら定着した。

「全員が全部触れる」と「全員が何も触れない」の中間が、エージェント組織の健全な状態だ。

> **AI組織の事故は、能力不足ではなく所有権不明から起きる。**

## コスト制御──COOはsonnet、spawnはsprintで

組織化には別のコストもついてくる。**推論コスト**だ。

エージェントが25個あって、それぞれが Claude を呼ぶ。COOがブリーフィングのたびに全部門のレジストリと state を読む。1日10回ブリーフィングを叩けば、それだけでまとまったコストになる。

私は最初、全てのエージェントを Opus で動かしていた。「重要な判断は高性能モデルで」と思ったからだ。1週間で API 利用料が想定の3倍になった。

そこで作ったのが「**判断の重さ × 呼出頻度**」の2軸マトリクスだ。

| | 呼出頻度: 低 | 呼出頻度: 高 |
|---|---|---|
| **判断重要度: 高** | Opus（重要かつ稀） | **Opus → Sonnet** に降格検討 |
| **判断重要度: 低** | Sonnet で十分 | **Haiku** で十分 |

COO はブリーフィングで1日10回呼ばれる。判断重要度は高い。だが「全部門の状態を読む」というルーチン作業がメインだ。**Opus である必要はない**。Sonnet で十分動く。

逆に、Advisory Board の audience-analyst（読者理解の専門家）は週に1回しか呼ばれないが、判断重要度は最高だ。**ここは Opus** にする。

`paperbanana-visualizer`（画像生成）は外部 API（Gemini）を叩く特殊なエージェントなので、モデル選択ではなく API コール回数で制御する。

もう1つの制御が「**spawnはsprintコマンドのみ**」というルールだ。

COO がブリーフィングを出すとき、デフォルトでは他のエージェントを spawn しない。「コンテンツ部門で X.com 投稿を出した方がいいですね」とコマンドを提案するだけだ。私が `/team-content-sprint` を叩いたときだけ、3チャネル並列でエージェントが spawn される。

これで暴走を防げる。COO が「念のため全部門のエージェントを呼んでおこう」と勝手に並列実行するのを構造的に止めている。

> **AI組織は、人件費ではなく推論コストで破綻する。だから役職ごとにモデルを分ける。**

## なぜ29個まで増え、25個に落ち着いたのか

最初は3個から始まった。

- writer（コンテンツ書く人）
- reviewer（読む人）
- planner（計画を立てる人）

これだけで動くと思った。実際、1ヶ月は動いた。だが、複数チャネルの運用が始まると役割が曖昧になった。「writer は X.com も書くのか、ブログも書くのか」「planner は週次計画なのか日次計画なのか」。指示するたびに「今日の writer はブログ用です」と前置きが必要だった。

そこで「**役職を専門化**」した。

- x-ai-lifestyle（X.com専門ライター）
- libecity-main（リベシティ専門ライター）
- blog-ai-frontier（ブログ専門ライター）

これでチャネル別の特化ができた。だがコンテンツ系だけで6個に増え、「これ全部 content-strategist が見るのか」になった。それで部門長を作った。content-strategist。

部門長を作ったら、他の領域でも「部門化」のメリットが見えた。R&D、Career & Comms、Tech Infrastructure。それぞれに部門長を置いた。

エージェントは雪だるま式に増えた。最大で29個になった。Content 部門だけで10個近く、Advisory Board に6個、PaperBanana（画像生成パイプライン）に6個、その他で7-8個。

**29個書いて、4個減らした**。

廃止した代表例が `x-life-design` だ。X.com の「仕組み化×内省」アカウントを運用するエージェントだった。アルゴリズム変更で当該アカウントの運用を停止したため、2026-03-03 にアーカイブした。

ただし、エージェント定義ファイル自体は削除しなかった。description に「**[ARCHIVED 2026-03-03] X.com 仕組み化×内省アカウント — チャネル完全停止済み。このエージェントは使用しないこと**」と明記して残した。

なぜ消さないか。**試行錯誤の証跡**だからだ。「過去にこういう役職を作って、こういう理由で廃止した」という記録は、次に同じ過ちを繰り返さないための地図になる。半年後に「X.comのサブアカウントを作りたい」と思ったとき、この archived エージェントを読めば「過去にこう設計してこう失敗した」が一発で分かる。

統合した例もある。最初は「reviewer」「fact-checker」「style-guard」と3つに分けていた批評系エージェントを、最終的に「devils-advocate」（批判検証エージェント）1つに統合した。3個に分けたとき、誰に何を頼めば良いか分からなくなった。1個に統合したら、「とりあえず devils-advocate にぶつける」で済むようになった。

3個に分けたほうが「正しい設計」に見える。だが、運用してみると「**1個でいい**」ことが分かる。これが机上の組織設計と実運用組織の違いだ。

29個から25個への収束は、こうした廃止と統合の積み重ねだ。「数を減らした」のではない。「責務に合うように再編した」結果として、たまたま25個になった。

来月にはまた変わっているかもしれない。それでいい。組織は固定するものではなく、動かしながら再編するものだ。

> **正しいエージェント数は先に決まらない。機能する責務分解の結果として決まる。**

## 本業×AIで組織は強くなる

ここまでの設計を読んで、「**製造業の組織設計に似ている**」と感じた人がいるかもしれない。

実際、似ている。意図的に似せた。

私は製造業のエンジニアで、14人のチームを管理している。設計、テスト、文書、品質保証——それぞれに担当を置き、責任を明確にし、文書で残し、変更管理を回す。日々やっていることだ。

AI 組織を作るとき、これをそのまま持ち込んだ。

| 製造業の業務原理 | AI組織への転用 |
|----------------|--------------|
| 役割分担（設計/テスト/文書） | 4部門による責務分解 |
| BOM（部品表） | レジストリ駆動アーキテクチャ |
| 朝会・引き継ぎメモ | State File パターン |
| 工程責任の明確化 | File Ownership Rule |
| 工数管理 | コスト制御（モデル選択 × 呼出頻度） |
| 失敗事例の文書化（ナレッジマネジメント） | アーカイブされたエージェント定義 |

AI 活用の領域には「**本業×AI**」を独自ポジションにする発想がある。AI の知識量で競うのではなく、自分の本業の構造を AI 活用に持ち込めば、誰も真似できないポジションが取れるという考え方だ。

私の場合、それが製造業の組織設計だった。AIネイティブの人なら「**そんな大袈裟な組織は要らない、もっと軽量に動けばいい**」と言うかもしれない。だが、私は14人のチームを毎日回している人間として、「軽量に動く」と「動かない」が紙一重であることを知っている。役割を切り、責任を置き、引き継ぎ可能にしないと、人もAIも動かなくなる。これは本業の現場感覚から来ている。

もしあなたが医療従事者なら、医療の組織原理を持ち込めばいい。チーム医療の役割分担、申し送りの構造、インシデント報告の習慣——これは AI 組織でもそのまま機能する。

教育者なら、授業設計の構造（導入→展開→まとめ）を AI のタスク設計に持ち込める。

法務なら、契約管理の責任分解と版管理の原則がそのまま使える。

**AI 活用の差別化は、AI 知識の量ではない。本業の構造を移植できるかで決まる**。「AIに詳しい」より「自分の本業を抽象化できる」の方が、長期では強い。

私が3ヶ月で29エージェントを書いて25個に収束させられたのは、AIの知識があったからではない。**製造業で同じことを14人のチームで毎日やっていたから**だ。本業の構造があったから、AI組織を設計する語彙があった。

## アンチパターン3つ

最後に、エージェント組織を作るときにやってはいけないことを3つ。

### NG1: エージェントを「便利機能の寄せ集め」として増やす

**症状**:
- 似た役割のエージェントが乱立する
- 「これは誰に頼めばいい？」が毎回発生する
- エージェント数は増えるのに成果は伸びない

**処方箋**:
- 部門・役職・責任で再編する。エージェントを増やす前に「**これはどの部門の責務か**」を必ず問う
- 組織図から逆算して定義する。組織図に置き場のないエージェントは、本当に必要か疑う

### NG2: 文脈共有を会話任せにして、Stateを残さない

**症状**:
- COO に毎回同じ説明を繰り返す
- セッションをまたぐと優先順位がぶれる
- COO が指揮官ではなく伝言係になる

**処方箋**:
- `07_System/State/` を中心に状態を明文化する
- 部門長が日次・週次で state を書き戻す習慣を持つ
- State File は「組織の朝会メモ」と捉え、肥大化させない（1部門30-50行）

### NG3: 全員が全部触れる設計にしてファイル衝突を起こす

**症状**:
- 同じファイルを複数エージェントが上書きする
- 誰が壊したのか追えない
- ユーザーの思考メモ（`00_Memo/`）まで AI が汚染する

**処方箋**:
- File Ownership Rule を設定する。最小10個程度に絞る
- `00_Memo/` はユーザー専用の聖域として固定する
- 排他書込みを前提に設計する。「全員が触れる」は事故の温床

## まとめ

エージェント組織は「**設計**」ではなく「**運用**」だ。

最初から完璧な組織図を描こうとしなくていい。3エージェントから始めて、必要に応じて部門化し、廃止と統合を経て、機能する形に収束させる。29個書いて4個減らした私のように、増減を恐れない。

本章で扱った設計パターンを振り返る。

1. **4部門＋COO＋CEO** の組織図で責任を分ける
2. **レジストリ駆動アーキテクチャ** で組織を辿れる構造にする
3. **State File パターン** で文脈を継承する
4. **File Ownership Rule** で衝突を防ぐ
5. **コスト制御**（モデル選択 × spawn制限）で組織を持続可能にする
6. **試行錯誤の証跡を残す**（廃止しても削除しない）
7. **本業の業務原理を AI 組織に移植する**

これでエージェントを「誰が何を担うか」という組織として配置できた。だが、組織図だけではまだ動かない。実際の運用では、各部門と各役職が**どのチャネルで会話し、どこで案件を受け渡し、どこに成果を流すか**という「通信路」の設計が必要になる。

次章 Ch.05 では、この組織を実際に稼働させるための `channel-agents` 設計に進む。部門とチャネルをどう結びつけるか——「組織が回り始める瞬間」の具体化だ。
