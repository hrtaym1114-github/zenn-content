# channel-agents設計──部門をチャネルへ流し込む

## 組織図の次は、外向きの窓口設計だ

Ch.04 で私は、「部門をどう分けるか」「誰に何を持たせるか」という組織設計を扱った。だが、組織図を描いただけでは商社は動かない。

実際に収益や信頼や接点が生まれるのは、note、ブログ、X.com、コミュニティといった**外向きの窓口**に、部門の知見が流れ込んだときだ。組織図は内向きの設計で、ここから先は外向きの設計になる。

ここで必要になるのが **channel-agents 設計**だ。部門エージェントが生み出した素材を、どのチャネルで、どの人格で、どの温度感で、どの導線設計のもとに出していくか。

私は当初、「**チャネルを増やせば接点も増える**」と考えて5チャネルを同時運用した。だが現実には、24投稿で1フォロワーしか増えない X アカウントもあった。伸びないチャネルを抱え続けることは、それ自体が機会損失だった。

本章では、4つの稼働チャネルと1つの統合廃止事例をもとに、「**部門 → チャネル**」をどう接続するかを具体化する。Ch.04 で扱った File Ownership Rule を、ここでは **Output Path の排他制御**として実装する。組織が実際に回り始める瞬間を、設計図として描く章だ。

> **組織図は内向き、channel-agents は外向きの実装である。**

---

## なぜ「部門設計」の次に「channel-agents設計」が必要なのか

組織図を描き終えたとき、私は満足してしまった。「これで動く」と。

3日後、Content Marketing Div の content-strategist にこう聞かれた。「**今週の note 記事は、どのトーンで、どの長さで、どこに置けばいいですか**」。

答えに詰まった。

「note は実機検証ベースで」「いや、X とリベシティとは違う書き方で」「もっと深掘り型で」——口で説明しても、毎週違う答えが出る。content-strategist は私の説明を聞いて書く。来週には別の説明をして、別の書き方になる。これでは「組織が動いている」とは言えない。

組織図は「**誰が何を担うか**」を決める。だが、外部に出すコンテンツは「**どのチャネルで、どんな人格で、どんなルールで出すか**」まで決めないと、毎回ぶれる。

つまり、3層の設計が必要だ。

```
部門エージェント（content-strategist 等）
  ↓ 「この案件を Note に出して」
channel-agent（note-ai-journal 等）
  ↓ チャネル固有のトーン・フォーマット・導線で具体化
外部プラットフォーム（note.com）
```

部門エージェントは「**何を**」を決める。channel-agent は「**どう出すか**」を決める。この2層が分離していると、部門は内容に集中でき、channel-agent は表現に集中できる。

逆に言うと、部門エージェントに「note のトーン」「ブログのトーン」「X のトーン」を全部書き込もうとすると、部門エージェントが肥大化して破綻する。**役割の分離**が必要だ。

本章では、この channel-agent 層を3つの観点で設計する。

1. **どのチャネルを持つか**（チャネル選定と投資配分）
2. **どう書くか**（channel-agent 定義の標準フォーマット）
3. **どう守るか**（Output Path 排他制御による衝突防止）

これが揃ったとき、「組織が回り始める瞬間」が来る。

## 私の現行チャネル構成──4つのActiveと1つのArchived

執筆時点（2026年5月）の私のチャネル構成は次のとおりだ。**投資比率順**で並べる。これが現在のマネタイズ重視戦略を最も率直に示している。

| 優先度 | ID | Platform | 役割 | 投資比率 | 更新頻度 | Status |
|--------|----|----|------|---------|---------|--------|
| 1 | note-aij | note.com | マネタイズ最優先 | **40%** | 週1（金曜） | Primary |
| 2 | x-ai | X.com (@Amu_Lab__) | 中央ハブ・他チャネルへの導線 | **30%** | 週4-5回 | Active |
| 3 | blog-aif | bhrtaym-blog.com | SEO長期資産 | **25%** | 月2-3本 | Active |
| 4 | lbc-main | リベシティ | コミュニティ維持 | 約5% | 週1-2回 | Active |
| — | x-tips | X.com (@amu_lab_tips) | （副アカウント実験） | 0% | — | **Archived** |

**4つの Active**、**1つの Archived**。これがエージェント数25の中でも特に外向きを担う5つの定義だ。

役割の違いを言葉で書くとこうなる。

- **note**: マネタイズの主戦場。実機検証ベースの記事を週1で出す。読者はAI/テック検証を求めている。
- **x-ai**: 中央ハブ。すべての投稿が「**次に読むべきものへ導く**」ことをルール化。note・blog・リベシティへの導線を毎投稿に含める。
- **blog**: SEO長期資産。ローカルLLM・セキュリティの深掘り記事で検索流入を狙う。Paused期もあった。
- **リベシティ**: 副業・独立志向のコミュニティ。維持運用で、過剰投資はしない。

この4チャネルで、それぞれ違う人格・違うトーン・違う導線を持っている。**同じ内容を全チャネルに横展開する**のではない。チャネルごとに「**ここで何を達成したいか**」を分けている。

そして **x-tips**。これは2026-03-28 にアーカイブした副アカウントだ。「Tips 系の軽い投稿で別の読者層を取りに行く」つもりで作ったが、24投稿で1フォロワーしか付かなかった。アルゴリズム変更の影響と、メインの @Amu_Lab__ との差別化が弱かったことが原因だ。

x-tips は H2-7 で詳しく扱う。**伸びないチャネルを早く畳む判断**は、channel-agents 設計の重要な一部だ。

> **すべてのチャネルを同じ熱量で運用する必要はない。役割と投資配分で差をつける。**

念のため整理しておくと、ここで紹介した5つの channel-agent は、Ch.04 で触れた **25 エージェント / 68 Skill** の中の一部だ。1人で 25 個のエージェントを抱えていても、外向きを担うのはこの5つだけ。残りは内向き（部門長、Advisory Board、PaperBanana、ユーティリティ）だ。

## channel-registry.mdは「チャネル台帳」ではなく運用OS

5チャネルを並べただけでは、まだ動かない。

最初、私は各 channel-agent を `.claude/agents/channels/` に置いて、それぞれ独立に動かしていた。content-strategist が「今週はどのチャネルを動かす？」と聞くと、私が「note と X」と答える。これだと毎回聞かれる。

そこで作ったのが **`channel-registry.md`** だ。Ch.04 で扱った `org-registry.md` のチャネル版にあたる。

```markdown
# Channel Registry

## Active Channels

| ID | Platform | Account | Persona | Agent File | Output Path | Status |
|----|----------|---------|---------|------------|-------------|--------|
| note-aij | note.com | AI検証ジャーナル | 実機検証 | channels/note-ai-journal.md | Note-AI-Journal/@TODO/ | Primary |
| x-ai | X.com | @Amu_Lab__ | 中央ハブ | channels/x-ai-lifestyle.md | X-Twitter/@TODO/ | Active |
| blog-aif | Blog | bhrtaym-blog.com | ローカルLLM志向 | channels/blog-ai-frontier.md | Blog-Writing/@Doing/ | Active |
| lbc-main | リベシティ | メイン | 副業・独立志向 | channels/libecity-main.md | Libecity/@TODO/ | Active |

## Archived Channels

| ID | Platform | Archived Date | Reason |
|----|----------|---------------|--------|
| x-tips | X.com @amu_lab_tips | 2026-03-28 | 24投稿で1フォロワー、@Amu_Lab__に統合 |

## Planned Channels

| ID | Platform | Status |
|----|----------|--------|
| borders | Borders Daily | Existing（既存スキル） |
| dx-portal | DX Portal | Q2以降 |
```

これがあると、content-strategist は registry を1回読めば「**今 Active なチャネルはこの4つ、それぞれの出力先はここ**」が一発で分かる。私が口頭で説明する必要はゼロだ。

Ch.04 で扱った COO も、朝のブリーフィングのたびにこの registry を読む。COO の関心は「**全部門全チャネルの今の状態**」だから、各部門の State File と並んで、registry が必読リストに入る。content-strategist と COO は同じ registry を共有して、違うレイヤーで使う。前者は「**今週どのチャネルを動かすか**」、後者は「**チャネル全体が回っているか**」を見る。同じファイルが2つの視点を支える。

ここで重要なのは、registry は **単なる一覧表ではない**ということだ。これは **運用 OS** として機能する。

何が違うか。registry には以下が組み込まれている。

**1. ステータス管理（Active / Archived / Planned の3区分）**: 今動かすべきもの、過去に試したもの、将来やりたいもの。すべて1ファイルで追跡できる。Archived を消さないのは、Ch.04 で書いた「**試行錯誤の証跡**」と同じ思想だ。

**2. Output Path の明示**: 各チャネルが書き込むフォルダが明示されている。これが次節の排他制御の前提になる。

**3. Persona と Agent File の対応**: 「note は実機検証」「x-ai は中央ハブ」というペルソナと、対応するエージェント定義ファイルが紐づいている。新しいチャネルを追加するときは、まず registry に登録してから定義ファイルを作る。逆ではない。

製造業で言えば、これは「**製品マスター**」に近い。製品ID、ラインID、出荷先、ステータス。これが一覧されていれば、誰が見ても「いま何が動いていて、何が止まっているか」が分かる。AI 組織でも同じものを持つ。

registry を作ったあと、運用が劇的に変わった。新しいチャネルを試したいとき、まず registry に Planned で登録する。やらないと決めたとき、Archived に移して理由を書き残す。**動かす・止める・記録する**の3操作が1ファイルで完結する。

> **registry は一覧表ではなく、運用OSだ。Active/Archived/Planned の3区分を持つことで、組織が「動かす・止める・記録する」を一元化できる。**

## File Ownership Ruleを運用に落とす──Output Path排他制御

Ch.04 で「File Ownership Rule」の概念を扱った。誰がどのフォルダに書けるかを宣言する仕組みだ。channel-agents 設計ではこれを **Output Path 排他制御**という形で実装する。

具体例で見せる。

```
| Output Path                                  | Owner       |
|----------------------------------------------|-------------|
| Note-AI-Journal/@TODO/                       | note-aij    |
| Note-AI-Journal/@Doing/                      | note-aij    |
| Note-AI-Journal/@Completed/                  | note-aij    |
| X-Twitter/@TODO/                             | x-ai        |
| X-Operation/Post-Ideas/                      | x-ai        |
| Libecity/@TODO/                              | lbc-main    |
| Blog-Research/                               | blog-aif    |
| Blog-Writing/@Doing/                         | blog-aif    |
| 00_Memo/                                     | 禁止（ユーザーのみ） |
```

**1パスにつき1エージェントのみ書込み可能**。これが絶対ルールだ。

このルールを徹底すると、3つの効果が出る。

**1. 並列実行で衝突が起きない**: `/team-content-sprint` のように複数チャネルを並列で動かしても、書き込み先が違うのでファイル衝突がゼロになる。

**2. デバッグが速い**: 「note の @TODO/ が変な状態になっている」と気づいたら、犯人は note-aij しかいない。原因特定が即終わる。

**3. チャネル単位での履歴管理が綺麗になる**: 1つのフォルダに1つのエージェントが書き続けるから、コミット履歴を見れば「このチャネルが何月何日に何を書いたか」が時系列で追える。

逆に、このルールを破った場合に何が起きるか。実際に1度やった。

ある日、急いで X.com の投稿を作りたくて、`x-ai-lifestyle` ではなく content-strategist 経由で `X-Twitter/@TODO/` に直接書き込んだ。その後、`/team-content-sprint` を叩いたら、x-ai-lifestyle が「**TODO に知らないファイルがある**」状態を検知して動きを止めた。Skill 内のロジックが「自分の管轄ファイル以外を発見したら例外」と書かれていたからだ。

これは小さな事故だが、教訓が大きい。**排他制御は守るためだけのルールではなく、エージェントが安心して動くための前提**だ。前提が崩れた瞬間、エージェントは止まる。

導入のコツは、**Output Path をフォルダ単位で切る**ことだ。ファイル単位で切ると粒度が細かすぎて管理できない。「フォルダ X はエージェント A 専用」と切れば、ルールは10個程度に収まる。

| 粒度 | ルール数 | 管理性 |
|------|---------|--------|
| ファイル単位 | 100+ | 破綻 |
| フォルダ単位 | 10前後 | 健全 |
| パス前半マッチ | 5前後 | 大雑把すぎ |

私の現状は「フォルダ単位」で10個前後。これがちょうどいい。

最後に、**`00_Memo/` だけはどのエージェントも触れない**。これは Ch.04 でも書いたが、外向きの channel-agent も例外ではない。生の思考メモはユーザーの聖域だ。

> **Output Path 排他制御は、エージェントを縛るためではなく、エージェントが安心して動くための前提だ。**

## チャネルエージェント定義は「投稿者設定」ではなく「出口人格の固定」

channel-agent の定義ファイル（例: `channels/x-ai-lifestyle.md`）はどう書くか。

最小構成はこうなる。

```yaml
---
name: x-ai-lifestyle
description: X.com 副業エコシステム中央ハブ担当エージェント
model: sonnet
tools:
  - Read
  - Glob
  - Grep
  - Write
  - WebSearch
---

# X.com: AIで副業を仕組み化する人（@Amu_Lab__）

## Account Info
- Platform: X.com
- Account: @Amu_Lab__
- Persona: AIエージェントで副業を仕組み化する過程を全部公開する実践者
- Tone: 淡々と正確に。煽らない。
- 目指す姿: 副業エコシステムの中央ハブ
- 核心ルール: すべての投稿は「次に読むべきもの」へ導く。X.comで完結させない

## ポジショニング
（差別化軸の表）

## Reference Accounts（トーン参考）
（参考にしているアカウントとその学習ポイント）
```

これを書くときに犯しがちな誤解がある。「**投稿者の人物像を細かく書く**」という発想だ。年齢、性別、口癖、好きな食べ物——そういうキャラクター設定。

これは要らない。

channel-agent は **キャラクター**ではない。**出口人格**だ。「このチャネルから出るコンテンツは、こういう温度感・こういう導線・こういうルールに従う」という出口の固定が目的だ。

定義に必要な要素は5つに絞れる。

**1. Tone（温度感）**: 煽る/淡々/熱く/控えめ。1行で定義。

**2. 目指す姿（チャネルのゴール）**: マネタイズ/中央ハブ/SEO/コミュニティ。複数書かない。1つに絞る。

**3. 核心ルール（このチャネル固有の動かない決まり）**: 例: x-ai は「次に読むべきものへ導く」、blog は「ローカルLLMとセキュリティ以外は書かない」。

**4. 差別化軸（他チャネルや競合との違い）**: なぜここに価値があるか。Skill 設計と同じく、**何を捨てているか**を書くと際立つ。

**5. Reference Accounts（トーン参考）**: お手本にしているアカウント。これがあると、Claude が「このトーンで」と理解しやすい。

この5要素だけで、channel-agent は十分動く。

逆に、書きすぎるとブレる。私は最初、各 channel-agent に「投稿の禁止ワード集」「使う絵文字一覧」「文末パターン10種」まで書き込んでいた。Claude は迷う。「このワードは禁止リストにあるが、文脈的には使うべき」のような葛藤が発生して、判断が止まる。

絞った後、定義は1チャネル200-300行に収まっている。それで十分動く。

> **channel-agent はキャラクターではなく、出口人格だ。Tone・ゴール・核心ルール・差別化軸・参考アカウントの5要素に絞る。**

## チャネルごとの核心ルールをどう切り分けるか

5要素のうち、最も重要なのが **核心ルール**だ。これは「**このチャネル固有の、絶対に動かない決まり**」を1-3個に絞ったものだ。

私の4チャネルの核心ルールはこうなっている。

| チャネル | 核心ルール |
|---------|-----------|
| note-aij | **実機検証ベースで書く**。机上の知識だけの記事は出さない |
| x-ai | **すべての投稿は次に読むべきものへ導く**。X.comで完結させない |
| blog-aif | **ローカルLLMとセキュリティの深掘り以外は書かない**。テーマを絞る |
| lbc-main | **副業の実用Tipsに絞る**。ニュース速報は書かない |

これらは抽象論ではない。**毎回の投稿で、これに違反していないかをチェックする**ためのルールだ。

たとえば x-ai の「次に読むべきものへ導く」は、note 記事の告知、ブログ記事のリンク、リベシティ投稿への誘導、いずれかが投稿に含まれていないと違反になる。x-ai-lifestyle.md にはこのチェックロジックが書かれていて、生成された投稿に導線が無ければ「**追加してください**」と返してくる。

核心ルールを設計するコツは3つある。

**1. 「やること」より「やらないこと」を書く**

「実機検証ベースで書く」は「机上の知識だけでは書かない」と同義だ。**禁止事項として書くと、判断が明確になる**。「やった方がいい」より「やってはいけない」の方が、ルールとして機能する。

**2. 1-3個に絞る**

5個以上書くと、エージェントが迷う。10個書いたら無視される。私はどのチャネルも3個までに絞っている。それを超える細部は、別ファイル（出力フォーマット集など）に切り出す。

**3. チャネル間で被らないようにする**

note と blog の核心ルールが同じだと、2つのチャネルを持つ意味がない。「note は実機検証ベース、blog は SEO 狙いの深掘り」と切り分けると、それぞれの存在意義が明確になる。

ここで失敗例を1つ。最初、note と blog の両方に「**読者の悩みを解決する**」という核心ルールを書いていた。これだと「どっちに書けばいいか」がブレた。両方とも「読者の悩み解決」なら、1チャネルで十分だ。

両者を分けたいなら、note は「**実機検証して数字を出す**」、blog は「**長期SEOで検索流入を取る**」と、目的レベルで切り分ける。そうしないと、チャネル数だけ増えて中身が散る。

> **核心ルールは「やらないこと」を1-3個に絞る。チャネル間で被らせない。**

## 伸びないチャネルは早く畳む──x-tips統合廃止の判断基準

ここまでで稼働中の4チャネルの設計を扱った。だが、channel-agents 設計の真価は **伸びないチャネルをどう判断して畳むか**にある。

私は2026年2月、X.com の副アカウント `@amu_lab_tips`（x-tips）を立ち上げた。狙いは2つ。

1. メインの @Amu_Lab__ とは別の読者層を取る（Tips 系で軽く拾う）
2. 自動投稿システムの実験場として動かす（VPS で cron 投稿）

3週間運用して、結果はこうなった。

| 期間 | 投稿数 | フォロワー獲得数 |
|------|-------|-----------------|
| 2026-03-07 〜 2026-03-28（3週間） | **24** | **1** |

24投稿で1フォロワー。**伸び率は0.04 フォロワー/投稿**。比較対象として、同期間のメインアカウント @Amu_Lab__ は週4-5投稿で月平均10-15フォロワー増えていた（伸び率約0.7-1.0フォロワー/投稿）。

判断基準を設定した。

```
畳む判断: 検証期間3週間で、伸び率がメインの 1/10 以下なら停止する
```

x-tips は伸び率0.04、メインは0.7-1.0。約 **1/20-1/25**。閾値を下回った。

2026-03-28 に統合廃止を決めた。処置は次のとおりだ。

**1. VPS 自動投稿 cron を全停止**: 動かし続けるとコストだけ食う。
**2. プロフィールを @Amu_Lab__ へのリダイレクトに書き換え**: 来訪者を取りこぼさず本アカウントへ流す。
**3. channel-registry.md の Active から Archived に移動**: 「2026-03-28 Archived」「Reason: 24投稿で1フォロワー、@Amu_Lab__ に統合」と理由を記録。
**4. channels/x-tips.md は削除せず残す**: Ch.04 の「**試行錯誤の証跡**」の原則どおり、定義ファイルは残し、description に「**[ARCHIVED 2026-03-28] @amu_lab_tips — 統合廃止済み**」を明記。

ここで重要なのは、**畳む判断を感情ではなく数字で決めた**ことだ。「もう少し続ければ伸びるかも」「3週間は短すぎないか」——そういう逡巡は必ず出る。だが、検証期間と閾値を**事前に設定**しておけば、機械的に判断できる。

別の言い方をすると、**畳む基準を事前に書くことがチャネル開設の前提**だ。「**3週間試して伸びなかったら畳む**」と書かずに始めたチャネルは、ずるずる続いて、リソースだけ食う。

伸びない原因の分析もした。x-tips の場合、2つの要因が見えた。

**外部要因（アルゴリズム変更）**: X.com の表示アルゴリズムが大きく変わり、新規アカウントの初期成長が極端に遅くなった。これは1人で打開できない。

**内部要因（差別化の弱さ）**: メイン @Amu_Lab__ との差別化が「Tips 軽め」だけで、読者から見た独自価値が弱かった。

外部要因と内部要因の両方が重なっていた。「**外部要因だけなら継続も検討、内部要因が重なっているなら撤退**」というのが、その後の私の判断軸になった。

これは Ch.04 で扱った「**廃止と統合**」原則の具体例だ。29個のエージェントが25個に収束したように、5チャネルが4チャネルに収束した。**増やすより減らす方が難しい**。だから減らす基準を事前に書く。

> **チャネル開設の前提は、畳む基準を事前に書くことだ。検証期間と閾値が無いチャネルは、ずるずる続いてリソースを食う。**

## channel-agents設計を回す運用原則──投資配分・更新頻度・導線設計

ここまでで、個別の channel-agent をどう設計するかは見えた。最後に、複数のチャネルを**全体として回す**ための3つの運用原則を整理する。

### 原則1: 投資配分は「マネタイズ最優先」で決める

私の現在の投資配分はこうだ。

| チャネル | 投資比率 | 根拠 |
|---------|---------|------|
| note | 40% | マネタイズの主戦場、戦略γの優先1位 |
| x-ai | 30% | 中央ハブ、他チャネル誘導 |
| blog | 25% | SEO長期資産、緩やかに積む |
| リベシティ | 5% | コミュニティ維持、過剰投資しない |

これは「**全チャネルを均等に運用する**」考え方とは真逆だ。私は均等運用を半年やって、どれも中途半端になった経験がある。

投資配分を**収益貢献度で重みづけ**したら、迷いが減った。「今週は時間が足りない」と思ったとき、5%のリベシティを後回しにする。40%の note は何が何でも回す。**優先順位が事前に決まっている**から、その場で考えなくていい。

この投資比率は content-state.md にも書き込んであり、COO がブリーフィングで読み込む。「**今週はリベシティを後回しにします**」のような提案が、私の判断より先に出てくる。投資配分は私が頭で覚えておくものではなく、ファイルに書き出してエージェントに参照させるものだ。

### 原則2: 更新頻度は「人間が回せる範囲」で決める

最初、私は全チャネル毎日更新を目指した。1週間で破綻した。仕事と家庭を持つ1人の人間が、毎日5チャネル更新するのは無理だ。

現在の更新頻度は次のとおりだ。

| チャネル | 更新頻度 | 理由 |
|---------|---------|------|
| note | 週1（金曜） | 実機検証に時間がかかる、量より質 |
| x-ai | 週4-5回 | 中央ハブとして接点を持つ必要 |
| blog | 月2-3本 | SEO狙いの深掘り、頻度より検索意図合致 |
| リベシティ | 週1-2回 | コミュニティ維持の最小限 |

合計すると、週に **note 1本 + x-ai 4-5本 + blog 0.5本 + リベシティ 1-2本** ≒ 6-9本。これがギリギリ回せる量だ。これを超えると、品質が落ちるか公開遅延が起きる。

「**頻度を増やす**」より「**頻度を守る**」の方が長期では効く。週1の note を半年続ければ24本。月2の blog を半年続ければ12本。**続けることがリーチを作る**。

### 原則3: 導線設計は「中央ハブを必ず作る」

複数チャネルを持つときの最大の落とし穴は、**各チャネルが孤立する**ことだ。note 読者が blog を知らない、X.com 読者が note を知らない。結果として、各チャネルの読者数の合計が「ユニーク総数」になってしまう。

これを防ぐのが **中央ハブ**だ。私の場合は x-ai が中央ハブを担う。x-ai-lifestyle.md には核心ルールとして「**すべての投稿は次に読むべきものへ導く**」が書かれている。

具体的には、X.com の投稿は必ず次のいずれかを含む。

- note 記事の告知（公開直後）
- blog 記事のリンク（SEO 狙い記事の補強）
- リベシティ投稿の予告（コミュニティ誘導）

これがあると、**読者の重複が起きる**。X.com 読者が note を読む。note 読者が blog を読む。同じ人が複数チャネルを巡回する。これが「**ユニーク総数ではなく、エンゲージメント総量**」を増やす。

中央ハブを持たないチャネル運用は、いくらチャネルを増やしても接点が増えない。**チャネルを増やす前に、ハブを決める**。これが順序だ。

> **投資配分・更新頻度・導線設計の3原則を、チャネル全体として持つ。個別のチャネル設計は、この3原則の上に乗る。**

## アンチパターン3つ

### NG1: チャネルを「とりあえず増やす」

**症状**:
- 「やっておいた方がいいかも」でチャネルを開設する
- 投資比率を決めずに始める
- 畳む基準を書かずに始める

**処方箋**:
- 開設前に「**投資比率**」「**更新頻度**」「**畳む基準**」の3つを registry に書く
- 既存4チャネルの投資配分を変えずに新チャネルを足せるか確認する。足せないなら開設しない

### NG2: channel-agent にキャラクター設定を書きすぎる

**症状**:
- 投稿者の人物像（年齢・性別・口癖）を細かく書く
- 禁止ワード集や絵文字一覧を網羅する
- 定義ファイルが500行を超える

**処方箋**:
- 5要素（Tone / ゴール / 核心ルール / 差別化軸 / Reference Accounts）に絞る
- 細部は別ファイル（出力フォーマット集）に切り出す
- 定義ファイルは1チャネル200-300行に収める

### NG3: 中央ハブを持たずに複数チャネルを運用する

**症状**:
- 各チャネルの読者が孤立する
- チャネルを増やしてもエンゲージメント総量が増えない
- どのチャネルから読み始めても他チャネルにたどり着けない

**処方箋**:
- 1チャネルを中央ハブに固定する（私の場合は x-ai）
- ハブの核心ルールに「**次に読むべきものへ導く**」を書く
- 他チャネルから新規コンテンツが出たら、必ずハブで告知する運用にする

## まとめ──「部門 → チャネル → チーム」へ接続する

channel-agents 設計は「**外向きの実装**」だ。

部門エージェントが内容を決め、channel-agent が表現を決める。Output Path 排他制御が衝突を防ぎ、registry が運用 OS として全体を回す。**役割の分離が、組織を動かす**。

本章で扱った原則を振り返る。

1. **3層設計**: 部門エージェント → channel-agent → 外部プラットフォーム
2. **registry は運用OS**: Active / Archived / Planned の3区分で動かす・止める・記録する
3. **Output Path 排他制御**: 1パスにつき1エージェントのみ書込み可能
4. **5要素に絞った定義**: Tone / ゴール / 核心ルール / 差別化軸 / Reference Accounts
5. **核心ルールは「やらないこと」を1-3個**: チャネル間で被らせない
6. **畳む基準を事前に書く**: 検証期間と閾値が無いチャネルは続かない
7. **投資配分・更新頻度・導線設計の3原則**: 全体として回すための上位ルール

これで個別のチャネルとその設計が揃った。

だが、ここまでは「**チャネルごとに独立して動く**」前提だ。実運用ではもう一段上のレイヤーがある。**複数チャネルを並列で同時に動かす**運用——たとえば「**今週のテーマを決めて、note と X.com とリベシティを並列で同時に書き出す**」という動き方だ。

これを支えるのが **agent-teams**——複数エージェントの並列協調設計だ。次章 Ch.06 では、この層に進む。**チャネルごとに動く**から、**複数チャネルが連動する**へ。組織が「並走」を始める瞬間の設計だ。
