# daily-workflow──1日の運用の流れ

## 設計しただけでは組織は回らない

Ch.06 の最後で、私はこう書いた。

> 組織は設計するものではなく、運用するものだ。次は、毎日の動かし方を扱う。

Ch.07 は、その宣言を回収する章だ。

Part 2 までで、CLAUDE.md を整え、Skill を書き、エージェント組織を設計し、channel-agent を切り出し、agent-teams で並列実行まで組み上げた。設計図としては完成形だ。

ところが、設計図があることと、毎日動くことは**まったく別の問題**だ。

私自身がそうだった。Ch.04 で 25 個のエージェントを書き終えたとき、満足してしまった。「これで自動的に副業が回る」と。

回らなかった。

朝起きても、どのコマンドから叩けばいいか分からない。叩く時間がない。叩き忘れる。叩いても結果を見ない。1週間で気づいた。**設計図と運用は別物**だ。

特に副業で回す「1人総合商社」では、この差が容赦なく出る。本業の合間で動かす私の副業時間は、**平日30分から1時間、休日でも2-3時間**。この制約の中で、毎朝どこから起動し、日中にどう同期し、夕方にどう閉じるか——それが決まっていなければ、組織はすぐに「**置物化**」する。

Part 3 の初章である本章が扱うのは、壮大な戦略ではない。むしろ逆だ。**5分、10分、15分の単位**で「**どう回すか**」だ。

`/morning-sync`、`/coo-briefing`、`/daily`、`/daily-update`、`/daily-evening`——この一連の流れを通じて、「**組織を設計した状態**」から「**組織が毎日回っている状態**」へ移る。その切り替え点を、daily-workflow という運用の型として具体化する。

設計編が閉じた。ここからは運用編だ。

> **組織設計の完成はゴールではなく、daily-workflow の起点である。**

---

## 平日30分-1時間で回す──daily-workflowは時間制約から設計する

副業の話をすると、よく聞かれる。

「平日、何時間くらい使ってますか？」

正直に答える。**平日30分から1時間**。多くて1時間半。これ以上は無理だ。本業がフルタイム、家族との時間もある。子どもを寝かしつけたあとに少しできる程度。

休日は2-3時間。土曜の朝に集中するか、日曜の昼にまとめて動くか。これも子どもの予定が入れば縮む。

世の中の「副業で稼ぐ」発信は、**この時間制約を語らない**ことが多い。「毎日3時間集中すれば」「土日10時間使えば」——その前提でワークフローを設計すると、本業フルタイムの社会人には合わない。1週間で破綻する。

私は最初、毎日2時間取る前提でワークフローを組んだ。当然、続かなかった。残業が入った日は0分。子どもが熱を出した日も0分。1週間のうち2-3日は計画が崩れた。

そこで発想を逆転させた。**「30分しか取れない」を前提に、ワークフローを設計する**。30分でも回る型を作る。それ以上時間が取れた日は、ボーナスとして余裕タスクを足す。

これが daily-workflow の根本思想だ。

```
× 「2時間あれば全部できる」前提で設計
○ 「30分しかない」前提で設計、超えた分は余裕
```

時間制約から設計すると、必然的に**3フェーズ構造**に落ち着く。

| フェーズ | 時間 | 目的 |
|---------|------|------|
| **朝** | 5-15分 | 1日を起動する（状態確認、優先タスク確定） |
| **日中** | 合間に5分×1-2回 | 進捗同期（Daily ⇔ Kanban） |
| **夕方** | 10-15分 | 1日を閉じる（完了集計、明日への引き継ぎ） |

合計しても **最低20分、最大35分**。これなら平日30分の制約に収まる。残った時間で本業のメール処理、家事、家族との時間が取れる。

時間制約が明確だと、各コマンドも自然と最適化される。`/morning-sync` を3分で終わるよう設計する。`/coo-briefing` のブリーフィング出力を1画面に収める。`/daily-evening` の振り返り項目を3つに絞る。**時間が決まると、設計が決まる**。

逆に「**いくらでも時間が取れる前提**」で設計したワークフローは、必ず時間が膨張する。1コマンドが10分で終わるはずが15分かかる。15分が30分に伸びる。それを毎日繰り返せない。

副業 daily-workflow の本質は「**長く働く設計**」ではなく「**短く回す設計**」だ。

> **30分しか取れないを前提に設計する。時間制約が、ワークフローを規定する。**

## 朝5-15分で1日を起動する──/morning-sync → /coo-briefing → /daily

朝、私が叩くコマンドは3つだ。

```
1. /morning-sync   （2-3分）外部状態の同期
   ↓
2. /coo-briefing   （3-5分）全部門状態の統合と優先アクション提案
   ↓
3. /daily          （3-5分）デイリーノート作成、Top 3 Priorities設定
   ↓
合計: 8-13分
```

順番が重要だ。**外部状態 → 組織状態 → 個人タスク**という流れになっている。

### /morning-sync ──外部状態を取り込む

最初に叩くのが `/morning-sync` だ。これは「**外部で起きていること**」を Vault に取り込む。

具体的には次を同期する。

- **メール**: 昨夜から朝までに届いたメールを Outlook から同期
- **カレンダー**: 今日の予定を Google Calendar から取得
- **前日継続タスク**: 昨日の `/daily-evening` で繰り越し決定したタスク

これは「**自分が動く前に、世界が動いていた情報**」を見るための作業だ。重要なメールが届いていないか。今日の本業の会議は何時か。昨日のうちに優先順位が変わるような出来事があったか。

`/morning-sync` を飛ばすと、その後の `/coo-briefing` や `/daily` が**古い情報のまま動く**。「**昨日のままの今日**」を計画してしまう。これが副業を続けるうえで一番の落とし穴だった。

### /coo-briefing ──組織の現状を読む

次に `/coo-briefing` を叩く。これは Ch.04 で扱った COO による全4部門ブリーフィングだ。

COO はこう動く。

1. `org-registry.md` を読み、Active 部門を確認
2. 各部門の **State File** を読む（content-state, rd-state, career-state, infra-state）
3. **Staleness 判定**: 各データソースの鮮度を Warning / Critical / Healthy で判定
4. 統合ブリーフィングを出力: 「今日はこれを優先すべきです」

Staleness 判定の閾値はこうなっている。

| データソース | Warning | Critical |
|------------|---------|---------|
| trend.md（朝のトレンド収集） | 当日分なし | 2日以上なし |
| メールJSON | 3日以上前 | 7日以上前 |
| inner-coach（内省セッション） | 7日以上前 | 14日以上前 |
| infra-health（Vault健全性） | 7日以上前 | 14日以上前 |
| skills update（スキルマップ） | 30日以上前 | 60日以上前 |
| project-registry | 7日以上前 | 14日以上前 |

判定ルール:

- **Critical 1つ以上** → 部門ステータス 🔴
- **Warning 1つ以上**（Critical 無し） → 🟡
- **すべて閾値内** → 🟢

これがあると、私が「**何から手をつけるべきか**」を考える必要がない。COO のブリーフィング出力に「Tech Infrastructure: 🔴 — infra-health が14日以上前。先に `/infra-health` を回してください」と書いてある。私はそれに従うだけだ。

Staleness 判定の本質は、「**赤信号を先に潰す**」運用にある。ピカピカに光るところを伸ばすより、暗いところを先に潰す方が、組織は持続する。

### /daily ──個人のタスクを確定する

最後に `/daily` を叩く。これは個人のデイリーノートを作成し、Top 3 Priorities を設定する。

`/daily` は内部で次を実行する。

1. `bash 07_System/Scripts/get-date-info.sh` で今日の日付・曜日・週番号を取得
2. テンプレートをコピーして `02_Daily/YYYY/YYYY-MM/YYYY-MM-DD/` に配置
3. `01_Inbox/` から未完了タスクを3つ抽出
4. **Weekly Command Center** を読み、今週のフォーカスと実行待ちアラートを反映
5. **Top 3 Priorities を質問**してくる（私が答える）
6. Daily Kanban を「今日やる」カラムでリセット

ここで**朝イチのもう1つの儀式**を入れる。**エネルギースコアの記録**だ。1-10で自分の体調・集中力を数値化する。

エネルギースコアが低い日（4以下）の Top 3 Priorities は、**重い思考タスクを避ける**。執筆系は休んで、整理系・ルーティン系に切り替える。エネルギースコアが高い日（8以上）は、思考が要る企画や原稿に集中する。

これは自分のバイオリズムに**ワークフローを合わせる**設計だ。「毎日同じ時間に同じことをやる」より、「毎日のコンディションに合わせて優先順位を変える」方が、長期では続く。

### 朝の8-13分で何が決まるか

朝の3コマンドが終わると、次が決まっている。

- 今日重要なメール・予定
- 今日叩くべきコマンド（COO 提案）
- 今日の Top 3 Priorities（私が決定）
- 今日のエネルギーコンディション

これだけ揃えば、その後の日中はもう「**判断**」をしなくていい。**実行するだけ**だ。

副業の最大の敵は「**毎回考える**」ことだ。「今日は何から手をつけるか」を毎朝ゼロから考えると、それだけで疲れる。**判断を朝の8-13分で終わらせる**——これが daily-workflow の朝フェーズの目的だ。

> **朝の8-13分で「判断」を終わらせる。日中は実行だけにする。**

## 日中は長く働かない──合間の5分で /daily-update を回す

日中は本業の時間だ。副業に長く時間を割けない。

それでも、副業を「**動いている状態**」に保つには、日中に短い同期作業を入れる。これが `/daily-update` だ。

### /daily-update の役割

`/daily-update` は、**Daily ノートと Daily Kanban の双方向同期**を行う。

```
Daily ノート ⇔ /daily-update ⇔ Daily Kanban
```

具体的には、次が起こる。

1. Daily ノート内の `- [ ]` チェックボックスを Kanban に反映
2. Kanban で完了になったタスクを Daily ノートに反映
3. 新しく追加されたタスクをどちらか欠けている側に追加

これを**5分以内**で終わらせる。長くかからない。

### いつ叩くか

私が `/daily-update` を叩くタイミングは、1日2-3回。

- **昼休み（12:00-13:00）**: 午前の進捗を Kanban に反映
- **退勤後（18:00-19:00）**: 夕方の状況を整理
- **必要時**: メール処理後や会議後にタスクが増えたとき

「**朝決めた Top 3 Priorities が、今どこまで進んでいるか**」を視覚化することが目的だ。

### Kanban が「現場」になる

`/daily-update` を回すと、Daily Kanban が**1日の現場の状態**を反映する。5カラム構成はこうなっている。

```
🔴 今日やる    | 🟡 作業中    | 🟢 完了    | 📦 今夜（19:00〜）  | 🔵 余裕があれば
```

朝は「🔴 今日やる」に Top 3 Priorities が並んでいる。日中に1つ着手すれば「🟡 作業中」に移動。終われば「🟢 完了」へ。夜にやる予定の公開・投稿系は「📦 今夜」に分けておく。

このカラム移動は、Obsidian の Kanban プラグインで**ドラッグ＆ドロップ**できる。1秒で動かせる。動かしたあと `/daily-update` を叩けば、Daily ノートにも反映される。

### なぜ「現場」が要るのか

副業時間が限られていると、「**自分が今、何をやっているか**」を見失いやすい。朝決めたタスクを忘れて、別のことを始める。完了したのに完了マークを付け忘れる。

Kanban が「現場」として常に開いていると、これが起きにくい。視覚的に「🟡 作業中」が空っぽだと、「あ、今は何もしてない」と気づける。「🟢 完了」が増えていくと達成感がある。**視覚化が継続を支える**。

> **日中の5分で Daily と Kanban を同期する。Kanban が「現場」として継続を支える。**

## 夕方10-15分で閉じる──/daily-evening が明日の起点を作る

1日を閉じるのが `/daily-evening` だ。

これは「**今日を終わらせる**」ためのコマンドであると同時に、「**明日の起点を作る**」ためのコマンドでもある。

### /daily-evening の動作

`/daily-evening` を叩くと、次が起こる。

1. 今日の Daily Kanban から完了タスクを集計
2. Daily ノートに「今日完了したこと」を記録
3. 未完了タスクを抽出
4. 未完了タスクを **明日へ繰り越すか / 廃棄するか** をユーザーに問う
5. 振り返りを3項目で記録（うまくいったこと、改善点、明日意識すること）
6. 翌日の Daily ノート用に「**引き継ぎメモ**」を生成

ここで重要なのは、**未完了タスクを「自動で繰り越さない」**ことだ。

### 繰り越し判断こそが運用

未完了タスクを毎日機械的に繰り越すと、Kanban に**幽霊タスク**が溜まる。3日繰り越されたタスクは、5日繰り越される。1週間繰り越されたタスクは、1ヶ月繰り越される。**そして誰も触らない**。

`/daily-evening` で1日1回、未完了タスクに対して問う。

「これは明日もやるか？ それとも廃棄するか？」

廃棄が増えても良い。むしろ廃棄を許容する文化が、Kanban を**生きた状態**に保つ。「**やる気はあるが手が回らないタスク**」は、潔く廃棄したほうがいい。本当に必要なら、また Inbox から復活する。

### 引き継ぎメモ

`/daily-evening` の最後で、翌日の Daily ノート用に**引き継ぎメモ**を生成する。例:

```
■ 2026-05-19 → 2026-05-20 引き継ぎ

未完了で繰り越すタスク:
- [ ] note記事「Claude Code × Skills」公開作業（公開ボタンだけ残り）

今日の発見:
- /team-content-sprint は 7-10分で終わると分かった
- COO ブリーフィングの staleness 判定が役立った

明日意識すること:
- 朝のエネルギースコアを必ず記録する
```

これが翌朝の `/daily` で参照される。「**昨日の自分が、今日の自分に申し送る**」仕組みだ。

人間のチームでも引き継ぎメモは重要だが、1人副業ではもっと重要だ。**今日の自分と明日の自分は別人**だと考えた方がいい。記憶は薄れる。優先順位はぶれる。文書化された引き継ぎだけが、組織を継続させる。

### 夕方を閉じる効果

`/daily-evening` を叩くと、「**今日は終わった**」という心理的な区切りが付く。これがないと、夜中もずっと「あれもやってない、これもやってない」が頭に残る。

10-15分で1日を閉じる。明日への引き継ぎを書き出す。これで頭が空っぽになる。**継続のためには、区切りが要る**。

> **夕方の10-15分で1日を閉じる。未完了タスクは「繰り越すか廃棄するか」を必ず問う。引き継ぎメモが今日と明日をつなぐ。**

## Daily Kanbanを運用面にする──5カラムで「今日の現場」を見える化する

Daily Kanban は本書で何度か言及してきたが、ここで本格的に扱う。

ファイル: `07_System/Dashboards/Daily-Kanban.md`

このファイルを Obsidian の Kanban プラグインで開くと、自動的にボードビューで表示される。**マークダウンファイルがそのままボードになる**。

### 5カラム構成

```
🔴 今日やる   | 🟡 作業中  | 🟢 完了  | 📦 今夜（19:00〜） | 🔵 余裕があれば
─────────── | ───────── | ─────── | ───────────── | ─────────────
朝の Top 3   | 進行中    | 終了   | 公開・投稿系    | 優先度低
```

### 各カラムの役割

| カラム | 役割 |
|-------|------|
| **🔴 今日やる** | 朝の Top 3 Priorities が入る。常に3つに絞る |
| **🟡 作業中** | 今着手しているタスク。同時1-2個まで |
| **🟢 完了** | 1日の達成記録。夕方に見て達成感を得る |
| **📦 今夜（19:00〜）** | 公開・投稿系の夜タスク。朝のタスクと混ぜない |
| **🔵 余裕があれば** | 時間があったらやる実験タスク。やらなくても OK |

5カラムにする理由は、**1日の時間帯と種類で区別する**ためだ。3カラム（TODO / Doing / Done）だと「今夜やる公開タスク」と「朝のうちにやる執筆タスク」が混ざる。混ざると、朝起きて Kanban を見たときに「**何から手をつけるか**」が判断できなくなる。

時間帯と種類を分けることで、**カラムを見れば自然と優先順位が分かる**状態にしている。

### 「余裕があれば」の心理学

5番目のカラム「🔵 余裕があれば」は、心理的に重要だ。

副業時間が限られていると、「**やりたいけど時間がない**」アイデアが毎日生まれる。これを「**今日やる**」に入れると、達成できない悔しさが残る。「**今夜**」に入れると、結局やらずに繰り越される。

「余裕があれば」に入れると、「**やらなくてOK、できたらラッキー**」というスタンスで残せる。心理的負担がゼロになる。やる気が起きた日にこのカラムから1つ拾えば、ボーナス感がある。

「**やらないことを許容するカラム**」を作ることが、副業を続けるコツだ。

### Kanban の絶対ルール

Daily Kanban を3ヶ月運用して、絶対ルールが3つに収束した。

**1. 「🔴 今日やる」は3つまで**

5つも6つも入れると、達成できずに毎日繰り越される。3つに絞ると、達成率が上がる。達成率が上がると、続けたくなる。

**2. 「🟡 作業中」は1-2個まで**

並行で3つ4つ着手すると、どれも中途半端になる。1つ終わらせてから次に進む。これが時間制約下では最も効率的。

**3. 「🟢 完了」を夕方に必ず見る**

達成したことを言語化して見る。これが副業の継続モチベーションを支える。`/daily-evening` の出力で「**今日完了したこと**」を読み上げる仕組みになっている。

> **Kanban の5カラムは「時間帯」と「種類」で区別する。「余裕があれば」を作ると、やらないことを許容できる。**

## COO briefingは「鮮度」を見る──staleness判定で部門の赤信号を先に潰す

朝の `/coo-briefing` の中心機能は**鮮度判定（staleness 判定）**だ。前節で触れたが、ここでもう少し深掘りする。

### 鮮度を見る理由

副業を続けていると、**徐々に放置されるデータソース**が出てくる。

- メールは毎日見ているつもりが、いつの間にか3日前のまま
- inner-coach（内省セッション）は2週間サボったまま
- infra-health（Vault健全性チェック）は1ヶ月前のまま
- skills update（スキルマップ）は2ヶ月前のまま

放置自体は悪くない。優先順位が低いから後回しになる。**問題は、放置されていることに気づかなくなる**ことだ。

`/coo-briefing` は朝のたびに「**何が古くなっているか**」を機械的に判定して、私に告げる。

### 鮮度判定の仕組み

判定対象とその閾値は次のとおりだ。

| データソース | Warning 閾値 | Critical 閾値 | 推奨アクション |
|------------|------------|-------------|---------------|
| trend.md | 当日分なし | 2日以上なし | `/neta-trend-daily` or `/team-content-sprint` |
| メールJSON | 3日以上前 | 7日以上前 | `/email-sync` |
| inner-coach session | 7日以上前 | 14日以上前 | `/inner-coach` |
| infra-health report | 7日以上前 | 14日以上前 | `/infra-health` |
| skills update | 30日以上前 | 60日以上前 | `/career-skills-update` |
| project-registry | 7日以上前 | 14日以上前 | `/rd-status` |

判定のアウトプットは部門ごとに 🔴 / 🟡 / 🟢 でまとめられる。Critical が1つでもある部門は 🔴、Warning だけなら 🟡、すべて閾値内なら 🟢。

### 「赤信号を先に潰す」原則

`/coo-briefing` の出力例を見せる。

```
■ COO Briefing 2026-05-19

📢 Content Marketing: 🟡
  ✅ trend.md (本日分あり)
  🟡 inner-coach session (10日前)
  → 推奨: 今週中に /inner-coach 実行

🔬 R&D Division: 🟢
  ✅ project-registry (3日前)

👤 Career & Comms: 🟡
  🟡 メールJSON (4日前)
  → 推奨: /email-sync を今日中に

⚙️ Tech Infrastructure: 🔴
  🔴 infra-health (16日前)
  → 推奨: 今すぐ /infra-health 実行

🔴 部門の対応を優先してください。
```

赤信号が出た部門を先に潰す。これが原則だ。**ピカピカに光るところを伸ばすより、暗いところを先に潰す方が、組織は持続する**。

これは製造業の制約管理（Theory of Constraints）の発想に近い。優秀なラインをさらに最適化するより、ボトルネックになっているラインを底上げする方が、全体スループットが上がる。AI 組織でも同じだ。

### 「全部 🟢 にしない」許容

逆説的だが、**全部 🟢 にしようとしすぎてはいけない**。

副業時間は有限だ。30分の朝時間で、すべての赤信号を潰そうとすると、肝心の優先タスク（Top 3 Priorities）に時間が残らない。

私のルールはこうだ。

- **🔴（Critical）は、その日のうちに対処**
- **🟡（Warning）は、その週のうちに対処**
- **🟢（Healthy）は、放置**

🟡 を1週間以内に対処できれば、🔴 への悪化は防げる。**赤信号化する前に手を打つ**運用なら、副業時間を圧迫せずに組織を健全に保てる。

> **COO briefing は赤信号を先に告げる。🔴 は当日、🟡 は週内、🟢 は放置。これで時間を圧迫せずに組織を保つ。**

## 持ち越しを前提に設計する──「毎日回る組織」は未完了を詰まらせない

ここまで読んで、こう思った人がいるかもしれない。「**でも、結局タスクは持ち越されますよね？**」

そのとおりだ。持ち越しは起きる。

正直に書くと、私の Daily Kanban には今もこういうタスクが残っている。

- **note 記事「claude-code-agent-skills」公開** — 5週持ち越し
- **ブログ @Doing 26件 CLI 一括移動** — 6週持ち越し

5週、6週。長い。

これは恥ずかしい数字に見えるかもしれない。だが、本章の中心テーマは「**持ち越しを失くす方法**」ではない。「**持ち越しを前提に設計する方法**」だ。

### なぜ持ち越しは起きるか

3週間以上持ち越されたタスクには、共通の特徴がある。

1. **着手のハードルが高い**: 「note 記事公開」は文章修正・画像生成・SEO 設定・公開ボタン押下の複数ステップが必要。1ステップ目から重い
2. **完了の喜びが少ない**: ブログ @Doing 26件移動は、終わっても誰も褒めてくれない。地味な掃除タスク
3. **緊急性が低い**: 公開しなくても誰も困らない。後回しにできる

これらが重なると、毎日「今日はやめておこう」が積み重なる。

### 持ち越し前提の3つの対処

持ち越しを失くそうとせず、**持ち越しが起きても組織が回る**ように設計する。私の運用には3つの工夫がある。

**1. 「📦 今夜」カラムに分ける**

公開・投稿系の重いタスクは Top 3 Priorities ではなく「📦 今夜」に入れる。これだと「**朝の Top 3 が達成できなかった**」感が出ない。夜にやれなかった日があっても、翌日に同じカラムで残せる。

**2. 「持ち越し週数」を可視化する**

私の Kanban のタスクには「**（X週持ち越し）**」と注記を付けている。「note 記事公開（5週持ち越し）」のように。

可視化すると、**どこかで決断が迫られる**。「5週持ち越し」を見ると「もうやめるか、今週中にやるか、どっちかにしよう」という気持ちになる。注記がないと、永遠に繰り越されてしまう。

**3. 月1回の「廃棄レビュー」**

月末に1度、Kanban の全タスクを見直して、3週以上持ち越されたものを**廃棄するか確定する週を決めるか**を判定する。やらないと決めたら堂々と廃棄する。

廃棄を許容する文化がないと、Kanban は**幽霊タスクの倉庫**になる。そして本当に新しい着手すべきタスクが埋もれる。

### 持ち越し率の目安

私の実測では、Daily Kanban のタスクのうち、**当日完了率は60-70%**、**週内完了率は85-90%**。残り10-15% は持ち越されるか廃棄される。

これが「**毎日回っている**」と私が言える数字だ。100% 完了は目指していない。

副業時間は不確定だ。本業が忙しい日、子どもが体調を崩した日、自分の集中が続かない日——必ず計画は崩れる。**崩れることを織り込んだワークフロー**だけが、長期的に続く。

> **持ち越しを失くそうとせず、持ち越しても組織が回る設計にする。「📦 今夜」カラム、持ち越し週数の可視化、月1回の廃棄レビュー——この3つで Kanban を生きた状態に保つ。**

## アンチパターン3つ

### NG1: 朝のコマンドを毎日叩く前提で設計する

**症状**:
- `/morning-sync` `/coo-briefing` `/daily` を全部叩かないと1日が始まらない設計
- 寝坊した日、子どもが熱を出した日に、朝のルーティンが崩壊する
- 「朝のコマンドを叩けなかった」罪悪感で副業を辞めたくなる

**処方箋**:
- 朝のコマンドは「**叩ければやる**」程度に位置付ける
- 叩けなかった日は、昼休みに `/daily` だけ叩く運用にする
- ルーティンは「**毎日同じ時間に同じ手順**」ではなく「**最低限の起動シーケンス**」と捉える

### NG2: Kanban を厳密に管理しようとする

**症状**:
- タスクの粒度を細かく分けすぎる（「note記事修正 → 画像生成 → SEO設定 → 公開」と4つに分ける）
- カラム移動を逐次行わないと気が済まない
- Kanban を更新する時間が、実作業の時間を超える

**処方箋**:
- タスクは粗くて良い（「note 記事公開」で1つ）
- カラム移動は1日2-3回まとめて行う
- Kanban は「**現場の見える化**」が目的、厳密管理が目的ではない

### NG3: 持ち越しタスクを無視して新タスクを足し続ける

**症状**:
- Kanban に古いタスクが溜まり、新タスクと混ざる
- どれが今日やるべきか分からなくなる
- 結局すべてが進まない

**処方箋**:
- 月1回の廃棄レビューを必ず行う
- 3週以上持ち越されたタスクは「**廃棄 / 今週着手 / 完全に切り出して別計画**」の3択
- 「いつかやる」は廃棄と同義。明確に判定する

## まとめ──設計は閉じた、運用が始まった

Part 3 の初章として、私の daily-workflow を全公開した。

時間配分の振り返り。

| フェーズ | 時間 | コマンド |
|---------|------|---------|
| 朝 | 8-13分 | `/morning-sync` → `/coo-briefing` → `/daily` |
| 日中 | 5分 × 1-2回 | `/daily-update` |
| 夕方 | 10-15分 | `/daily-evening` |
| **合計** | **20-35分** | — |

これが「**平日30分しかない副業時間**」で組織を回す型だ。

本章で扱った原則を振り返る。

1. **時間制約から設計する**: 30分しか取れない前提でワークフローを組む
2. **判断は朝に終わらせる**: 8-13分で1日の優先順位を確定、日中は実行だけ
3. **Kanban は現場の見える化**: 5カラムで時間帯と種類を区別、視覚化が継続を支える
4. **夕方に閉じる**: 未完了の繰越判断、引き継ぎメモで今日と明日をつなぐ
5. **赤信号を先に潰す**: COO briefing の staleness 判定で、放置を防ぐ
6. **持ち越しを前提に**: 完璧な完了を目指さず、崩れることを織り込む
7. **エネルギースコアで自分に合わせる**: ワークフローを自分のコンディションに適応させる

設計編で「**何を作るか**」を扱い、ここまでで「**1日をどう回すか**」を扱った。

だが、まだ残っている問題がある。**1本のコンテンツが、企画から世に出るまでの動線**だ。

朝に「今日は note 記事を書く」と決めて、daily-workflow に乗せた。だが、その記事はどんな企画フローで生まれ、どう執筆され、どう図解が付き、どうファクトチェックされ、どう公開されるのか。**1本の流れ**は、daily-workflow とは別の設計が要る。

次章 Ch.08 では、この **content-pipeline** を扱う。**時間軸（daily）** から **コンテンツ単位の動線（pipeline）** へ。視点を切り替えて、1本のコンテンツが世に出るまでを設計する。

> **1日の流れは整えた。次は、1本のコンテンツが世に出るまでの流れを扱う。**
