# content-pipeline──1本のコンテンツが世に出るまで

## 時間軸からコンテンツ単位の動線へ視点を切り替える

Ch.07 では、daily-workflow という時間軸の中で、1日をどう回すかを設計した。朝・日中・夕方の3フェーズで組織を起動・同期・終了する型を作った。

だが、daily-workflow だけでは説明しきれない問題がある。

朝に「**今日は note 記事を書く**」と Top 3 Priorities に入れたとする。daily-workflow はその「**今日のタスク**」として記事執筆を扱う。だが、その記事はどんな企画フローで生まれ、どうリサーチされ、どう図解が付き、どうファクトチェックされ、どう公開されて、どう告知されるのか——**1本のコンテンツが世に出るまでの流れ**は、daily-workflow とはまったく別の設計が必要だ。

ここで視点を切り替える。**時間軸（daily）**から**コンテンツ単位の動線（pipeline）**へ。

私はこの動線を **content-pipeline** と呼んでいる。1本のコンテンツが「**ネタ発見 → 企画 → リサーチ → 執筆 → 図解 → ファクトチェック → 公開 → 告知 → エンゲ確認**」という9段階を通過する経路だ。daily-workflow と直交する**2つ目の設計軸**として扱う。

実際、Ch.07 で私が告白した「**ブログ @Doing 26件 6週持ち越し**」——あれは、daily-workflow の問題ではなかった。毎日 Kanban を見て、Top 3 Priorities を立てて、夕方に閉じる——その運用は回っていた。それでも 26件が詰まった。

原因は**content-pipeline の設計不備**だった。執筆と公開の間にボトルネックがあり、どこで詰まっているかが見えなかった。気合いで解決しようとして、6週かかった。本当は流れを設計し直すべきだった。

本章では、3つの主要パイプライン——**Commission-Delivery**、**Blog**、**Note**——を並べて比較し、どこにボトルネックが生まれ、どこに ownership と品質保証を入れるべきかを設計する。中心軸は Commission-Delivery だ。Ch.06 で導入した、ai-publishing-house への外部委託モデルを「**標準形**」として描く。

時間管理ではなく、**流路設計**の章だ。

> **コンテンツ運用の詰まりは、時間管理ではなく流路設計の問題である。**

## content-pipeline の全体像──1本が世に出るまでの9段階

content-pipeline は9段階で構成される。

```
1. ネタ発見    （00_Memo / 03_Input/ideas/）
2. 企画       （Inbox処理、スコアリング、振り分け）
3. リサーチ    （Blog-Research / シグナル収集）
4. 執筆       （ドラフト生成、@Doing/ で進行）
5. 図解       （nanobanana / paperbanana）
6. ファクトチェック（factcheck）
7. 公開       （note:publish / wp-post.py）
8. 告知       （note:x-announce / X.com投稿）
9. エンゲ確認  （engagement-check / weekly-pick）
```

この9段階のうち、**どれも省略できない**。1つでも欠けると、後で必ず手戻りが発生する。

たとえば**ファクトチェックを飛ばした記事**は、公開後にミスが発見されて修正コミットを打つことになる。修正後の告知も歪む。読者の信頼も傷つく。1つ省いた代償は、後段で何倍にもなって返ってくる。

これは製造業の品質管理と同じだ。1工程の手抜きが、最終出荷の手戻りを生む。「**川の上流での不良は、川の下流で何倍にもなって現れる**」というやつだ。

逆に、9段階を全部手作業でやれば持続しない。9段階 × 1本あたり数時間 × 月10本 = それだけで副業時間が消える。だから**各段階に適切なツールとエージェントを割り当てる**。これが content-pipeline の設計だ。

ここで重要な視点を1つ。9段階はすべて**異なるツール/エージェントが担う**ことになるが、これらが孤立していては意味がない。**前段から後段へ、状態が引き継がれる**必要がある。

たとえば、執筆フェーズ（@Doing）で完成したドラフトは、ファクトチェック工程に「**ファクトチェック未実施**」とメタデータが立った状態で渡される。ファクトチェック完了後、メタデータが「**ファクトチェック済（YYYY-MM-DD Genspark）**」に更新される。公開工程は、このメタデータを見て「**未チェックなら警告、済なら通過**」を機械的に判定する。

この**メタデータの引き継ぎ**が、content-pipeline を支える背骨だ。Ch.02 で設計したフォルダ構造、Ch.04 で設計した File Ownership Rule が、この引き継ぎを物理的に保証している。

本章では、Commission-Delivery を中心軸として、Blog / Note という2つの具体的なパイプラインを比較する。それぞれの段階で「**誰が担うか**」「**どんなツールを使うか**」「**どこにメタデータを残すか**」を設計する。

> **9段階はどれも省略できない。各段階に適切な担い手を割り当て、メタデータで状態を引き継ぐ。これがパイプライン設計の本質だ。**

## Commission-Delivery を標準形にする──制作を流れとして分業する

3つのパイプラインの中で、私が **標準形** として位置付けているのが Commission-Delivery だ。Ch.06 で agent-teams の文脈で触れたが、ここで本格的に扱う。

### Commission-Delivery とは何か

ひとことで言うと、「**私（1人総合商社のCEO）が、ai-publishing-house（社外プロダクション）に制作を発注し、納品物を回収して公開する**」モデルだ。

```
私（CEO）
   ↓ /commission-content で発注書を作成
ai-publishing-house（外部制作チーム）
   ↓ 制作・編集レビュー
納品物（delivery-manifest.md と本文）
   ↓ /receive-delivery で回収
各チャネル @TODO/ に配置
   ↓ 私が最終確認・公開
公開
```

ここで重要なのは、**私がコンテンツを書かない**ことだ。私の役割は「**何を作るかを決め、納品物を見極め、公開判断する**」までに限定される。書く・編集する・図解を付ける——これらは ai-publishing-house の責務だ。

これは「**自社で全部作る商社**」ではなく「**良い発注先を持つ商社**」のモデルだ。本物の商社が、自社工場で全製品を生産しないのと同じ。**良い発注書を出し、良い納品物を見極め、良い流通を組む**——これが商社の本質的な仕事だ。

### Commission-Delivery の4段階

実装上、Commission-Delivery は4段階に分かれる。

**1. 発注書作成（Commission）**

`/commission-content` を叩くと、その日のトレンドデータ、シグナル、Content Seeds を収集して、チャネル別にスコアリングしたうえで**発注書**が生成される。

発注書には以下が記述される。

```markdown
# Commission: YYYYMMDD-HHMMSS-[topic]

## Channel
- target: note-aij

## Topic
- [テーマ]

## Persona & Tone
- channels/note-ai-journal.md から継承

## Source Material
- trend.md の該当ネタへのリンク
- 関連する Research ファイル

## Quality Requirements
- 文字数: 3,000-5,000字
- ファクトチェック必須
- インフォグラフィック生成必須

## Delivery
- 形式: マークダウン + サマリー画像
- 期限: 2026-MM-DD

## 報酬・条件
- 公開後の編集権はCEO（私）が保持
```

これを `ai-publishing-house/09_Commissions/@Queue/` に送付する。「**社外発注書を出す**」感覚だ。

**2. 制作（Production）**

ai-publishing-house 側で、発注書を受領した制作チームが動く。これは別の Claude Code プロジェクトで動いている。担当エージェントが企画・リサーチ・執筆・編集レビューまでを担う。

ここで重要なのは、**私の Vault（obsidian-1）と ai-publishing-house は完全に別プロジェクト**であることだ。私の作業を妨げず、独立して制作が進む。プロジェクトが分離していることで、**ファイル衝突のリスクがゼロ**になる。

**3. 納品（Delivery）**

制作が完了すると、ai-publishing-house は `10_Deliveries/[commission-key]/` に以下を配置する。

- `delivery-manifest.md`（納品書、編集レビュー結果含む）
- 本文ファイル（マークダウン）
- 図解・画像ファイル
- メタデータ（ファクトチェック状況、推奨公開タイミング）

`delivery-manifest.md` には **Editor Review Result** が必ず記載される。

```
Editor Review Result: APPROVED
- 編集ポイント: 3件指摘、すべて反映済み
- ファクトチェック: 済（Genspark cross_check、修正2点反映）
- インフォグラフィック: 生成済み
- 推奨公開: 2026-05-22（金曜朝）
```

**4. 回収（Receive）**

私が `/receive-delivery` を叩くと、`10_Deliveries/` をスキャンし、各 commission-key の delivery-manifest.md を確認したうえで、APPROVED の納品物を各チャネルの `@TODO/` に配置する。

`REVISION_NEEDED` の納品物は配置されず、リストアップだけされる。私が判断して「**もう一度発注し直す**」か「**手で修正する**」を決める。

### なぜ Commission-Delivery が「標準形」か

この4段階モデルが、なぜ私の中で標準形になったか。理由は3つある。

**理由1: 責任境界が明確**

「**書く人**（ai-publishing-house）」と「**公開する人**（私）」が明確に分かれる。書き手が公開判断もすると、自分の原稿に甘くなる。分離すると、**第三者の目で見られる**ようになる。

**理由2: 私の時間が「判断」に集中する**

書く時間が消える代わりに、「**この発注書で良いか**」「**この納品物で良いか**」を判断する時間に変わる。判断は早い。書くより数倍早い。私の30分が「**書く30分**」ではなく「**判断する30分**」になる。

**理由3: 並列性が出る**

ai-publishing-house が制作している間、私は別の仕事ができる。これが daily-workflow と組み合わさると、強い。朝に発注書を3本出して、夜に納品物を回収する。日中は本業に集中する。**待っている時間が私の自由時間になる**。

### Commission-Delivery が向くケース・向かないケース

すべてのコンテンツを Commission-Delivery にすべきかというと、そうではない。

| 向くケース | 向かないケース |
|----------|--------------|
| 1記事 1,500字以上 | 単発の短文ツイート |
| トーンが定型化されている（note週刊AI検証等） | 私の生体験記事（体調・気分が出るもの） |
| 公開タイミングが柔軟（数日先までOK） | 速報性が要る（リアルタイム反応） |
| 図解・ファクトチェックが必要 | 単純な引用RT |

X.com の単発ツイートを Commission-Delivery にすると、発注 → 制作 → 納品の往復で1日以上かかる。速報性が消える。これは Commission-Delivery の弱点だ。

ブログのような長文記事、noteの実機検証記事——こうした**型化された中長文コンテンツ**で Commission-Delivery が最も効く。

### 私の運用比率

執筆時点で、私のコンテンツ制作の約 **60%** が Commission-Delivery を経由している。残り 40% は Blog パイプライン（独自の段取り）と Note パイプライン（週刊運用）、それと手書きの X.com 投稿だ。

Commission-Delivery 比率をもっと上げたいか、と聞かれると、現状の 60% が適度だと思う。**100%を発注に回すと、自分の手触りが消える**。執筆という行為が、書き手にとっての思考の場でもあるからだ。完全に切り離すと、書く力そのものが衰える。

「**判断と編集**は自分でやる、**書く**の主力は発注に出す**」——このバランスが、1人総合商社の最適解だと考えている。

> **Commission-Delivery の本質は、自社で書かずに発注書と納品物の往復で回す商社モデル。私の役割は「判断する人」になる。**

## Blog パイプライン──量産系導線は、段取りを固定して詰まりを減らす

Blog パイプライン（bhrtaym-blog.com 向け）は、私が長年使ってきた**独自の段取り**を Skill 化したものだ。Commission-Delivery とは別物として、ここで扱う。

### Blog の6コマンド連鎖

```
/blog00-planning           → 週次執筆計画、TOP 5-10提案
   ↓
/blog01-generate-article   → 記事生成（指定キー）
   ↓
/blog02-generate-seo       → SEO情報生成
   ↓
/blog03-generate-social    → SNS投稿文生成
   ↓
/blog04-generate-thumnail  → サムネイル画像プロンプト生成
   ↓
/blog05-archive            → リサーチ素材アーカイブ
   ↓
wp-post.py                 → WordPress 投稿
```

6つの Skill を順番に叩く。Ch.06 で「**逐次依存のパイプラインは Teams 化不可**」と書いたが、Blog パイプラインがその典型例だ。各 Skill が前の出力を入力にする。並列化できない。

### なぜ「段取りを固定」するか

このパイプラインの強みは、**段取りが固定**されていることだ。

逆に言うと、毎回「**この記事はSEOを先にやろうか、サムネを後回しにしようか**」と考え始めると、必ず段取りが崩れる。段取りが崩れると、SEO設定を忘れたまま公開してしまう、サムネを後付けで急いで作る、といったミスが起きる。

私は最初、Blog パイプラインを「**柔軟に**」運用しようとした。「今日は記事だけ、SEOは明日」「サムネは公開当日に」のような。1ヶ月で破綻した。**柔軟性は持ち越しを生む**。

そこで段取りを固定した。記事生成 → SEO → SNS文 → サムネ → アーカイブ → 投稿。この順番を変えない。記事生成だけ終わって SEO に進まない場合、その記事は「**未完成**」として扱い、@Doing/ に置いたままにする。

これで「**SEO 未設定で公開**」は構造的に起こらなくなった。

### Blog @Doing 26件 6週持ち越しの正体

Ch.07 で告白した「**ブログ @Doing 26件 6週持ち越し**」は、まさにこの Blog パイプラインの詰まりだった。

実態を明かすと、26件のうち多くが「**記事生成は終わったが SEO/SNS/サムネが未着手**」の状態だった。/blog01 までは叩いたが、/blog02 以降を叩く時間が取れず、@Doing/ に滞留していた。

これは段取りの問題ではなく、**WIP（Work In Progress）の問題**だ。同時に進めている記事が多すぎた。本来 WIP の上限を3-5本に絞るべきところ、26本まで膨張させた。

WIP制御については H2-8 で詳しく扱うが、Blog パイプラインに固有の対策として、`/blog00-planning` で**新規追加の上限**を週3本にしている。これを超える記事は、企画段階で却下する。「**詰まらせない**」を入口で防ぐ。

> **Blog パイプラインは段取りを固定する。柔軟性は持ち越しを生む。新規追加の上限を入口で絞る。**

## Note パイプライン──週刊運用は、公開前後の確認まで含めて完結させる

Note パイプライン（note.com / AI検証ジャーナル）は、**週刊運用**を前提に設計されている。

### Note の4コマンド連鎖

```
/note:receive-draft        → Xserverからドラフト取得（外部執筆）
   ↓
/factcheck                 → ファクトチェック実行
   ↓
/note:publish              → note.comに下書き保存
   ↓ （公開後）
/note:x-announce           → X.com告知投稿生成
   ↓ （数日後）
/note:engagement-check     → メトリクス収集
```

Blog より段数が少ない。理由は、note には記事の SEO 設定やカスタムサムネ（記事サムネイル）の機能が標準で備わっており、**プラットフォーム側で完結する処理は私の Skill 側で重複させない**設計にしているからだ。Blog の WordPress 側では別途 SEO プラグインやサムネ生成が必要なので段数が増えるが、note は記事画面の中で完結する。**プラットフォームの特性に合わせてパイプラインを短くする**。

### 週刊運用の意味

note は **毎週金曜公開** という固定リズムで回している。これは Ch.05 で扱った投資配分（note 40%、Primary）の運用ルールでもある。

固定リズムにすると、3つの効果がある。

**1. 読者の期待値が形成される**: 「金曜に新記事が出る」と読者が知ると、ブックマークしてくれる。リズムが信頼を作る。

**2. 制作スケジュールが組める**: 月曜にネタ確定、火-水で発注 or 執筆、木でファクトチェック、金で公開——という1週間の流れが固定できる。

**3. 公開後の動線も組める**: 金曜公開なら、土日のうちに X.com で告知、月曜にエンゲ確認、水曜に振り返り——という公開後ルーティンも組める。

毎回違うタイミングで公開すると、これらが全部崩れる。**固定リズムが、パイプラインを支える**。

### 公開前後の確認まで含めて「完結」とする

Note パイプラインで重要なのは、`/note:publish` で**終わらない**ことだ。

公開しただけでは「**完結**」とは呼ばない。次の3つまで含めて1サイクルとする。

1. **/note:x-announce**: 公開直後（数時間以内）に X.com で告知投稿を生成
2. **/note:engagement-check**: 数日後にメトリクス（PV、スキ、購入数）を収集
3. **次週企画への反映**: メトリクスから次週のテーマを調整

最も忘れがちなのが 3 だ。前週のエンゲ結果を見ずに次週の企画を立てると、毎週独立した記事になってしまう。**前週の反応が次週の選択を変える**という、フィードバックループが回らない。

私はこれを習慣化するために、`/note:weekly-pick`（週刊ピックアップ）の中で、前週のエンゲ結果を自動的に参照するようにしている。**フィードバックループをパイプラインに組み込む**——これが Note パイプラインで一番効いた工夫だ。

> **Note パイプラインは公開で終わらせず、告知・エンゲ確認・次週反映までを1サイクルにする。フィードバックループがパイプラインを支える。**

## 品質保証は後付けしない──factcheck と図解生成をパイプラインに埋め込む

3パイプラインに共通する「**横断テーマ**」が、品質保証だ。

これらは「**後付け**」してはいけない。パイプラインの**特定段階に埋め込む**設計が要る。

### factcheck の埋め込み位置

ファクトチェック必須ルールは、本書全体の**絶対ルール**として扱っている。公開前のコンテンツ（ブログ・note・Zenn）には、ファクトチェック実施状況をメタデータに必ず記載する。

埋め込み位置はパイプラインごとに異なる。

| パイプライン | factcheck 位置 |
|------------|--------------|
| Commission-Delivery | ai-publishing-house 側の制作中（delivery-manifest.md に結果記載） |
| Blog | /blog01 直後、/blog02 の前 |
| Note | /note:receive-draft 後、/note:publish 前 |

ツールは `/factcheck`（Genspark の `gsk task cross_check` 経由）が標準だ。

メタデータ記載例:

```yaml
ファクトチェック: 済（2026-05-19 Genspark / [[20260519_xxx-factcheck]]）
ファクトチェック修正: 済（2026-05-19 リンク2件修正、数値1件追記）
```

「**ファクトチェック: 未**」のまま公開しようとすると、`/note:publish` や `wp-post.py` が**警告を出す**。警告を見たうえで「了承して公開」もできるが、デフォルトは未チェック公開を防ぐ設計だ。

### 図解生成の埋め込み

図解は、コンテンツの理解を助ける重要な要素だ。だが、執筆中に「**ついでに図も作っておこう**」とすると、必ず後回しになる。

そこで、各パイプラインに**図解生成のトリガーポイント**を設けている。

**1. 記事内図解の自動検出**

`/blog01-generate-article` や Commission-Delivery の納品物には、**図解候補の自動検出**が組み込まれている。記事をスキャンして「**3ステップ以上の手順**」「**3項目以上の比較**」「**システム構成の説明**」などのパターンを検出し、図解候補としてリストアップする。

**2. サマリーインフォグラフィックの自動生成**

ブログ・note の記事執筆完了後、`/nanobanana:infographic [記事ファイル]` で**記事全体を要約したインフォグラフィック**を自動生成する。これが SNS シェア時の主役画像になる。

**3. 学術図表が要るときは PaperBanana**

ワークフロー・パイプライン・アーキテクチャ・統計グラフ・概念図——これらの**プロ品質図解**が必要なときは、`/paperbanana-generate --type [タイプ] [説明]` を使う。Ch.06 で扱った5エージェントパイプラインだ。

### 品質保証を「最後」に置かない

最も避けたいのは、**品質保証を公開直前に詰め込む**ことだ。

```
× 悪い設計
執筆 → 図解 → ファクトチェック → 公開（全部直前）
  └ どこかで時間切れになり、品質保証が省略される

○ 良い設計
執筆 → ファクトチェック（中段に固定）→ 図解（中段に固定）→ 公開
  └ 品質保証が独立した段階として確保される
```

私は最初、悪い設計でやっていた。公開当日に「**ファクトチェックを忘れていた**」「**サマリー画像を作ってない**」と気づいて慌てる、を繰り返した。

中段に固定した後、こうした事故はゼロになった。「**品質保証は最後ではなく、流れの中段**」——これが鉄則だ。

> **品質保証は後付けしない。factcheck はパイプラインの中段に固定、図解は記事執筆完了後に自動トリガー、PaperBananaで学術品質まで対応する。**

## 所有権とステータスで流れを壊さない──@TODO / @Doing / @Completed を作業場にする

content-pipeline を物理的に支えるのが、**フォルダ構造によるステータス管理**だ。

各チャネルは次の3フォルダを持つ。

```
05_Output/Areas/Content-Creation/[Channel]/
├── @TODO/        ← 着手前のドラフト
├── @Doing/       ← 進行中
└── @Completed/   ← 公開済み
```

これは Ch.02 で扱ったフォルダ設計、Ch.04 / Ch.05 で扱った File Ownership Rule の応用だ。

### ステータスとフォルダの一致

content-pipeline の各段階で、コンテンツファイルは次のように移動する。

```
ネタ発見 → 03_Input/ideas/                  （まだコンテンツ化していない）
   ↓ 企画
@TODO/ に配置                                （これから書く / 発注する）
   ↓ 着手
@Doing/ へ移動                                （執筆中・編集中）
   ↓ 公開
@Completed/ へ移動                            （公開済み）
```

このフォルダ移動が、そのままコンテンツの**ステータス**になる。`@Doing/` のファイル数 = 現在進行中の記事数。`@Completed/` のファイル数 = 公開済み記事数。**ファイルシステムが、ダッシュボードになる**。

ステータス管理ツール（Notion、Trello、Asana 等）を別に持つと、二重管理が発生する。フォルダだけで管理すれば、二重管理がない。「**コンテンツファイル＝ステータス**」がシンプルさを支える。

### 所有権の埋め込み

Ch.05 で扱った Output Path 排他制御も、ここで効く。

| フォルダ | 所有エージェント |
|---------|----------------|
| `Blog-Writing/@Doing/` | blog-aif |
| `Note-AI-Journal/@TODO/` `@Doing/` `@Completed/` | note-aij |
| `Libecity/@TODO/` | libecity-main |
| `X-Twitter/@TODO/` | x-ai-lifestyle |

所有エージェント以外は、これらのフォルダに書き込めない。COO も、別の channel-agent も、手を出せない。これによって、**パイプラインの各段階で誰が責任を持つかが、フォルダレベルで保証される**。

### フォルダ間移動のルール

ファイル移動には3つのルールがある。

**1. 自動移動はしない（基本）**

書込みが排他制御されていても、フォルダ間の**移動**は手動が基本だ。私が「これは公開した」と判断したら、`mv` コマンドや Obsidian の UI で `@Doing` → `@Completed` に動かす。

自動移動を組み込むと、「**どの時点で完了とみなすか**」の判断が機械化されてしまう。実際には「**公開はしたが告知はまだ**」「**告知もしたがエンゲ確認は未**」のように、グラデーションがある。グラデーションを機械化すると、半端な状態で `@Completed` に移って忘れられる。

**2. 移動時にメタデータ更新を必ず行う**

`@Doing → @Completed` への移動時には、ファイルのメタデータに**公開日**と**公開URL**を必ず追記する。これがないと「**完了したフォルダにいるが、実際に公開されたかは不明**」というゾンビが生まれる。

**3. @Completed から逆流させない**

一度 `@Completed` に入ったファイルは、原則として戻さない。修正が必要なら、別のコピーを作って `@Doing` で扱う。これは Git の `git revert` と似た発想で、**履歴を消さない**ことを優先する。

> **content-pipeline はフォルダ構造とステータスを一致させ、所有エージェントで責任を保証する。手動移動を基本にしてグラデーションを尊重する。**

## 詰まりは根性では解消しない──26件持ち越しから学んだWIP制御の原則

Ch.07 で告白した「**ブログ @Doing 26件 6週持ち越し**」は、本章で原則化するべき題材だ。

この詰まりは、努力や気合いで解消するべきものではない。**設計の問題**だ。

### なぜ詰まったか

詰まりの原因を分解すると3つに分かれる。

**1. 入口で絞っていなかった**

新しい記事ネタを思いつくたびに、`/blog00-planning` で承認していた。これだと、思いつくたびに @Doing に入ってくる。**入口の流量を制御していなかった**。

**2. 中段で停滞していた**

`/blog01-generate-article` で記事生成までは進むが、その後の `/blog02-generate-seo` `/blog03-generate-social` `/blog04-generate-thumnail` を叩く時間が取れない。中段の SEO/SNS/サムネのステップで止まっていた。これが「**未完成の記事が@Doing に滞留**」を生んだ。

**3. 出口の閉塞を放置していた**

`wp-post.py` を叩いて WordPress に投稿するべきタイミングを逃すと、公開せずに置きっぱなしになる。出口が閉塞していると、@Doing から @Completed への移動が止まる。**出口の詰まりが、上流に逆流する**。

### 製造業のWIP制御を見本にする

私の本業は製造業エンジニアだ。製造ラインで詰まりが起きたら、対処法は決まっている。

**Work In Progress（WIP）の上限を設定する**。

ライン上に同時に存在できる仕掛品の数を、物理的に制限する。上限を超えたら、新規投入を止める。これが**かんばん方式**だ。詰まりを防ぐ手法として、製造業で最も体系化され広く普及した運用の一つだ。

これを content-pipeline に持ち込んだ。

```
@Doing/ の WIP 上限:
  - Blog:  最大 5本（同時進行）
  - Note:  最大 3本
  - X.com: 最大 10本（短文だから上限緩め）
```

上限に達したら、`/blog00-planning` 等の Skill が**新規企画の受付を停止**する。「**今は @Doing が満杯です。1本完成させてから次を受けます**」と返す。

これだけで、26件は3週間で 5本まで減った。**入口を絞った効果**だ。

### WIP制御の3つの原則

WIP制御を運用するための3原則がある。

**原則1: 上限は「やり切れる数」で決める**

「**やりたい数**」ではない。「**今の自分の時間と集中力で、確実に完成させられる数**」だ。私の場合、Blog は本業の合間に進めるので、同時 5本が上限。Note は週末に集中するので、同時 3本（実質週1で1本完成）。

**原則2: 上限を超えた新規ネタは「保留リスト」に置く**

「**やらない**」ではない。「**今は受けない**」だ。新規ネタは `03_Input/Blog-Research/` の **保留リスト** に積んでおく。@Doing に空きが出たら、保留リストから取り込む。

**原則3: 出口の詰まりを最優先で解消する**

@Doing が詰まる原因の多くは、出口（公開段階）の閉塞だ。「**公開する時間を取れていない**」がボトルネック。これを解消するために、毎週金曜の夕方を「**公開専用時間**」として固定した。執筆も発注も入れない。**公開だけをやる時間**だ。

### WIP制御は副業に特に効く

WIP制御は、本業フルタイムの社員には「制約が多い」と感じるかもしれない。「**たくさん同時進行できる方が効率的では**」と思うかもしれない。

だが、副業時間が限られている人ほど、WIP制御は効く。

理由は単純で、**副業の時間制約は変えられない**からだ。投入できる時間が一定なら、同時進行を増やしても1本あたりの完成時間は伸びるだけ。それなら同時進行を減らして、1本ずつ完成させる方が、公開ペースが安定する。

製造業の WIP制御は、ライン速度を上げるためではなく、**詰まりを防ぐため**にある。1人総合商社も同じだ。**速く動かすため**ではなく、**詰まらせないため**に WIP制御を入れる。

> **詰まりは根性で解消しない。WIP制御を入口に設置し、上限を超えたら新規受付を止める。出口の閉塞を最優先で解消する。これが製造業から学んだ流路設計の原則だ。**

## アンチパターン3つ

### NG1: 段階を飛ばす

**症状**:
- ファクトチェックを「今回は急ぎだから」と飛ばす
- 図解を「後でいい」と公開後に回す
- リサーチを軽視して執筆に直行する

**処方箋**:
- 9段階のうち、どれも省略可能とみなさない
- 各段階に**メタデータでステータスを残す**（「factcheck: 未/済」等）
- 段階を飛ばした記事は、必ず後段で手戻りが発生することを認識する

### NG2: 段取りを毎回変える

**症状**:
- 「今日は SEO を先にやろう」「サムネを後回しに」と毎回判断する
- パイプラインの順序が記事ごとにバラバラ
- 公開時に「あれを忘れた」が頻発する

**処方箋**:
- パイプラインの段取りを**固定する**
- 変更したいときは、Skill の定義を書き換える（運用ではなく設計の変更）
- 段取り固定が、品質を保証する

### NG3: WIPの上限を設けない

**症状**:
- 思いついたネタを次々と @Doing に投入する
- @Doing が10本、20本と膨張する
- どれも中途半端で、何も公開できない

**処方箋**:
- パイプラインごとに WIP 上限を設定する（Blog 5、Note 3 等）
- 上限を超えたら新規ネタは保留リストに積む
- 出口の閉塞を最優先で解消する（公開専用時間を週次で確保）

## まとめ──pipelineを設計したら、次は自動起動

content-pipeline は、daily-workflow と直交する**2つ目の設計軸**だ。

時間軸（daily）で1日の運用を回し、コンテンツ軸（pipeline）で1本の動線を設計する。この2軸が揃って初めて、1人総合商社は**安定して公開し続ける**組織になる。

本章で扱った原則を振り返る。

1. **9段階パイプライン**: ネタ発見〜エンゲ確認までを段階化、省略しない
2. **Commission-Delivery を標準形に**: 書く・編集する人と公開判断する人を分離
3. **Blog は段取り固定**: 柔軟性は持ち越しを生む
4. **Note は週刊運用で完結**: 公開後のフィードバックループまで含める
5. **品質保証は中段に固定**: factcheck と図解生成を後付けしない
6. **フォルダ＝ステータス**: @TODO / @Doing / @Completed で状態を表現
7. **WIP制御**: 入口で絞る、上限を超えたら受けない、出口を最優先で解消
8. **製造業の原理を移植**: 副業ほど WIP制御が効く

これで、コンテンツが世に出るまでの動線は設計できた。

だが、ここまでの content-pipeline は**手動起動が前提**だ。私が `/commission-content` を叩く。`/factcheck` を叩く。`/note:publish` を叩く。Skill 化して順番が決まっているから速いが、**起動が人依存**だ。

人依存の何が問題か。**人間は叩き忘れる**。

毎週金曜の note 公開を、月曜のうちに発注し忘れる。`/note:engagement-check` を叩き忘れて、前週のメトリクスが取れない。`/factcheck` を叩く前に間違って `/note:publish` を叩いてしまう。**人間の不完全さが、せっかく設計したパイプラインを壊す**。

ここで必要になるのが、**hooks** ——イベント駆動の自動起動だ。「**Daily ノートを保存したら、自動でメタデータを抽出する**」「**Commission を作ったら、自動で対応するシグナルを Archived に動かす**」「**特定のフォルダにファイルが配置されたら、自動で次の Skill を呼び出す**」——こうした**コンテキストスイッチの部分自動化**が、人間の叩き忘れを構造的に防ぐ。

次章 Ch.09 では、Claude Code の **hooks** を扱う。パイプラインを**手動起動から半自動起動へ**進化させる仕組みだ。content-pipeline を「**設計しただけ**」から「**自動で回り始める**」へ。最後の仕上げに入る。

> **パイプラインを設計したら、次は自動起動の仕組みが要る。人間の叩き忘れを構造的に防ぐのが hooks の役割だ。**
