# hooks──手動起動から半自動起動へ

## hooksは「便利機能」ではなく、叩き忘れ対策の基盤である

Ch.08 の終わりで、私はこう書いた。

> 人間の叩き忘れを構造的に防ぐのが hooks の役割だ。

これは単なる操作の自動化ではない。

1人総合商社の運用で本当に痛いのは、**知識不足ではなく、「分かっていたのに、その場でやらなかった**」ことだ。

- プロンプトを記録し忘れる
- 途中の判断を残し忘れる
- ファイル編集の意図をログ化し忘れる
- タスクが終わったのに振り返りを回し忘れる

こうした抜け漏れは、個人の気合いで潰そうとしても潰せない。気合いは消耗品だ。**イベントに反応する仕組み**で潰すしかない。

hooks は、そのための装置だ。Skill やコマンドを「**必要になったら思い出して叩く**」運用から、セッション開始・プロンプト送信・ツール実行前後・終了時といった**節目で自動的に処理を差し込む運用**へ切り替える。

これは便利機能の追加ではない。Ch.04 で組織を作り、Ch.05 で channel-agent を切り出し、Ch.06 で agent-teams で並列実行し、Ch.07 で daily-workflow を回し、Ch.08 で content-pipeline を整えてきた——その**Part 3 の仕上げ**として、運用を「**人間依存**」から「**構造依存**」へ移す一手だ。

本章では、私が実際に使っている hooks を材料に、半自動起動の設計図を示す。

> **hooks は便利機能ではなく、人依存から構造依存へ運用を移す装置である。**

---

## 全部は触らない──私がまず使う5つのhookと役割分担

Claude Code には複数の hook イベントがある。

| hookイベント | 発火タイミング |
|------------|--------------|
| **UserPromptSubmit** | ユーザーがプロンプトを送信した瞬間 |
| **PreToolUse** | Claude がツールを呼ぼうとした直前 |
| **PostToolUse** | ツール実行が完了した直後 |
| **SessionStart** | セッション開始時 |
| **Stop** | セッション終了時 |
| **SubagentStop** | サブエージェント終了時 |
| **PreCompact** | コンテキスト圧縮の直前 |
| **Notification** | 通知発火時 |

8つある。全部に hook を設定したい衝動に駆られるが、最初は**5つに絞る**のが正解だ。

私が常用している hook はこの5つだ。

| hook | スクリプト | 目的 |
|------|----------|------|
| UserPromptSubmit | english-learning-reminder.sh | 日本語入力時に英語学習ブロックを要求 |
| PreToolUse (Write\|Edit) | teammate-idle-check.sh | 並列セッションのアイドル検知 |
| PostToolUse (TaskUpdate) | task-completed-check.sh | タスク完了時の振り返り発火 |
| PostToolUse (Write\|Edit) | log-file-edit.sh | ファイル編集ログ記録 |
| Stop | log-session-stop.sh | セッション終了時の振り返り保存 |

「**PreCompact**」「**Notification**」「**SubagentStop**」「**SessionStart**」は最初は設定していない。必要になったら追加する。

### なぜ5つに絞るか

hook は「**便利だから増やす**」と必ず後悔する。理由は3つある。

**1. 発火タイミングが重なって動作が読めなくなる**

PreToolUse と PostToolUse の両方に hook を設定し、さらに UserPromptSubmit にも、SessionStart にも——となると、1回の Claude 呼び出しで複数 hook が連鎖発火する。**どの hook がどんな順番で動いたか**が、ログを見ても分からなくなる。

**2. デバッグ不能になる**

hook の中でエラーが起きると、Claude の動きが**サイレントに変わる**ことがある。「**今日はなぜか Claude が遅い**」「**書き込みが時々失敗する**」——原因が hook にあると、特定に何時間もかかる。設定数が少ないほど、原因特定が早い。

**3. 「やりすぎ自動化」が運用を硬直化する**

すべての行動に自動処理を差し込むと、**例外的な動き方ができなくなる**。「今日は急ぎだから振り返りスキップしたい」「このセッションだけログを抑制したい」——こういう柔軟性が、自動化過剰だと失われる。

5つに絞る理由は、運用を**シンプル・デバッグ可能・柔軟**に保つためだ。

### 5つの役割分担

5つの hook は次のように役割を分担している。

```
入力の質を上げる      → UserPromptSubmit (english-learning-reminder)
出力の事故を防ぐ      → PreToolUse        (teammate-idle-check)
完了時の振り返り      → PostToolUse       (task-completed-check)
編集の証跡を残す      → PostToolUse       (log-file-edit)
セッションを記憶する  → Stop              (log-session-stop)
```

入力 → 出力前 → 完了 → 記録 → セッション終了。**1回のセッションの流れに沿って、節目に hook を配置**している。これがバラバラだと運用が壊れる。

> **hook は5つに絞る。発火タイミングが重なる設計は、デバッグ不能と運用硬直化を生む。**

## UserPromptSubmit──入力の瞬間に、行動の質を底上げする

最初に紹介するのが **UserPromptSubmit** だ。これはユーザーがプロンプトを送信した瞬間に発火する。

### english-learning-reminder.sh の役割

私はこの hook に `english-learning-reminder.sh` というスクリプトを割り当てている。動作はこうだ。

1. ユーザーの入力テキストを受け取る
2. 日本語が含まれているか判定（正規表現で「ひらがな・カタカナ・漢字」を検出）
3. 日本語入力なら、Claude への「**追加指示**」を注入: 「**応答冒頭に英語翻訳ブロック（📝 English Translation / 💡 Point / 🔄 Alternative）を必ず出力**」
4. 英語入力なら、別の指示を注入: 「**応答冒頭に英文添削ブロック（✅ Your English / 📝 More Natural / 💡 Tip）を必ず出力**」

これにより、私が普段の作業で Claude と日本語で会話しているだけで、**毎回の応答が英語学習教材**になる。

意図的な学習時間を取らなくても、**日常の作業フローに学習が埋め込まれる**。これが UserPromptSubmit hook の威力だ。

### なぜ「入力の瞬間」が重要か

英語学習を「習慣化したい」と思うとき、多くの人は「**毎朝30分英語の勉強**」のような時間ブロックを作る。私もやった。続かなかった。本業と副業の合間に、純粋な学習時間を確保するのは難しい。

そこで発想を変えた。「**学習時間を作る**」のではなく、「**既存の活動を学習機会に変える**」。

Claude Code を使う時間は毎日ある。本業のコード、副業の執筆、雑談——全部 Claude と日本語で対話する。ここに hook で英語学習を差し込めば、**学習時間ゼロで学習が進む**。

これは UserPromptSubmit でないとできない。プロンプト送信のたびに発火するから、**毎回の応答**が学習機会になる。Skill だと「叩いた時だけ」、Agent だと「呼ばれた時だけ」。hook だけが「**全プロンプト**」をフックできる。

### 入力フックの3つの活用パターン

UserPromptSubmit は学習以外にも使える。私が試したパターンは3つだ。

**1. 学習埋め込み**: 英語学習リマインダー（採用中）

**2. プロンプト品質チェック**: 「曖昧な指示を検出して、明確化を促す」hook を試した。「これ作って」と書くと「**何を作りますか? 既存のどのファイルを参照しますか?**」と Claude が必ず聞き返すようになる。

**3. コンテキスト注入**: 「現在のタスクリスト」「直近の Daily ノート」を毎プロンプトに自動添付。Claude が**毎回最新の状況**を踏まえて返答する。

3つ目はトークン消費が増えるので、私は採用していない。1つ目（学習埋め込み）が継続効果が最も大きい。

> **UserPromptSubmit は「入力の瞬間」に介入する装置。日常の作業に学習や品質チェックを埋め込める。**

## PreToolUse──書く前に止めることで、チーム運用の事故を減らす

次が **PreToolUse** だ。Claude がツール（Write、Edit、Bash 等）を呼ぼうとした**直前**に発火する。

### teammate-idle-check.sh の役割

私はこの hook に、`teammate-idle-check.sh` というスクリプトを割り当てている。対象ツールは `Write|Edit`。

動作はこうだ。

1. Write または Edit が呼ばれそうになる
2. hook が発火し、現在実行中の**他のセッション**を確認
3. 同じファイルを別セッションが触っていないか判定
4. 触っている場合: 警告を表示、ファイル衝突リスクを Claude に通知
5. 触っていない場合: 通常通り処理続行

Ch.06 で扱った agent-teams の並列実行と、Ch.05 で扱った File Ownership Rule の**最終的な物理保障**になる。

### 「書く前に止める」発想

PreToolUse の強みは、「**書く前に止める**」ことだ。

PostToolUse（書いた後に何かする）では、すでに書き込み事故が起きている。**書いた後で気づいても遅い**。PreToolUse なら、書く前に判定して**書き込みを止めることもできる**。

たとえば、誤って `00_Memo/` 配下に書き込もうとしたとき、PreToolUse hook で「**00_Memo/ はユーザー専用です**」と止められる。Ch.04 で「00_Memo/ は絶対禁止」と所有権ルールを書いたが、それを**物理的に強制する**のが PreToolUse の役割だ。

### PreToolUse の3つの典型用途

PreToolUse は次の3つに使うのが定番だ。

**1. 危険操作の事前ブロック**: `rm -rf`、`git push --force` 等を Bash で叩こうとしたら止める。

**2. ファイル所有権の検証**: 書き込み先フォルダが、エージェントの所有範囲か確認する。

**3. 並列実行時の衝突回避**: 上記の teammate-idle-check のように、別セッションとの干渉を防ぐ。

私は3つ目だけ採用している。1つ目と2つ目は Claude が CLAUDE.md と Skill の指示で守るので、hook で二重チェックは過剰だ。**hook での強制と、Claude の指示遵守は、二重にせず役割分担する**。これが運用のシンプルさを保つコツだ。

### PreToolUse の落とし穴

便利な PreToolUse だが、落とし穴もある。

**hook が遅いと Claude 全体が遅くなる**。Write/Edit のたびに hook が走るので、hook 内で時間のかかる処理（ネットワークアクセス、大量ファイル読込）を入れると、書き込みのたびに数秒待たされる。

私の運用ルールは「**PreToolUse の hook は1秒以内に終わらせる**」。1秒を超える処理が必要なら、PostToolUse に回す（事後処理にする）。

> **PreToolUse は「書く前に止める」装置。物理的な強制力があるが、遅い hook は Claude を遅くする。1秒以内に終わらせる。**

## PostToolUse──終わった直後に振り返るから、知識が資産になる

**PostToolUse** はツール実行が完了した直後に発火する。

### task-completed-check.sh と log-file-edit.sh

私はこの hook に2つのスクリプトを割り当てている。

**1. task-completed-check.sh（matcher: TaskUpdate）**

タスクのステータスが `completed` に変わった瞬間に発火する。動作はこうだ。

1. どのタスクが完了したか取得
2. そのタスクの活動ログ（このセッションでの編集・コマンド実行履歴）を Claude に整理させる
3. 「**Why（なぜやったか）**」「**学び（何を得たか）**」「**パターン（次回活かせる原則）**」の3項目で振り返り
4. 振り返りを `.logs/YYYY-MM-DD/` に保存

これにより、**タスクを完了するたびに、知識が自動的に蓄積される**。私が「振り返りをしよう」と思わなくても、PostToolUse が勝手にやってくれる。

**2. log-file-edit.sh（matcher: Write|Edit）**

ファイル編集のたびに発火し、編集内容を `.logs/YYYY-MM-DD/edits.md` に追記する。

- 編集ファイル名
- 編集タイムスタンプ
- 変更概要（Claude が短く要約）

これがあると、「**今日何をやったか**」を後から振り返れる。Daily の `/daily-evening` で「今日完了したこと」を集計するときに、この edits.md が原材料になる。

### 「終わった直後」の重要性

振り返りを後回しにすると、何が起きたか忘れる。

私が手作業で振り返りを書いていた頃、夕方に「今日何やったっけ」と思い出そうとして、半分も覚えていなかった。重要な判断や学びが、その日のうちに記録されないと、**翌日には消えている**。

PostToolUse hook で「**終わった瞬間に**」振り返るから、記憶が新鮮なうちに記録される。これが知識を**資産化**する。

### 振り返りの3項目（Why / 学び / パターン）

振り返りの3項目は、ふだんから意識している原則だ。

| 項目 | 内容 | 例 |
|------|------|---|
| **Why** | なぜそれをやったか | 「note週刊AI検証の公開準備、フィードバックループを回すため」 |
| **学び** | 何を得たか | 「ファクトチェックで数値ミス1件発見、Genspark の精度を再確認」 |
| **パターン** | 次回活かせる原則 | 「数値を含む記事は必ず事前ファクトチェック、特に倍率・割合は要注意」 |

「Why」がないと、後で見ても「**何のためにやったか**」が思い出せず、参考にならない。

「**パターン**」がないと、毎回個別の出来事として終わってしまい、**知識が蓄積されない**。次回似た状況になったときに、また同じ判断をゼロから始めることになる。

3項目セットで振り返ると、**個別の出来事が原則に昇華される**。これが知識資産化の本質だ。

### log-file-edit.sh で取れるデータ量

参考までに、私の Vault では1日あたり 30-50ファイルが編集されている（コンテンツ・コマンド・設定すべて含む）。log-file-edit.sh はこの全部を記録する。

1ヶ月で約1,000ファイル分の編集ログが蓄積される。「**先月のこの時期、何をやっていたか**」を振り返るとき、この edits.md が最強の検索資源になる。

> **PostToolUse は「終わった直後」に振り返る装置。Why / 学び / パターンの3項目で記録すれば、個別の出来事が原則に昇華される。**

## SessionStartとStop──セッションを「作業」ではなく「業務単位」に変える

最後に **Stop**（セッション終了時）について扱う。SessionStart はまだ運用していないが、参考までに触れる。

### log-session-stop.sh の役割

私は Stop hook に `log-session-stop.sh` を割り当てている。動作はこうだ。

1. セッションが終了する
2. このセッションでの全活動を要約（編集ファイル、実行コマンド、完了タスク）
3. `.logs/YYYY-MM-DD/session-NNN.md` に保存
4. 翌日の `/daily` で参照可能にする

これにより、**セッションが「業務単位」になる**。

### セッションを「業務単位」にする意味

普通、Claude Code のセッションは「**Claude を開いた瞬間から閉じた瞬間まで**」の単なる作業時間として扱われる。

これを「**業務単位**」に変える、とはどういうことか。

業務単位とは、「**目的があり、入力があり、出力があり、振り返りがある**」一連のまとまりだ。会社員が普段の仕事で「**この案件を1つ完結させた**」と感じるあの単位。

ふだんの Claude セッションを業務単位にすると:

- セッション開始時に「**今日のセッションの目的**」が明確になる
- セッション終了時に「**何を達成したか**」「**何を残したか**」が記録される
- 翌日のセッション開始時に、前日のセッション要約が参照できる
- セッションをまたいだ**継続性**が生まれる

これは hook なしでもできるが、毎回手動でやるのは続かない。**Stop hook が勝手に**「**業務まとめ**」を作るから、自動的に業務単位になる。

### log-session-stop.sh の出力例

```markdown
# Session 2026-05-19-003

## Duration
- 開始: 14:30
- 終了: 17:15
- 経過: 2h 45m

## 完了したタスク
- Ch.08「content-pipeline」本文執筆（15,032字）
- Ch.08 レビュー（観点別チェック完了）
- Ch.09 構成案生成（gsk task super_agent）

## 編集ファイル（主要）
- chapters/08-content-pipeline.md（新規作成）
- 03_Input/Zenn-Book-Drafts/2026-05-19_ch09-structure.md（新規作成）

## 実行コマンド
- gsk task super_agent (2回)
- /factcheck (1回)

## 振り返り
- Ch.08 の H2-3 を厚く書いたことで Commission-Delivery の価値が伝わる原稿になった
- 次セッションは Ch.09 本文執筆から開始
- 持ち越し: Ch.10 構成案、Ch.11 構成案、最終通読
```

これが毎セッション自動で生成される。翌日の `/daily` でこのファイルを読めば、「**昨日の続き**」がすぐに分かる。

### SessionStart の使い道

SessionStart は私はまだ使っていないが、想定される用途は1つある。

**前日のセッション要約を自動表示する**。SessionStart hook で `.logs/YYYY-MM-DD/session-NNN.md` の前日分を Claude に渡せば、毎セッション開始時に「**前回はここまでやりました**」と前置きされる。これがあると、コンテキストスイッチが速くなる。

ただし、これは Stop の log-session-stop.sh が必須前提だ。Stop で記録しないなら、SessionStart で渡すデータがない。**Stop が起点で、SessionStart が活用**という関係。

> **Stop hook はセッションを「作業」から「業務単位」に変える。SessionStart と組み合わせれば、セッションをまたいだ継続性が生まれる。**

## .logs/YYYY-MM-DD/──hooksを記録装置で終わらせず、知識抽出装置にする

ここまで紹介した hook の多くが、`.logs/YYYY-MM-DD/` に書き込みをする。

```
.logs/
├── 2026-05-19/
│   ├── prompts.md          ← UserPromptSubmit hook が記録
│   ├── edits.md            ← log-file-edit.sh が記録
│   ├── task-reflections.md ← task-completed-check.sh が記録
│   ├── session-001.md      ← log-session-stop.sh が記録
│   ├── session-002.md
│   └── session-003.md
├── 2026-05-18/
│   └── ...
```

これは単なる記録装置に見えるが、**運用次第で知識抽出装置になる**。

### 知識抽出のフロー

`.logs/` を**読み返す**運用を組み込むと、知識抽出が機能する。

**1. 週次レビューでの活用**

毎週金曜の `/team-weekly-review`（Ch.06）で、1週間分の `.logs/` を読む。「**今週繰り返し出てきたパターン**」を抽出する。

たとえば、PostToolUse で記録された振り返りに「**ファクトチェックで数値ミス発見**」が3回出てきたら、「**数値を含む記事は事前にスプレッドシートで計算検証する**」という新ルールを Skill に組み込む。

**2. 月次の Skill メンテナンス**

月末に `.logs/` の1ヶ月分を眺める。よく使われた Skill、ほとんど使われなかった Skill、毎回うまく動かなかった Skill——使用パターンが見える。

使われなかった Skill は廃止候補。毎回うまく動かない Skill は改修候補。**ログが、Skill 改善の原材料**になる。

**3. 失敗事例集としての蓄積**

セッション要約の中で「**今日詰まったこと**」「**やり直したこと**」を記録すると、それが失敗事例集になる。Ch.11 で本書全体の失敗を振り返るが、その原材料の多くはこの `.logs/` から来ている。

### ログを「読まない」と意味がない

ここで強調しておくべきは、**ログは溜めるだけでは意味がない**ことだ。

私も最初、ログを溜めて満足していた時期があった。1ヶ月で `.logs/` が200ファイルを超えた頃に気づいた——「**一度も読み返していない**」。

ログは**読み返す前提**で運用しないと、ただのストレージコストになる。週次・月次の読み返し時間を**カレンダーに固定**することで、はじめてログが知識抽出装置になる。

私は毎週金曜の夕方を「**ログ読み返し30分**」として固定している。30分で1週間分は読めない。だから「**ランダムに3日分だけピックアップ**」ルールにしている。完璧ではないが、ゼロよりはずっといい。

> **`.logs/` は記録するだけでは知識装置にならない。週次・月次の読み返し時間を固定すれば、ログが Skill 改善と知識抽出の原材料になる。**

## hooks導入の順番──小さく始めて、半自動起動へ育てる

最後に、hook 導入の順番について書く。

私の試行錯誤から導いた**推奨導入順**は、こうだ。

```
Phase 1（最初の1週間）
  → Stop hook (log-session-stop.sh)
     セッション要約だけ自動化、効果を実感

Phase 2（2週目）
  → PostToolUse (log-file-edit.sh)
     編集ログを取り始める

Phase 3（3週目）
  → PostToolUse (task-completed-check.sh)
     タスク完了時の振り返りを自動化

Phase 4（4週目以降）
  → UserPromptSubmit, PreToolUse
     より高度な hook を追加
```

理由は段階的に説明する。

### Phase 1: Stop だけから始める

最初に導入するべきは Stop hook だ。理由は3つある。

**1. 動作が分かりやすい**: セッション終了時に1回だけ動くから、いつ動いたかが明確。デバッグが容易。

**2. 効果を実感しやすい**: セッション要約が `.logs/` に蓄積されていくのを見ると、「自動化って便利だ」と実感する。これが続けるモチベーションになる。

**3. 失敗してもダメージが小さい**: セッション終了後の処理だから、失敗しても作業の流れに影響しない。安全に試せる。

### Phase 2-3: PostToolUse 系を追加

Stop で慣れたら、PostToolUse 系を追加する。log-file-edit と task-completed-check の2つ。

これらは「**事後処理**」だから、エラーが起きても進行中の作業を止めない。安全。

### Phase 4: より高度なものに進む

最後に UserPromptSubmit と PreToolUse を導入する。これらは「**進行中の作業に介入する**」hook なので、エラー時の影響が大きい。十分に慣れてから手を出す。

### 「全部一気に」は失敗する

hook を導入したくなる気持ちは分かる。だが、**一気に5つ全部を入れると、必ず後悔する**。

複数 hook の発火順序が把握できず、何かおかしくなったときに**どの hook が原因か特定できない**。1つずつ、効果を確認しながら追加するのが、長期的に最も速い導入方法だ。

製造業の生産ライン立ち上げと同じだ。**全部の機械を一気に動かさない**。1機械ずつ、動作確認しながら順次稼働させる。これが結果として最も速い立ち上げになる。

> **hook 導入は Stop から始めて段階的に育てる。一気に5つ入れると、デバッグ不能になって運用が破綻する。**

## アンチパターン3つ

### NG1: 全hookイベントに hook を設定する

**症状**:
- 8つの hook イベント全部にスクリプトを割り当てる
- 1回のセッションで複数 hook が連鎖発火
- 何かおかしくなったとき、どの hook が原因か分からない

**処方箋**:
- まず5つに絞る（UserPromptSubmit, PreToolUse, PostToolUse 2本, Stop）
- 必要になってから追加する
- 「便利だから増やす」ではなく「必要だから増やす」

### NG2: hook の中で重い処理をする

**症状**:
- PreToolUse hook がネットワークアクセスや大量ファイル読込をする
- Write/Edit のたびに数秒待たされる
- Claude 全体が遅くなる

**処方箋**:
- PreToolUse hook は1秒以内に終わらせる
- 重い処理は PostToolUse に回す（事後処理にする）
- それでも重いなら、hook ではなく別の Skill に切り出す

### NG3: ログを溜めるだけで読み返さない

**症状**:
- `.logs/` に1ヶ月で数百ファイルが蓄積
- 一度も読み返していない
- ストレージだけ食って、知識抽出に活用されていない

**処方箋**:
- 週次・月次の読み返し時間をカレンダーに固定
- 全部読まなくていい。「ランダム3日分」でも継続する方が重要
- 読み返しから抽出したパターンを Skill に反映する
