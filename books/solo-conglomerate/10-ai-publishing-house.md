# ai-publishing-house──外部プロダクションとの接続

## 「外部プロダクションとの接続」が必要になるのはなぜか

Ch.09 の最後で、私はこう書いた。

> Part 3完成、運用は構造化された。次は外部プロダクションとの接続——1人総合商社の「商社性」を扱う。

Part 3 まででは、私の Vault 内部で完結する設計を扱ってきた。CLAUDE.md、Skill、エージェント組織、channel-agent、agent-teams、daily-workflow、content-pipeline、hooks——これらはすべて **私の Vault という1つのプロジェクト**の中の話だ。

ここで本章 Ch.10 から視点を**外**に向ける。

Vault の外には、もう1つの大きなプロジェクトが動いている。**ai-publishing-house** という名前の、独立した別プロジェクトだ。Ch.06 と Ch.08 で「**Commission-Delivery**」という名前で何度か登場した、あの外部制作プロダクションの実体である。

なぜ「**外部プロダクションとの接続**」が必要なのか。理由は単純で、**1人で全部抱えると、本物の商社にはなれない**からだ。

本物の総合商社は、**製造業を本業としているわけではない**。もちろん子会社や事業投資を通じて製造・生産拠点を持つケース（三菱商事のサーモン養殖事業 Cermaq、食品加工子会社など）はあるが、**価値の源泉は生産設備ではなく、情報・ネットワーク・資金を活用した仲介・投資・流通機能**にある。良い発注先を持ち、納品物を見極め、流通を組む——これが商社の本質的な仕事だ。

1人総合商社も同じ構造を持つべきだ。私（CEO）が**判断・編集・公開**に集中するために、**制作そのもの**は別プロジェクトに切り出す。それが ai-publishing-house の役割だ。

本章では、ai-publishing-house がどんな組織で、Vault とどう接続し、なぜ別プロジェクトにしたかを扱う。1人総合商社が「**1人プロジェクト**」ではなく「**複数プロジェクトを束ねる商社**」として機能する仕組みを公開する。

> **1人で全部抱える設計には限界がある。本物の商社になるには、制作を外部プロダクションに切り出す必要がある。**

## ai-publishing-houseは何をする組織なのか

ai-publishing-house は、私の作業環境上は `~/desktop/work1/ai-publishing-house/` という別ディレクトリにある。Vault（`obsidian-1/`）とは完全に別プロジェクトだ。Claude Code でこのディレクトリを開くと、また別の CLAUDE.md と別の Skill 群が立ち上がる。

実体としては、**出版社のワークフローをそのまま実装したエージェント組織**だ。

### 11フォルダ構造

ai-publishing-house のディレクトリ構造はこうなっている。

```
ai-publishing-house/
├── 00_Proposals/      ← 企画書（CEOが承認したもの）
├── 01_Research/       ← 取材・調査メモ
├── 02_Outlines/       ← 章構成案・記事プロット
├── 03_Manuscripts/    ← 初稿
├── 04_Editing/        ← 編集中
├── 05_Production/     ← 図解・組版・最終チェック
├── 06_Published/      ← 公開済み（参照用アーカイブ）
├── 07_Marketing/      ← マーケティング素材
├── 08_State/          ← プロジェクト全体の状態管理
├── 09_Commissions/    ← Vault から受領した発注書
└── 10_Deliveries/     ← Vault に納品する成果物
```

11フォルダ。**00 → 06 が制作の流れ**、**07 がマーケ**、**08 が状態管理**、**09 と 10 が Vault との接続インターフェース**だ。

これは本物の出版社の組織構造をそのまま写している。企画→リサーチ→アウトライン→原稿→編集→制作→公開という一連の流れがフォルダ順に並んでいる。

### 出版社の役割を担うエージェント

このフォルダ群を動かすのは、ai-publishing-house 内部のエージェントだ。Vault の COO や content-strategist とは別人格で、別の役職を担う。

| 役職 | 役割 |
|------|------|
| **編集長**（Editor-in-Chief） | 全体の進行管理、最終承認 |
| **記者**（Reporter） | 01_Research でのリサーチ |
| **ライター**（Writer） | 03_Manuscripts での初稿執筆 |
| **編集者**（Editor） | 04_Editing での編集 |
| **制作担当**（Production） | 05_Production での図解・組版 |
| **マーケター**（Marketer） | 07_Marketing でのプロモ素材作成 |

Vault 側の25エージェントとは完全に別人格だ。**プロジェクトが分かれているから、エージェントも分かれている**。同じ「ライター」という呼称でも、ai-publishing-house のライターは Vault の channel-agent とは別物だ。

### なぜ「出版社」というメタファーか

ai-publishing-house に「**出版社**」というメタファーを採用したのは偶然ではない。

メタファーがあると、**各エージェントの役職と責任が直感的に分かる**。「編集長」という言葉を聞けば、誰でも「全体を統括する人」と理解する。「記者」「ライター」「編集者」も同様だ。

これが「制作部長」「執筆担当者A」「執筆担当者B」のような無味乾燥な命名だと、エージェントを増やすたびに「**この人は何をする人だっけ**」を確認する手間が増える。

**業界メタファーは、エージェント組織の自己説明性を高める**。製造業ならライン長・工程担当・検査員。医療なら主治医・看護師・薬剤師。それぞれの業界で確立した役職名を使うと、ゼロから理解する必要がない。

> **ai-publishing-house は出版社のワークフローを11フォルダで実装した、Vault とは別の独立プロジェクトである。業界メタファーが組織の自己説明性を高める。**

## VaultとあいだのCommission-Deliveryインターフェース

Vault と ai-publishing-house がどう接続するか。これが本章の核心だ。

接続点は2つのフォルダだけ。**09_Commissions/** と **10_Deliveries/**。この2フォルダが、2つの独立プロジェクトを繋ぐ唯一の境界だ。

### 09_Commissions/ ── Vault からの発注書置き場

Vault 側で `/commission-content` を叩くと、発注書がここに置かれる。具体的には、ai-publishing-house の `09_Commissions/@Queue/YYYYMMDD-HHMMSS-[topic].md` というファイルになる。

発注書の構造は次のとおりだ。

```markdown
# Commission: 20260519-143000-note-claude-skills-deep-dive

## Channel
- target: note-aij
- account: bhrtaym
- platform: note.com

## Topic
Claude Code Skills の深掘り解説。
特に Plugin Skills と Personal Skills の境界、
Skill 共有のベストプラクティスについて。

## Persona & Tone
- channels/note-ai-journal.md から継承
- 実機検証ベース、淡々と正確に

## Source Material
- 03_Input/Research/AI-Tools/20260518_claude-code-skills.md
- 関連の trend.md 抜粋

## Quality Requirements
- 文字数: 3,000-5,000字
- ファクトチェック必須（Genspark cross_check）
- インフォグラフィック生成必須（nanobanana:infographic）
- コードサンプル含む

## Delivery
- 形式: マークダウン + サマリー画像
- 期限: 2026-05-22
- 納品先: 10_Deliveries/20260519-143000-note-claude-skills-deep-dive/

## 報酬・条件
- 公開後の編集権は Vault 側CEO（私）が保持
- 修正依頼時の応答 SLA: 48時間以内
```

この発注書には、ai-publishing-house が制作に必要なすべての情報が含まれている。**チャネル、ペルソナ、素材、品質要件、納期、納品先**。書き手と顧客（私）の関係を1ファイルで完結させる。

### 10_Deliveries/ ── ai-publishing-house からの納品物置き場

ai-publishing-house で制作が完了すると、`10_Deliveries/20260519-143000-note-claude-skills-deep-dive/` というディレクトリが作られ、以下が配置される。

```
10_Deliveries/20260519-143000-note-claude-skills-deep-dive/
├── delivery-manifest.md   ← 納品書、編集レビュー結果
├── article.md             ← 本文（マークダウン）
├── infographic.png        ← サマリー画像
└── factcheck-report.md    ← ファクトチェックレポート
```

`delivery-manifest.md` には**編集レビュー結果**が必ず記載される。

```markdown
# Delivery Manifest

## Commission Reference
- Commission Key: 20260519-143000-note-claude-skills-deep-dive
- Received: 2026-05-19 14:30:00
- Delivered: 2026-05-21 18:42:00

## Editor Review Result
**APPROVED**

- 編集ポイント: 3件指摘、すべて反映済み
- ファクトチェック: 済（Genspark cross_check、修正2点反映）
  - 修正1: Plugin Skills のフォルダ名（typo）
  - 修正2: Personal Skills の制限事項を正確に
- インフォグラフィック: 生成済み
- 推奨公開: 2026-05-22（金曜朝）

## Quality Metrics
- 文字数: 4,287字（要件 3,000-5,000字内）
- 図解数: 3（インフォグラフィック1、フロー図2）
- ファクトチェック修正回数: 2

## CEO への注意事項
- なし（クリーン納品）
```

Vault 側で `/receive-delivery` を叩くと、この `delivery-manifest.md` を読み取って、`APPROVED` のものだけを Vault の `Note-AI-Journal/@TODO/` に配置する。`REVISION_NEEDED` の納品物は配置されず、リストアップだけされる。

### この2フォルダが「契約書」になる

`09_Commissions/` と `10_Deliveries/` が、Vault と ai-publishing-house の**契約書**として機能する。

- **発注書**が「私が何を求めているか」を明文化する
- **納品書**が「私が何を受け取ったか」を明文化する
- 両者の差分が「**追加要件**」「**修正依頼**」になる

これは現実の業務委託契約と同じ構造だ。**契約書がなければ、外注は機能しない**。AI 組織でも同じだ。発注書と納品書が明文化されているから、Vault と ai-publishing-house は**他人同士として**正しく機能できる。

### 同一プロジェクトに統合しなかった理由

ここで素朴な疑問が出る。「**Vault と ai-publishing-house を1つのプロジェクトにまとめれば、09/10 のやり取りが不要では?**」

これは敢えて分けている。理由は次のH2で扱う。

> **Commission-Delivery は 09_Commissions と 10_Deliveries の2フォルダで実装される。発注書と納品書が「契約書」として2プロジェクトを繋ぐ。**

## なぜ別プロジェクトにしたのか──分離は整理ではなく経営判断である

「**1つのプロジェクトに統合すれば、ファイル管理が楽では?**」

これに対する私の答えは「**いいえ、別プロジェクトのままが良い**」だ。理由は3つある。

### 理由1: ファイル衝突リスクのゼロ化

Vault と ai-publishing-house で扱うフォルダは完全に別だ。同じファイルを別エージェントが同時に書き換える可能性は構造的にゼロ。

Ch.06 で扱った agent-teams や Ch.07 の daily-workflow で、複数エージェントが並列で動く設計をしてきた。同一プロジェクト内では File Ownership Rule で衝突を制御するが、**プロジェクト分離なら、そもそも衝突しえない**。

これは「**安全装置**」の二重化だ。File Ownership Rule（論理的制約）に加えて、プロジェクト分離（物理的制約）が効いている。論理だけでなく物理でも担保されているから、運用ミスで衝突が起きる確率がさらに下がる。

### 理由2: 責任境界の明確化

Vault は「**1人総合商社のCEOである私**」のプロジェクトだ。ai-publishing-house は「**外部の制作プロダクション**」のプロジェクトだ。

この境界が明確だから、**書く責任**と**公開する責任**を分離できる。

- 書く責任: ai-publishing-house のライターと編集者
- 公開する責任: Vault 側の私

同一プロジェクト内で「書く人」「公開する人」を分離しようとしても、結局**気持ちのうえで**1人の作業に戻ってしまう。「書いたんだから、ついでに公開しよう」になる。

プロジェクトを物理的に分けると、**気持ちの上でも別物**になる。「ai-publishing-house の納品物を、私が編集判断して公開する」——この境界が、自然に立つ。

### 理由3: スケール時の独立性

ai-publishing-house は、将来的に**複数のクライアント Vault に納品する**ことを想定している。今は私の Vault からの発注しか受けていないが、将来は他の人の Vault からも発注を受けられる構造になっている。

そのとき、Vault と ai-publishing-house を同一プロジェクトにしていると、**他のクライアントが私の Vault を覗ける**問題が発生する。プロジェクト分離なら、ai-publishing-house は複数の Vault と接続できる**汎用的な制作プロダクション**になる。

これは「**ゆくゆくは複数の Vault で使われるかもしれない**」という設計判断だ。今すぐ複数 Vault 接続が必要なわけではないが、必要になったときに**設計を作り直さずに済む**。

### 「分離は整理ではなく経営判断」

ここで強調したいのは、**分離は単なる整理整頓ではなく、経営判断**だということだ。

整理整頓なら「フォルダで分けるだけ」でいい。だがプロジェクト分離は、**責任・権限・将来性**を含む経営判断だ。

私は最初、Vault 内に `08_AI-Pub/` というサブフォルダを作って ai-publishing-house を中に置こうとした。「**同じプロジェクトの方が便利**」と思ったからだ。

3週間運用して、間違いに気づいた。Vault のエージェントが ai-pub 配下のファイルに手を出してしまう事故、Vault の COO ブリーフィングに ai-pub のタスクが混入してしまう事故。これらは「**プロジェクトが同じ**」という前提があると避けようがなかった。

分離してから、これらの事故はゼロになった。**プロジェクト境界が、自然に責任境界になる**。

> **Vault と ai-publishing-house の分離は、ファイル整理ではなく経営判断だ。ファイル衝突ゼロ・責任境界の明確化・将来のスケール独立性の3つを担保する。**

## Phase 1 でどこまでできたか──「動く制作会社」としての最小成立条件

ai-publishing-house は執筆時点（2026年5月）で **Phase 1 完了**の状態にある。

Phase 1 で実装したのは、**動く制作会社としての最小成立条件**だ。具体的には次の3つ。

### Phase 1 の3つの成立条件

**1. 11フォルダ構造の確立**

00_Proposals から 10_Deliveries までの11フォルダがすべて作成済み。各フォルダの用途と所有エージェントが定義済み。

**2. エージェント定義の整備**

編集長、記者、ライター、編集者、制作担当、マーケターの定義ファイルが完成。各エージェントが自分の役職と責務を理解して動ける。

**3. Vault との接続テスト完了**

実際に Vault から `/commission-content` で発注書を投げ、ai-publishing-house が制作し、`10_Deliveries/` に納品し、Vault が `/receive-delivery` で回収する——この一連の流れが**実際に動く状態**になっている。

### 動いた具体例: Claude仕事術企画

Phase 1 の最初の実例が、`202602-claude-business-proposal.md`（**Claude仕事術**）という企画だ。

この企画は Vault 側で立案され、`/commission-content` で ai-publishing-house に発注された。ai-publishing-house は受領後、リサーチ→アウトライン→原稿→編集→制作のフローを通過させて、納品物を Vault に返した。

この往復が**問題なく動いた**ことが、Phase 1 完了の証拠だ。「**設計しただけ**」ではなく「**実際に1案件が完走した**」のが Phase 1 の到達点。

### 待機中: 本書の企画

執筆時点で、ai-publishing-house の `00_Proposals/@Queue/` には `202603-solo-conglomerate-proposal.md`——**本書の企画書**——が承認待ち状態で置かれている。

「**Zenn Book「1人総合商社」自力出版**」の企画は、本来 ai-publishing-house に発注して制作してもらう想定だった。だが、戦略γへのピボット（マネタイズ最優先）の中で、私自身で執筆する方針に変更した。

そのため、この企画書は ai-publishing-house の`@Queue` で**承認待ちのまま**置かれている。皮肉なことに、ai-publishing-house に発注しなかったからこそ、本書はあなたの手元に届いている。

### Phase 2 以降の構想

Phase 1 で「**動く**」段階は達成した。Phase 2 以降の構想は次のとおりだ。

| Phase | 内容 |
|-------|------|
| Phase 2 | 並列発注の安定化（複数 Commission を同時実行） |
| Phase 3 | 編集品質の指標化（編集レビューの定量評価） |
| Phase 4 | 複数 Vault からの発注受付（マルチクライアント対応） |
| Phase 5 | マーケティング機能の自律化（07_Marketing/ の能動運用） |

これらは順次着手していく予定だ。Phase 5 まで揃ったとき、ai-publishing-house は「**完全な独立出版社**」になる。

> **Phase 1 では「動く制作会社」の最小成立条件を達成した。実例の1案件完走が到達点。Phase 2 以降は安定化・指標化・マルチクライアント化・自律マーケへ。**

## 「商社」の本質は、自社生産ではなく良い発注先を持つこと

本書のタイトル「**1人総合商社**」の「商社」という言葉について、ここで深掘りしておきたい。

私が「1人総合商社」と命名したとき、最初は単に「**1人で複数のチャネルを運営する**」という意味のメタファーだった。だが、ai-publishing-house を作る過程で、このメタファーがもっと深い意味を持つことに気づいた。

### 商社は何をする会社か

総合商社の本業は、**自社で物を作ること**ではない。

三菱商事はトヨタの車を作っていない。三井物産は半導体を製造していない。住友商事は鉄鋼を製錬していない。

商社がやるのは、次のことだ。

1. **市場とニーズの見極め**: 何が売れるか、誰が買うかを読む
2. **良い発注先の選定**: 信頼できる生産者・サプライヤーを持つ
3. **品質と納期の管理**: 発注通りの物が、期日通りに納品されるか管理する
4. **流通と販売**: 商品を市場に届ける

この4つが商社の本質的な仕事だ。**自社で作る**は含まれない。

### 1人総合商社の「商社性」

これを1人総合商社に当てはめると、こうなる。

| 商社の仕事 | 1人総合商社での実装 |
|----------|-------------------|
| 市場とニーズの見極め | content-strategist と Advisory Board が分析（Ch.05） |
| 良い発注先の選定 | ai-publishing-house を社外プロダクションとして持つ（本章） |
| 品質と納期の管理 | delivery-manifest.md で編集レビュー結果を確認 |
| 流通と販売 | channel-agent が各プラットフォームに公開（Ch.05） |

ここで重要なのは、「**3番目の発注先**」だけが**自社（Vault）の外**にあることだ。1番目（ニーズ分析）と4番目（流通）は Vault 内で完結する。2番目（生産）だけが外部委託。

これは**最小限の外部化**だ。「**自分が一番苦手で時間がかかる部分**」だけを外に出して、他はすべて自分で抱える。これが現実的な1人商社の形だ。

### 「全部外注」も「全部自作」も失敗する

もし「**全部 ai-publishing-house に外注**」したら、私は何をするのか? ニーズ分析も流通も外に出すと、**私の役割が消える**。これは商社ではなく、**ただの出資者**だ。

逆に「**全部 Vault で自作**」したら、Ch.06 で扱った agent-teams で並列実行しても限界がある。書く時間、編集する時間、図解を作る時間——これらが副業時間（30分-1時間）を食い尽くす。

「**ニーズ分析と流通は自分、生産は外**」のバランスが、1人副業として最適だ。これが商社の構造を1人に圧縮した形になる。

### 「外注先を育てる」も商社の仕事

もう1つ、商社的な発想がある。**外注先を「使い捨て」にせず、育てる**ことだ。

ai-publishing-house は最初、私の発注に対して納期を守れないことがあった。ファクトチェックを忘れることもあった。図解の品質がばらついた。

これを「**ダメな外注先だ**」と切り捨てるのではなく、フィードバックして改善していった。発注書のテンプレートを改善し、納品書のレビュー項目を細かくし、編集レビューの基準を明文化した。

結果、3ヶ月で ai-publishing-house の品質は安定した。今では発注の8割が `APPROVED` で返ってくる。最初は5割もなかった。

**外注先を育てる**——これも商社の重要な仕事だ。良い発注先は買ってくるものではなく、**育てるもの**だ。

> **「商社」の本質は、自社生産ではなく、良い発注先を持ち、育てること。1人総合商社の「商社性」は ai-publishing-house で実装される。**

## content-pipelineを組織として見る──原稿制作から流通までを一続きにする

Ch.08 で content-pipeline の9段階（ネタ発見〜エンゲ確認）を扱った。本章で ai-publishing-house を導入したので、content-pipeline を**組織として見直す**ことができる。

### 9段階の責任分担

content-pipeline の9段階を、**どの組織が担うか**で塗り分けると、こうなる。

| # | 段階 | 担当組織 | 担当エージェント |
|---|------|---------|----------------|
| 1 | ネタ発見 | Vault | content-strategist, channel-agents |
| 2 | 企画 | Vault | content-strategist |
| 3 | リサーチ | **ai-publishing-house** | 記者 |
| 4 | 執筆 | **ai-publishing-house** | ライター |
| 5 | 図解 | **ai-publishing-house** | 制作担当 |
| 6 | ファクトチェック | **ai-publishing-house** | 編集者 |
| 7 | 公開 | Vault | channel-agents |
| 8 | 告知 | Vault | x-ai-lifestyle |
| 9 | エンゲ確認 | Vault | channel-agents |

**ネタ発見・企画・公開・告知・エンゲ確認**は Vault。**リサーチ・執筆・図解・ファクトチェック**は ai-publishing-house。

この塗り分けが、Commission-Delivery の本質を可視化する。**Vault は「企画と流通」を担い、ai-publishing-house は「制作」を担う**。

### この分担の効果

この組織分担には3つの効果がある。

**1. 視点の純度が上がる**

ネタを考えているとき、私（Vault）は「**どんなネタが伸びるか**」だけに集中できる。「**書く労力**」を考えない。書く労力は ai-publishing-house の問題だから、私の判断には入らない。

これが同一プロジェクト内で「**書く労力もあるから、このネタは後にしよう**」のような判断が混ざると、純粋なニーズ判断にならない。

**2. ボトルネックが見える**

@TODO が詰まっているのか、@Doing が詰まっているのか、@Completed が遅いのか——フォルダ単位で詰まりを見える化できる。Ch.07 で言及した「ブログ@Doing 26件持ち越し」も、この見える化があったから検出できた。

組織が分かれていると、**どの組織で詰まっているか**まで見える。これが「**外部プロダクションの納品が遅い**」と「**自分が公開に手が回らない**」を切り分ける。

**3. 改善対象が絞れる**

ボトルネックが ai-publishing-house 側なら、発注書の改善や ai-pub 側のエージェント改善が必要。Vault 側なら、自分の運用ルール改善が必要。**改善対象を間違えない**。

同一プロジェクトだと「全部自分のせい」になりがちで、改善のための分析が散漫になる。組織を分けると、**責任の所在が明確**になり、改善が機動的になる。

> **content-pipeline の9段階を組織単位で塗り分けると、責任分担とボトルネック検出が両立する。改善対象を間違えない設計になる。**

## 1人で抱えないための設計が、最後に自分の仕事を増やす

ここまで「**1人で抱えないために ai-publishing-house を作った**」と書いてきた。だが、正直に書いておくべき**パラドックス**がある。

**1人で抱えないための設計が、結局自分の仕事を増やす**ことがある。

### パラドックスの正体

ai-publishing-house に制作を委ねたことで、私は確かに「書く」「編集する」「図解を作る」という労働から解放された。

だが、増えた仕事もある。

**1. 発注書を書く判断**

ai-publishing-house に何を発注するか、毎回判断する必要がある。発注書の品質次第で、納品物の品質が決まる。良い発注書を書く時間が、新たに必要になった。

**2. 納品物を見極める判断**

ai-publishing-house から来た納品物を `APPROVED` で受け入れるか、`REVISION_NEEDED` で差し戻すか。これも毎回判断が必要。雑に受け入れると、品質の悪いコンテンツが公開される。

**3. 発注先のメンテナンス**

ai-publishing-house のエージェント定義を改善する、発注書テンプレートを更新する、編集レビュー基準を改訂する——これらの**メタな仕事**が増えた。

書く仕事は減ったが、**判断する仕事と発注先を育てる仕事は増えた**。トータルの時間で見ると、初期は**むしろ増えた**かもしれない。

### なぜそれでも分離するのか

ではなぜ分離するのか。理由は2つ。

**1. 判断の仕事は私が代替不可能**

書く仕事は、ai-publishing-house がやってくれる。だが「**何を発注するか**」「**何を公開するか**」の判断は、私にしかできない。CEO の仕事は判断だ。書く仕事から判断する仕事へのシフトは、CEO 業務として正しい。

**2. 長期的にはスケールする**

短期的には仕事が増えるが、長期的には ai-publishing-house がより成熟し、私の判断時間が安定する。今は発注書テンプレートを毎回いじっているが、いずれはテンプレートが固定化されて、判断時間が短くなる。

**短期の労力増を受け入れて、長期のスケールを取る**。これが ai-publishing-house を作った経営判断だ。

### 「楽になる」だけが目的ではない

「**AI 活用すれば楽になる**」という発信は世の中に多い。だが、実体験として、**1人で AI を組織化すると、最初は楽にならない**。むしろ忙しくなる。

楽になるのは、**設計が安定した後**だ。設計途中の3-6ヶ月は、設計のための時間が乗ってくる。これを「**楽にならないからやめた**」と諦めると、永遠に組織化されない。

ai-publishing-house も Phase 1 が完了するまでに3ヶ月かかった。3ヶ月、追加の労力を払ってきた。Phase 2-5 がいつ完成するかも分からない。それでも、組織化された後の楽さを信じて、今は労力を払っている段階だ。

> **1人で抱えないための設計が、最初は自分の仕事を増やす。判断の仕事と発注先を育てる仕事が新たに乗る。だが、長期のスケールを取るために短期の労力増を受け入れる。**

## アンチパターン3つ

### NG1: Vault と ai-publishing-house を統合する

**症状**:
- 「同じプロジェクトの方が便利」と統合してしまう
- ファイル衝突が発生する
- 責任境界が曖昧になり、書く人と公開する人の区別が消える

**処方箋**:
- プロジェクトは物理的に分ける
- 接続は 09_Commissions/ と 10_Deliveries/ の2フォルダだけに限定
- 「**1つにまとめれば楽**」という誘惑に負けない

### NG2: 発注書を雑に書く

**症状**:
- 「だいたいこんな感じで」と曖昧な発注書
- ai-publishing-house からの納品物が期待と違う
- 修正往復が増えて結局自分で書き直す

**処方箋**:
- 発注書テンプレートを固定する（チャネル、ペルソナ、素材、品質要件、納期）
- 良い発注書は良い納品物を生む、悪い発注書は悪い納品物を生む
- 発注書を書く時間を惜しまない

### NG3: 「最初から楽になる」を期待する

**症状**:
- 外部委託すれば即時に楽になると期待する
- 設計の3-6ヶ月で挫折する
- 「やっぱり自分で書いた方が早い」と外部委託を諦める

**処方箋**:
- 初期の3-6ヶ月は楽にならないと受け入れる
- 「判断する仕事」と「発注先を育てる仕事」が新たに乗ることを認識する
- 長期のスケールを取るための短期の労力増として位置付ける

## まとめ──Part 4の始まり、本書の核心へ

本章は Part 4（拡張編）の初章として、**外部プロダクションとの接続**を扱った。

要点を振り返る。

1. **ai-publishing-house は出版社ワークフローの別プロジェクト**: 11フォルダ構造
2. **Commission-Delivery は 09 と 10 の2フォルダで実装**: 発注書と納品書が契約書
3. **分離は経営判断**: ファイル衝突ゼロ・責任境界・スケール独立性
4. **Phase 1 で動く制作会社が成立**: 実例の1案件完走が到達点
5. **「商社」の本質は良い発注先を持つこと**: 自社生産ではなく外注先を育てる
6. **content-pipeline を組織で塗り分ける**: Vault と ai-pub の責任分担で改善が機動化
7. **パラドックス**: 1人で抱えない設計が、判断と発注先メンテの仕事を増やす

これで「1人総合商社」の構造的完成形が見えた。Vault と ai-publishing-house の2プロジェクト、Commission-Delivery の契約書、25エージェント + ai-publishing-house の編集チーム——これらが組み合わさって、副業を「**仕組み**」として回せる。

だが、ここまで読んできて感じた人もいるかもしれない。「**こんなに整っていれば、もう失敗はないのでは?**」

答えは「**いいえ**」だ。

私は3ヶ月運用する中で、**数えきれない失敗**をしてきた。エージェント定義が空回りした。Skill が暴走した。発注書のミスで納品物が役立たずになった。Commission-Delivery が機能不全に陥った週もあった。

本書の最後の章 Ch.11 では、これらの**失敗と反復**を全公開する。「設計図」を見せた本書を、「**実運用の生データ**」で締めくくる。

理論的・構造的に整っていても、現実は崩れる。崩れた中で何を学び、どう改善したか——それが本書の最後のメッセージだ。

> **本章で構造的完成形が見えた。次章 Ch.11 では、3ヶ月運用で起きた失敗・反復・改善を全公開する。本書を「実運用の生データ」で締めくくる。**
