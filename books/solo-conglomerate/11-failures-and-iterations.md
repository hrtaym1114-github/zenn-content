# failures-and-iterations──3ヶ月運用の失敗と反復

## 失敗を公開する理由──設計図を「運用の現実」に接続する

Ch.10 の最後で、私はこう書いた。

> 本書の最後の章 Ch.11 では、これらの**失敗と反復**を全公開する。「設計図」を見せた本書を、「**実運用の生データ**」で締めくくる。

本章はその約束を果たす章だ。

ここまでの Ch.01〜10 で、私は **1人総合商社の設計図**を公開してきた。CLAUDE.md の書き方、フォルダ構造、Skill 設計、エージェント組織、channel-agent、agent-teams、daily-workflow、content-pipeline、hooks、ai-publishing-house——これらが揃えば、副業を「**仕組み**」として回せる。

だが、本書を読んで「**こんなに整っていれば失敗はないだろう**」と思った人がいるなら、その期待は裏切らなければならない。

私は3ヶ月運用する中で、**数えきれない失敗**をしてきた。エージェント定義が空回りした。Skill が暴走した。Commission-Delivery が機能不全に陥った週もあった。一度は副業全体を諦めかけた。

これらの失敗を**全公開する**理由は3つある。

**1. 設計図と運用は別物だから**

設計が美しくても、運用は崩れる。設計図だけ見せて「**これで完璧です**」と言うのは誠実ではない。設計と運用のあいだにある**ギャップ**を見せないと、本書は実用書として成立しない。

**2. 失敗のパターンには再現性があるから**

私の失敗の多くは、おそらくあなたも踏むパターンだ。「**29個まで増やしすぎる**」「**持ち越しタスクが溜まる**」「**Skill が暴走する**」——これらは1人で AI 組織を回せば、ほぼ確実に経験する。**事前に知っていれば、避けられる失敗**もある。

**3. 失敗から導いたメタ原則こそが本質だから**

設計図は私の3ヶ月の試行錯誤の**結果**だ。試行錯誤の**プロセス**にこそ、再利用可能な原則がある。「**完璧主義を捨てる**」「**持ち越しても回る設計**」「**廃止と統合を恐れない**」——これらは設計図には書けない。失敗の物語の中にしか現れない。

本章では、5つの失敗事例を扱う。そこから導いたメタ原則を整理し、最後に本書全体を読者へのメッセージで締めくくる。

> **設計図は完成形に見えるが、3ヶ月の試行錯誤の結果である。失敗を公開することで、設計図を運用の現実に接続する。**

## 29個は多すぎた──廃止と統合で25個に収束した

最初に振り返る失敗は、Ch.04 で簡単に触れた**エージェント数の暴走**だ。

### 何が起きたか

2026年2月、私は organism 設計に夢中になっていた。CLAUDE.md でプロジェクトの脳を整え、Skill で日常動作を言語化し、その次に「**エージェント組織**」を構築する段階に入った。

最初は3つから始めた。

- writer（コンテンツを書く人）
- reviewer（読む人）
- planner（計画を立てる人）

これで動くと思った。実際、1ヶ月は動いた。だが、5チャネル運用が始まると役割が曖昧になり、専門化と部門化を進めた。

そこから雪だるま式に増えた。Content 部門だけで10個近く、Advisory Board に6個、PaperBanana に6個、その他に7-8個。**最大で29個**に達した。

### 何が問題だったか

29個に達した時点で、**どのエージェントに何を頼めばいいか分からなくなった**。

```
私:「note の記事を書いて」
   ↓
私:「あれ、これは note-ai-journal? content-strategist?
     それとも writer? Advisory Board の audience-analyst?」
   ↓
私: 結局、毎回判断に5秒かかる
```

5秒の判断が、1日20回発生すれば100秒。1ヶ月で50分。**便利のために作ったエージェントが、判断コストを生んでいる**。

さらに、月の API 利用料が想定の3倍になった。Opus を多用していたエージェントが29個もあれば、当然そうなる。

### 何を変えたか

29個から25個に**減らした**。

廃止例:
- **x-life-design**: X.com「仕組み化×内省」アカウント運用エージェント。アルゴリズム変更でアカウント停止のため、2026-03-03 アーカイブ。
- 他3つ: 似た役割のエージェントを統合（「reviewer」「fact-checker」「style-guard」→ 「devils-advocate」1つに統合）

統合の判断基準はシンプルだ。「**この2つのエージェントの呼び分けで、私が3秒以上迷うなら統合**」。3秒迷うということは、責任境界が曖昧だ。曖昧なら統合した方が良い。

### 学んだこと

**「便利だから増やす」は罠**だ。エージェントを増やすたびに、判断コストが上がる。

**増やす前に「これと既存エージェントの境界は何か」を10秒で答えられない**なら、増やすべきではない。10秒で答えられないものを増やすと、必ず判断コストが上がる。

「**廃止と統合を恐れない**」——これが私が29個→25個の収束から学んだ原則だ。本書では Ch.04 のメッセージとして書いたが、本章で原則として再確認しておく。

> **エージェントは「便利だから増やす」と必ず破綻する。境界を10秒で説明できなければ統合する。廃止を恐れず、機能する数に収束させる。**

## 持ち越しは悪ではない──@Doing 26件とnote 5週停滞が教えたこと

次の失敗は、**持ち越しタスクの累積**だ。Ch.07 で告白した数字を、本章でもう一度直視する。

### 何が起きたか

執筆時点の私の状態:

- ブログ `@Doing/` に26件の記事が滞留。最も古いものは6週前のもの
- note 記事「claude-code-agent-skills」公開作業が5週持ち越し

5週、6週。「**まだ完成していない仕事**」が積み重なっていた。

毎週金曜の `/team-weekly-review` でこの数字を見るたびに、罪悪感が湧いた。「**今週も公開できなかった**」。

### 何を変えたか

最初は「**気合いで全部公開する週**」を作ろうとした。失敗した。気合いで26件を1週間で公開しようとすると、品質が落ちる。ファクトチェックを飛ばす。図解を急いで作る。結果として、急いで公開した記事は読者からの反応が薄かった。

そこで発想を変えた。「**26件全部を公開する**」のではなく、「**26件のうち本当に公開すべきもの**」を選別した。

選別基準:

| 判定 | 数 | 処置 |
|------|---|------|
| **今月中に公開すべき** | 5本 | @Doing に残し、優先公開 |
| **完成度を上げてから公開** | 8本 | @Doing で寝かせる、来月以降 |
| **このまま廃棄** | 13本 | アーカイブ移動 or 削除 |

26件中13件を**廃棄した**。これが大きかった。「**書いたから公開する**」ではなく「**価値があるから公開する**」に判断基準を変えた。

### 学んだこと

**「持ち越しを失くす」は不可能だ**。副業の時間制約があるかぎり、必ず持ち越しは発生する。

**目指すべきは「持ち越しても回る設計」**だ。Ch.08 で扱った WIP制御がそれだ。入口で絞る、上限を超えたら受けない、出口の閉塞を最優先で解消する。

そして、もう1つ重要なこと——**廃棄を許容する文化**だ。書いた記事を「公開しない」と決めるのは、勇気が要る。書いた労力が無駄になる気がする。

だが、本当の無駄は、価値の低い記事を増やすことだ。**書いた労力は、廃棄判断の経験として残る**。次回似たテーマを書く前に「これは前回廃棄したパターンに似ている」と気づける。

「**書く労力は無駄にならない、廃棄判断こそが価値**」。これが26件持ち越しから学んだ原則だ。

### note 5週持ち越しの正体

note 記事「claude-code-agent-skills」の5週持ち越しは、別の失敗だった。

これは「**公開ボタンが押せない**」問題だった。記事は完成していた。ファクトチェックも済んでいた。インフォグラフィックもあった。**残るは「公開」ボタンを押すだけ**。

それが押せなかった。

理由は「**完璧ではない気がする**」だった。もう一度読み直したい、もう少し書き足したい、タイトルがもっと良くできるはず——こうした気持ちが毎週繰り返されて、5週が経った。

これは Ch.00 で告白した「**半自動投稿システムは完成したが投稿実績0件**」とまったく同じ構造だ。3ヶ月運用してもこの病から完全には脱せていない。

対策として、**毎週金曜の19:00を「公開専用時間」として固定**した。この時間は他のことをしない。Kanban の「📦 今夜」カラムに入っているものを、ただ公開する。

完璧主義を時間で押し切る運用だ。それでもまだ完璧にはなっていない。**設計が完璧でも、運用は人間が崩す**——これが現実だ。

> **持ち越しは悪ではない。「持ち越しても回る設計」を目指し、廃棄を許容する文化を持つ。完璧主義は時間ブロックで押し切る。**

## Skillは便利な部下ではない──暴走する自動化をどう飼いならすか

3つ目の失敗は、**Skill の暴走**だ。

### 何が起きたか

Skill を書き始めた最初の頃、私はこういう Skill を作った。

```markdown
---
name: auto-organize
description: Inboxを自動整理する
---

# auto-organize

01_Inbox/ のファイルをすべて適切なフォルダに移動する。
判断基準は content-sorting-rules.md を参照。
```

これを実行したら、何が起きたか。

Claude は判断基準を読んで、`01_Inbox/` 配下のファイルを次々と移動した。だが、その中に**私が一時的に置いておいた重要なメモ**が混じっていた。判断基準に従って `04_Memory/` の深い階層に移動された。

数日後、そのメモを探した。`01_Inbox/` を見ても無い。「あれ、消した?」と Git ログを見て、ようやく移動先を見つけた。

これは「**便利な部下**」のはずだった Skill が、私の意図しない動きをした事例だ。

### 何が問題だったか

Skill の指示が**曖昧だった**。「適切なフォルダに移動する」と書いたが、私の中での「適切」と判断基準ファイルの「適切」が、必ずしも一致しない。

そして、**動作前にプレビューさせなかった**。Skill が「移動する」と書かれていれば、Claude は確認なしで実行する。

### 何を変えたか

Skill の設計ルールを3つ追加した。

**1. 副作用を伴う動作は必ず「プレビュー」を挟む**

破壊的・非可逆的な動作（移動、削除、上書き）の前に、Claude に「**これから何をするか**」をリストアップさせ、私の確認を求めるよう Skill に書き込む。

```markdown
## 動作前の確認

以下を実行します:
- ファイルA → フォルダX に移動
- ファイルB → フォルダY に移動

実行してよろしいですか? (y/n)
```

**2. 「上書きしない」を明文化**

既存ファイルを上書きする可能性がある動作は、明示的に「**既存ファイルがあれば停止して確認**」と書く。

**3. ドライランオプションを必須にする**

新しい Skill には `--dry-run` オプションを必ず付ける。最初に dry-run で挙動を確認してから実行する習慣を作る。

### 学んだこと

Skill は便利な部下ではない。**指示通りに動くロボット**だ。

部下なら「**そのメモは置いておいてください**」と空気を読む。Skill は読まない。書かれたとおりにやる。**書かれていないことはやらないし、書かれていることは全部やる**。

これを「**冷酷**」と感じるかもしれないが、むしろ良いことだ。**書かれたとおりにしか動かない**から、Skill は予測可能になる。空気を読む部下は、判断ミスをする可能性がある。Skill にはそれがない。

ただし、書く側（私）の責任は大きくなる。**書き漏れがあれば、必ず事故が起きる**。だから、副作用を伴う Skill には必ずプレビューを挟む。これが Skill との付き合い方の基本だ。

> **Skill は便利な部下ではなく、書かれたとおりにしか動かないロボットだ。プレビュー・上書き禁止・ドライランの3つで飼いならす。**

## 品質は最初から安定しない──ai-publishing-houseを5割から8割へ持ち上げた反復

4つ目の失敗は、**ai-publishing-house の初期品質**だ。

### 何が起きたか

Ch.10 で触れたとおり、ai-publishing-house は Phase 1 完了状態にある。だが Phase 1 に至るまでに、何度も品質問題が起きた。

最初の1ヶ月、発注した記事の**APPROVED率は約50%**だった。

```
発注10件
   ↓
納品10件
   ↓
APPROVED: 5件
REVISION_NEEDED: 5件
```

半分が修正待ちになる状態。修正のために再度のやり取りが必要で、結果として制作時間が伸びた。「**外注した方が遅い**」状態に陥った。

### 何が問題だったか

問題は3つに分かれた。

**1. 発注書が曖昧**

「note 記事 1本、トーンは普段通り、3000-5000字」のような大雑把な発注書だと、ai-publishing-house は何を作っていいか分からない。納品物が私の想定と大きくズレる。

**2. 編集レビュー基準が定義されていない**

ai-publishing-house 側の編集者が何をチェックすればいいか分からないので、ファクトチェック漏れ、文体不一致、図解品質ばらつきが頻発した。

**3. フィードバックループが回っていない**

REVISION_NEEDED で差し戻したとき、何が問題だったかを ai-publishing-house 側に伝えていなかった。同じミスが繰り返された。

### 何を変えたか

3つの問題に対して、3つの改善を施した。

**1. 発注書テンプレートを詳細化**

発注書の必須項目を増やした。Persona & Tone（channels/ ファイル参照）、Source Material（必読リサーチへのリンク）、Quality Requirements（文字数・図解必須・ファクトチェック必須）、Delivery（形式・期限・納品先）。

これにより、ai-publishing-house は何を作るべきかが明確になった。

**2. 編集レビュー基準を明文化**

ai-publishing-house 内に `editor-checklist.md` を作成。文体、ファクトチェック、図解、構成、SEO の5観点でチェック項目を定義。編集者エージェントはこれを必ず通す。

**3. delivery-manifest.md で問題点を記録**

REVISION_NEEDED で差し戻すたびに、`delivery-manifest.md` の「**Editor Review Result**」欄に具体的な問題点を記録する。ai-publishing-house 側はそれを読んで次回に活かす。

### 結果

3つの改善を3ヶ月続けた結果、APPROVED率は約 **80%** まで上昇した。

```
発注10件
   ↓
納品10件
   ↓
APPROVED: 8件
REVISION_NEEDED: 2件
```

完全には100%にはならない。なるべきでもないと思っている。**100% APPROVED は、編集レビューが甘い証拠**だ。20%が REVISION_NEEDED になる状態は、健全な品質管理が回っている証拠でもある。

### 学んだこと

**品質は最初から安定しない**。これが現実だ。

新しい仕組みを始めたとき、最初の1-2ヶ月は品質が不安定なのが普通。これを「**ダメな仕組みだ**」と諦めると、永遠に良くならない。

**フィードバックループを回し続ける**。何が悪かったか記録する、改善案を実装する、次回試す。これを3ヶ月続ければ、確実に品質は上がる。

「**最初から完璧を求めない**」「**改善のループを設計する**」——これがai-publishing-house の品質改善で学んだ原則だ。

> **品質は最初から安定しない。発注書を詳細化、編集基準を明文化、フィードバックループを記録する——この3つを3ヶ月続ければ、APPROVED率は5割から8割になる。**

## 原点の失敗を捨てなかったから、戦略γに移れた

5つ目の失敗——というより**原点の失敗**を振り返る。

### 何が起きたか

Ch.00 で告白したとおり、本書のすべての出発点は「**半自動投稿システムは完成したが投稿実績は0件**」という失敗だった。

2026年2月、5チャネルへの半自動投稿システムを完成させた。コマンドを叩けば投稿文が出てきた。3週間で1本も公開できなかった。

この失敗から「**仕組みを作るだけでは回らない、組織として回す必要がある**」という発想に至り、1人総合商社の設計に向かった。

### 戦略γへのピボット

執筆時点（2026年5月）、私は別の大きなピボットを経験している。**戦略γへの転換**だ。

これまでの戦略は「**note 週刊AI検証**」を主軸にマネタイズする方針だった。note の有料記事と Mexilia でフォロワーを増やして、月額収益化を目指していた。

だが、3ヶ月運用してみると、note の伸びが想定より遅かった。フォロワーは4週連続で増えなかった。週刊ピックアップ記事は安定して公開できているが、収益化に直結しない。

そこで戦略γにピボットした。「**Zenn Book 自力出版**」を主軸に切り替える。Zenn Book ¥1,980 × 月28冊 = 月¥53,940。これが現実的な月5万円ラインだ。

そして、その第一弾として書いているのが、本書だ。

:::message alert
**【第2版からの追記】この予測は外れた。**

「月28冊」に対し、**8ヶ月で実際に売れたのは2冊**（累計 ¥3,385）。約140分の1である。

さらに悪いことに、私はこのピボットを決めた1週間後（2026-05-31）に、**Zenn Books そのものを「着手禁止」として封印している**。封印した形式が、結果的に唯一の収益源になった。

なぜその判断を下したのか、何を見落としていたのかは **Ch.15** で全部書く。この予測を消さずに残しておくのは、**外れた予測こそが本書でいちばん価値のあるデータ**だからだ。
:::

### ピボットができた理由

ここで重要なことを書いておきたい。

私が戦略γにピボットできたのは、**それまでの失敗を捨てなかったから**だ。

- 半自動投稿システム0件 → 1人総合商社の設計に活用
- 29個→25個収束 → エージェント設計の原則を確立
- ブログ@Doing 26件持ち越し → WIP制御の重要性を学習
- ai-publishing-house 初期5割 → 発注書テンプレートを整備

これらの失敗が積み重なっていたから、戦略γで「**Zenn Book を自力出版**」と決めたとき、すでに**書くための基盤が揃っていた**。CLAUDE.md、Skill、エージェント組織、content-pipeline、品質保証ツール——すべて過去の失敗から学んで作ったものだ。

もし最初から戦略γを目指していたら、たぶん書けていなかった。**遠回りの失敗の蓄積が、ピボット時の俊敏性を生んだ**。

### 学んだこと

**失敗は資産**だ。

短期的には、失敗は時間とコストの損失に見える。だが、長期的には、失敗から作った仕組みが**次のピボットを支える土台**になる。

「**捨てる失敗**」と「**残す失敗**」の判別が重要だ。

| 捨てる失敗 | 残す失敗 |
|----------|---------|
| 同じことを繰り返した失敗 | 違うアプローチで学びがあった失敗 |
| 学びが言語化できない失敗 | 仕組みとして残せる失敗 |
| 感情的な失敗（モチベ低下等） | 構造的な失敗（設計の問題等） |

私の3ヶ月の失敗の多くは、右側（残す失敗）だった。だから戦略γへのピボットができた。**失敗の質**を高めることが、ピボットの可能性を残す。

> **失敗を捨てなければ、失敗が資産になる。残した失敗が、次のピボットの土台になる。失敗の質を高めることが、長期戦略の柔軟性を生む。**

## 3ヶ月運用で確信したメタ原則

5つの失敗事例を扱った。ここから抽出したメタ原則を、改めて整理する。

本書全体を貫く原則として、3つに凝縮する。

### メタ原則1: 完璧主義を捨て、機能する不完全さを取る

**完璧な設計**を目指すと、運用が始まらない。

「**もう少し練ってから**」「**完成度を上げてから**」と先延ばしすると、永遠に運用に入れない。私の半自動投稿システム0件、note 5週持ち越し、Skill 暴走——これらの根底にある共通項は「**完璧主義**」だ。

逆に、**機能する不完全さ**を許容すると、運用が始まる。

```
× 完璧な発注書を書いてから ai-publishing-house に渡す
○ 雑な発注書でも先に渡して、REVISION_NEEDED で修正していく
```

不完全な状態で公開した記事は、後から修正できる。逆に、未公開のまま完璧を目指した記事は、永遠に公開されない。**動いている不完全 > 動かない完璧**。

これが副業を続ける上での最大の心理的ハードルだ。私は今も完全には脱せていない。だが、意識して「**機能する不完全さ**」を取りに行く運用ルールを作っている。「**毎週金曜19:00は公開専用時間**」のように。

### メタ原則2: 廃止と統合を恐れない

増やすのは簡単だ。減らすのは難しい。

エージェント、Skill、チャネル、コマンド、ルール——すべて増やすときは「**便利かも**」と思って増やす。だが、増やすたびに**判断コスト**と**メンテナンスコスト**が増える。

定期的に減らす運用が必要だ。私は月末に「**廃棄レビュー**」をする。先月作ったエージェント、Skill、ルールを見直して、使われていないものを廃棄する。3週間以上持ち越されたタスクも見直す。

「**廃止と統合を恐れない**」。29個→25個の収束、x-tips の archive、ブログ@Doing の13件廃棄——これらはすべて「**減らす勇気**」が生んだ成果だ。

増やす量と減らす量を等しく保つ。これが組織を健全に保つ。**増減のバランスが、組織の生命線**だ。

### メタ原則3: 仕組みは目的化した瞬間に副業を止める

最後の原則は、もっとも大事だ。

**仕組み作りに夢中になると、副業の本来の目的（コンテンツ公開・収益化）が止まる**。

私はこの罠に何度も落ちた。Skill を50個書いた週、エージェントを29個に増やした週、ai-publishing-house の設計を3週間練り続けた時期——いずれも**コンテンツの公開はほぼゼロ**だった。

仕組み作りは楽しい。手応えがある。新しい設計を考えるのは、書くより楽だ。だから、無意識に仕組み作りに逃げてしまう。

逃げを防ぐ運用ルール:

- **毎週、最低1本は公開する**: 仕組みを触る前に、まず公開する
- **仕組みの改善は週末に集中**: 平日は運用専念
- **「これは何のための仕組み改善か」を毎回問う**: 目的があれば改善する、なければ後回し

「**仕組みは手段**」——これを常に意識し続けないと、目的化する。

> **3つのメタ原則: ①完璧主義を捨て、機能する不完全さを取る ②廃止と統合を恐れない ③仕組みは目的化した瞬間に副業を止める。**

## アンチパターン3つ

### NG1: 失敗を隠して設計図だけ公開する

**症状**:
- 「私の Vault は完璧に動いています」と発信する
- 失敗事例を隠す
- 読者が「自分はダメだ」と感じる

**処方箋**:
- 失敗を全公開する
- 失敗から導いた原則を語る
- 「**私もそうだった**」を読者に伝えるのが、運用ノウハウの真の価値

### NG2: 失敗を「次は気合いで克服する」と考える

**症状**:
- 失敗の原因を「やる気不足」「時間不足」に帰着させる
- 次回も同じ失敗を繰り返す
- 改善が積み重ならない

**処方箋**:
- 失敗の原因を**構造的に分析**する（仕組みの問題、設計の問題）
- 同じ失敗を繰り返さないための**運用ルール**を作る
- 気合いではなく構造で対処する

### NG3: 仕組み作りを「目的」と勘違いする

**症状**:
- 新しい Skill を作るのに夢中になる
- コンテンツ公開が止まる
- 「設計が完璧になったら公開する」と思っている

**処方箋**:
- 仕組みは手段、コンテンツ公開が目的
- 毎週1本は必ず公開する
- 仕組み改善は週末に集中、平日は運用専念

### あなたは完成形から始められる

私はここに至るまでに、3ヶ月の試行錯誤を要した。29個まで増やしてから25個に減らした。x-tips を作って24投稿で廃止した。ブログ@Doing 26件を6週間放置した。Skill を暴走させた。ai-publishing-house の APPROVED率を5割から8割に上げるまで3ヶ月かかった。

**あなたは、これらを経験せずに完成形から始められる**。

本書のテンプレート、設計図、アンチパターン集をコピーして、自分の文脈に合わせれば、私が3ヶ月かけて踏んだ地雷の大半を踏まずに済む。

これが本書の最大の価値だ。

### だが、あなたも必ず失敗する

ただし、これも約束する。

**あなたも必ず失敗する**。

私の設計図をそのままコピーしても、あなたのコンテキスト、本業、家族構成、得意領域、苦手領域——すべてが私と違う。だから、あなた固有の失敗が必ず発生する。

そのときに、本書のメタ原則を思い出してほしい。

1. **完璧主義を捨て、機能する不完全さを取る**
2. **廃止と統合を恐れない**
3. **仕組みは目的化した瞬間に副業を止める**

これらは、設計図ではなく**運用思想**だ。あなたの失敗の中身が私と違っても、対処の思想は共通している。

### 1人総合商社は「育てる」ものだ

最後に、1人総合商社は「**作る**」ものではなく「**育てる**」ものだということを書いておきたい。

本書では「**設計図**」という言葉を多用してきた。だが、設計図を引いて完成、ではない。**毎日少しずつ運用しながら、廃止と統合と改善を繰り返して**、徐々に育てていく。

私の Vault は今も完成形ではない。来週には何かが追加され、何かが廃止される。毎週、毎月、少しずつ形が変わる。それでいい。**変わり続けることが、1人総合商社の生命**だ。

### あなたへの呼びかけ

本書を読み終えたら、まず1つだけ実装してほしい。

「**1つだけ**」がポイントだ。本書には設計図が大量に詰まっているが、一気に実装しないでほしい。

最初に実装するなら、私の推奨は **Ch.03 の Skill** だ。`/daily` のような、毎日叩く小さな Skill を1つ書いてみる。それが定着したら、`/coo-briefing` のような次の Skill を書く。3ヶ月で5-10個の Skill が定着したら、エージェント組織に進む。

**1日 5-10分の Skill から始める**。これが1人総合商社のスタート地点だ。

私は3ヶ月で 68コマンド / 25エージェント / 5チャネルまで来た。あなたも、1日 5-10分の積み重ねから、ここに辿り着ける。

完成形から始められるあなたが、私より速く、より遠くに行けることを願っている。
