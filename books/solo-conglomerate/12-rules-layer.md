# rules層──エージェントに「憲法」を与える

## 呼ばれていないときに守るべきことを、どこに書くか

初版の設計には穴があった。3ヶ月運用して、その穴から事故が落ちてきて、ようやく気づいた。

Claude Codeでエージェント組織を組むとき、私たちは主に2つの場所にルールを書く。

| 場所 | 書けること | 効くタイミング |
|------|-----------|--------------|
| `.claude/agents/*.md` | そのエージェントの役割・専門性・口調 | **そのエージェントが呼ばれたとき** |
| `.claude/commands/*.md` | その手順の具体的なステップ | **そのコマンドが叩かれたとき** |

どちらも「呼ばれたときに何をするか」しか書けない。

では、**呼ばれていないときに守るべきこと**はどこに書くのか。

たとえば「記事に書く数値には必ず取得日を付ける」。これは特定のエージェントの仕事ではない。ブログを書くときも、noteを書くときも、Zennを書くときも、私が手で書くときも守るべきことだ。エージェント定義に書けば、そのエージェントを経由しない経路で破られる。コマンドに書けば、そのコマンドを使わない日に破られる。

**横断する制約を、縦の階層に書くと必ず漏れる。**

私はこれを「rules層」として分離した。現在7本ある。

```
.claude/rules/
├── factcheck-metadata.md          # 2026-03-04
├── blog-slug-metadata.md          # 2026-03-14
├── content-visual-generation.md   # 2026-03-14
├── completeness-freshness-critic.md # 2026-06-01 ★初版後
├── spiral-writing-integration.md  # 2026-06-12 ★初版後
├── ai-draft-interrogation.md      # 2026-08-24 ★初版後
└── hit-content-patterns.md        # 2026-08-24 ★初版後
```

初版執筆時点では3本。3ヶ月で4本増えた。**この4本は全部、事故から生まれている。**

## ルールは思想からは生まれない

先に結論を書く。私が失敗したのは、**最初に理想のルールセットを設計しようとしたこと**だった。

「AIに書かせるならこういう品質基準が要るだろう」と机の上で考えて作ったルールは、ほぼ使われなかった。抽象的すぎて、エージェントが読んでも行動が変わらないからだ。「品質の高い記事を書く」と書いてあるルールは、無いのと同じである。

いま生きている7本は、すべて**具体的な事故の再発防止として**書かれている。だから条文が異様に細かい。細かいのは正しい。

順に、どの事故が何を生んだかを書く。

## 事故1: 「正しいが古い」を誰も見ていなかった

### 何が起きたか

2026年5月、ローカルLLM環境の解説記事を公開した。ファクトチェックは通っていた。書いてある事実に誤りは無かった。

しかし記事は**使い物にならなかった**。

- 記事が「環境変数で接続する」と曖昧に書いていた手順は、その時点で公式が `ollama launch claude` という専用コマンドを提供していた。検証機でも使えた。私は知らずに、遠回りの手順を書いていた
- 推奨モデルとして挙げたのが1世代前の `qwen2.5-coder` だった。当時すでに `qwen3-coder` が出ていた
- さらに悪いことに、本文に「📝執筆メモ: ファクトチェック必須」という**内部注記が残ったまま公開されていた**

### なぜファクトチェックを通過したのか

ここが構造的な話だ。

ファクトチェックは「**書いてあることが正しいか**」を検査する。「環境変数で接続する」は、当時も間違いではなかった。「`qwen2.5-coder` は使える」も嘘ではない。だから全部通る。

誰も検査していなかったのは、この2つだ。

- **欠落（omission）**: 本来書くべきことが書かれていない
- **陳腐化（staleness）**: 正しいが古い

そして重要なのは、**この2つは同じネガティブスペースの盲点だ**ということだ。どちらも「ドラフトに書かれていないもの」を見る作業であり、ドラフトを読んでいる限り永久に見つからない。

工程の全員が「ドラフトに既に書かれている主張」だけを検査していた。これが穴の正体だった。

### 何を変えたか

`completeness-freshness-critic.md` を書いた。中核は3つ。

**① as-of アンカーを最初に打つ**

制作開始時に日付を確定し、以降の「最新か否か」の判断を全部その日付基準に固定する。

```bash
bash 07_System/Scripts/get-date-info.sh
```

曖昧な「最新」を禁止し、「2026-08-29時点で最新」に置き換える。

**② 独立参照セットを作る（ドラフトを見ずに）**

これが肝だ。ドラフトの記述に引きずられないよう、**ドラフトを読む前に**テーマの現在地をWebから取り直す。

- `[テーマ] [年]`
- `[ツール名] changelog` / `release notes`
- `[分野] 推奨モデル [年]`
- 公式リリースノート・GitHub Releases・モデルライブラリページに直接当たる

こうして作った「あるべき姿」と、ドラフトを**差分する**。ドラフト内の主張を検証するのではない。**ドラフトの外から、欠落を照らす。**

**③ 機械判定できるものだけハードブロックにする**

これは運用上いちばん重要な設計判断だった。

| 検出物 | 強度 |
|--------|------|
| `TODO` `要確認` `📝執筆メモ` `ファクトチェック必須` の残存 | **ハードブロック** |
| 欠落・陳腐化の疑い | 警告＋人間の承認 |
| 「最新を確認してください」等の逃げ表現 | 差し戻し候補（警告） |

ハードブロックは1種類だけにした。内部注記の残存は正規表現で100%検出でき、誤検出がゼロで、かつ読者に出してはいけないものだからだ。

一方「欠落」の判定は、どうしても過検出する。意図的に範囲外にした話題まで「書かれていない」と指摘してくる。これをハードブロックにすると、**私はルールを無効化する側に回る**。無効化されたルールは存在しないのと同じだ。

> **ゲートを増やすほど安全になるのではない。無効化されないゲートだけが安全を作る。**

### 学んだこと

`ファクトチェック: 済` というメタデータが、**検査していない軸まで安全だと誤保証していた**。これがいちばん怖かった。

だから軸を分離した。1つの「済」が意味する範囲を、明示的に狭くした。

```markdown
- **ファクトチェック**: 済（2026-08-29 Genspark / [[レポート]]）
- **鮮度レビュー**: 済（2026-08-29 as-of 2026-08-29 / Outdated: 0件）
- **網羅性レビュー**: 済（2026-08-29 critic / Missing: 2件）
- **尋問・引き算**: 済（2026-08-29 / 補強: 4箇所 / 削減: 5,200字→4,300字 -17% / 体験証拠: あり）
```

**「済」は、実際に検査した軸のみ安全を意味する。** 当たり前のことだが、軸が1本しか無いときは、この当たり前が破れる。

## 事故2: 全部通過してなお「どこかで読んだ話」だった

### 何が起きたか

上のルールを入れた後、記事は「正しく・最新で・網羅的」になった。それでも読み返すと、**面白くなかった。**

自分の記事33本を機械的に調べてみた。一人称の観測を示す語（`筆者` `試し` `やってみ` `感じた` `印象` `使ってみ`）の出現数を数えたら、こうなった。

**33本中11本（33%）が、一人称の観測ゼロ。**

全部のゲートを通過した記事が、3本に1本の割合で「自分がどこにも居ない記事」だった。事実が正しく、最新で、抜けも無い。そして**誰が書いても同じ**。

さらにチャネル別に分解すると、穴の位置が違うことがわかった。

| チャネル | 一人称の観測 | 設計理由 |
|---------|------------|---------|
| ブログ | 33本中11本が**ゼロ** | 薄い |
| note | 平均2〜5件で**強い** | **0〜1件** |
| Zenn | 0〜2件 | 0〜2件（2本はゼロ） |

同じ症状に見えて、noteは「体験はあるが、なぜそうなっているかの説明が無い」、ブログは「説明はあるが、自分が居ない」。**処方が逆だった。**

### 何を変えたか

`ai-draft-interrogation.md` を書いた。3工程ある。

**Step 1: 尋問（Interrogate）** — AI初稿を完成品ではなく**教材**として読み、各H2に4系統の問いを当てる。

| 系統 | 問い | 不合格の典型 |
|------|------|-------------|
| 根拠 | 一次情報は何か。出典URLと取得日は | 「〜とされています」で出典なし |
| **設計理由** | なぜこの仕様はこの形なのか。**検討された代替案**は | 挙動の説明だけ |
| **選定理由** | なぜこれを選ぶのか。**棄却した候補と理由**は | 「人気だから」 |
| 読者理解 | 前置きなしにコードが登場していないか | H2直後にいきなりコードブロック |

答えられない項目は**調べるか、落とす**。曖昧なまま残さない。

設計理由を書くには、リファレンスでは足りない。**公式の設計ドキュメント / RFC / GitHubのIssue・PR・Discussion / リリースノートの「なぜ変えたか」節**に当たる必要がある。リファレンスだけ読むと、挙動しか書けない。

**Step 2: 体験の証拠（Execution Evidence）** — ここだけはAIが生成できない。

実行環境（機種・OS・バージョン）、手元の出力（公式のコピペではなく自分が実行した結果）、詰まった箇所（**エラーメッセージの原文**）、操作感・見た目。

そして最重要の条項がこれだ。

> **実行していないなら、実行したふりをしない。**

未実行なら本文に明記する。

```markdown
> ※本節は公式ドキュメントに基づく記述で、筆者環境での実行検証は行っていません（2026-08時点）。
```

**「未検証」と書けば記事は死なない。書かずに実行した体裁をとることだけが信頼を壊す。**

**Step 3: 引き算（Reduce）** — 補強で膨らんだ本文を10〜20%削る。

AI冗長の定型は機械検出できる。

```
〜と言えるでしょう | 〜ではないでしょうか | 重要です | 欠かせません
様々な | 多岐にわたる | 〜する上で | 注目されています
と言っても過言では | 効率化を図る | 活用することで
```

削る優先順位は、①言い換え反復（同じ内容を語を変えて2回）②一般論の前置き（「近年、AIの活用が進んでいます」型）③重複した用語説明 ④新情報のない「まとめ」段落。

検査は1コマンドにした。

```bash
bash 07_System/Scripts/draft-critic.sh <記事ファイル>
```

AI冗長定型の出現箇所 / 体験証拠マーカーの有無 / 前置きなしコードブロック を一括レポートする。

### 学んだこと

**字数の下限は、冗長の免罪符になる。**

「ブログは2000-4000字」という基準を置いていたせいで、薄い記事が水増しで基準を満たしていた。下限があると、AIは必ず埋める。埋め方は言い換えの反復である。

だから引き算工程を**独立した強制ステップ**として置いた。「余裕があれば削る」では絶対に削られない。

## 事故3: 自分のタイトルが、ヒット記事の正反対だった

### 何が起きたか

蓄積していたトレンド収集データ（200日分）から、はてなブックマーク500users超の記事97本を抽出し、自分のブログ16本と定量比較した。

結果がこれだ。

| 指標 | ヒット97本 | 私の16本 |
|------|-----------|---------|
| タイトル長（中央値） | **29字** | **58字** |
| `【】`・絵文字で始まる | 11% | **94%** |
| 「2026年」を含む | 8% | **62%** |
| 「完全ガイド／徹底解説」 | 9% | **50%** |
| **効果値の数字（%・倍・件）** | **32%** | **0%** |

全項目が逆だった。しかも数字の使い方が決定的に違う。ヒット記事は**効果**に数字を使い、私は**年号**に数字を使っていた。

`【2026年最新】〇〇完全ガイド` という、私の定番フォーマットは、タイトルの一等地を情報量ゼロの記号で埋めていたことになる。

### 何を変えたか

`hit-content-patterns.md` を書いた。中身は5則あるが、効いたのは2つだ。

**則1: 数字は年号ではなく効果に使う**

`80%削減` `748例` `11モデル` `4ツール中1つだけ`。鮮度は本文の `※2026年8月時点` に降ろす。タイトルに年号は要らない。

そして**タイトルを1本にしない**という設計にした。

| 用途 | 設計 |
|------|------|
| 記事タイトル（h1・SNS共有時に出る） | 29字前後・修飾語ゼロ・固有名詞は前半 |
| SEO title / meta description | キーワードを機械的に詰める |
| X / note用の紹介文 | さらに振り切る |

**則2: リードの定型を禁止する**

ヒット97本に1件も存在しなかった定型を、名指しで禁止した。

```
〇〇で困っていませんか？
この記事は以下のような方に向けて書いています：
この記事のポイント
```

代わりに置いたのが、**読者の内心をカギカッコで引用して始める**型だ。

> 「Claude Code、思ったより速くならないな」と感じているなら

読者属性の列挙は書かない。**内心の引用が属性の代わりになる。**

（本書の初版Ch.00には「本書は次のような人に向けて書いている」という定型があった。この改訂版で書き直したのは、このルールに従った結果である。）

### 学んだことと、その後の訂正

ただし、このルールには**私が後で撤回した条項**がある。

初版のルールは「29字に収める」を強く押していた。実際に短くしてみると、**「何の記事か分からない」タイトル**が量産された。効果数値だけが残って固有名詞が落ちるからだ。しかも私のブログ環境ではSEOタイトルの分離設定が効かないことが後で判明し、「短いタイトルで検索流入も死ぬ」という最悪の組み合わせになりかけた。

そこで優先順位を明示的に書き換えた。

> **29字より固有名詞が優先。**

ルールに数値目標を書くときは、**その数値が他の要件と衝突したときどちらが勝つか**まで書かないと事故る。「29字以内」だけ書かれたルールは、29字のために意味を捨てる。

## rules層の設計原則（7本から抽出）

7本を運用してわかった、書くときの原則をまとめる。

### 原則1: 適用対象のマトリクスを必ず書く

全ルールに、チャネル別の適用範囲表を置いている。

| チャネル | 適用 |
|---------|------|
| ブログ | 全則 |
| note | 全則 |
| Zenn | Step 1・Step 3のみ |
| リベシティ | Step 2・Step 3のみ（コミュニティのトーンを優先） |
| X / Borders | 対象外（短文のため） |

これが無いルールは、必ず「守るべきでない場所」で発動して邪魔になる。邪魔になったルールは無効化される。

### 原則2: スキップ条件を明記する

```
- 本文300字未満
- ニュース速報（quick）— 事実の鮮度が主価値
- `--no-interrogate` 明示指定
```

**逃げ道を公式に用意する。** 用意しないと、非公式に逃げられる。非公式な迂回は記録に残らないので、ルールが機能していないことに気づけない。

### 原則3: 順序を固定する

複数のルールが同じ本文を書き換えるとき、順序が壊れると保証が消える。

```
ドラフト確定
  → 【尋問】→【体験の証拠】→【引き算】   ← 本文を書き換える工程
  → Spiral（文体の適用）                  ← 本文を書き換える工程
  → factcheck / 鮮度・網羅性クリティック   ← 本文を検証する工程
  → 公開
```

**書き換える工程は、検証する工程より必ず前に置く。** 検証済みの事実記述を後から書き換えたら、検証の意味が消えるからだ。当たり前に見えるが、ルールを1本ずつ足していくと簡単に逆転する。私は一度逆転させた。

### 原則4: 「なぜこのルールがあるか」を条文の中に書く

7本すべての冒頭に「## 背景」節がある。そこに事故の記録と実測値が書いてある。

理由が書いていないルールは、半年後の自分が消す。**未来の自分は、過去の自分が何を踏んだか知らない。**

## アンチパターン3つ

### NG1: 理想の品質基準を先に設計する

「良い記事とは」から始めると、抽象的で行動を変えないルールができる。**事故が起きるまで、そのルールは書けない。** 空のrules層から始めて、踏んだ地雷の数だけ増やすのが正しい。

### NG2: 全部をハードブロックにする

過検出するゲートをブロックにすると、書き手はゲートを無効化する側に回る。**誤検出しうる判定は必ず「警告＋人間の承認」にする。** 私のハードブロックは7本のルールを通じて1種類だけだ。

### NG3: エージェント定義に横断ルールを書く

「このエージェントは出典を必ず書く」と書くと、そのエージェントを経由しない経路で破られる。**横断する制約は横断する層に置く。** これがrules層を分離した理由そのものである。

## まとめ

- エージェント定義とコマンドは「呼ばれたとき」しか効かない。**横断する制約を書く層が別に要る**
- ルールは思想からではなく**事故から**生まれる。初版後に増えた4本はすべて実害の再発防止
- 検査していない軸まで「済」が保証してしまう事故を防ぐため、**軸を分離して個別に記録する**
- ハードブロックは**機械判定で誤検出ゼロのものだけ**。それ以外は警告にする。無効化されないゲートだけが安全を作る
- 全ルールに**適用マトリクス・スキップ条件・順序・背景**の4点を書く

次章では、このルール層を持った組織を**私が寝ている間に動かす**話をする。GitHub Actionsによる無人運用と、無人だからこそ起きる事故の話だ。
