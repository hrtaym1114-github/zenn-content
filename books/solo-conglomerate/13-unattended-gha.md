# 無人運用──寝ている間に動く組織

## 半自動の天井

初版で書いた組織には、明示していなかった前提がひとつある。

**すべての処理が「私がClaude Codeを起動している間」にしか動かない。**

これは思っていたより重い制約だった。エージェントを29人ぶん定義しても、私がターミナルを開かなければ全員が休んでいる。組織図があるだけで、稼働率は私の在席時間に完全に従属していた。

平日は本業がある。帰宅後に使えるのは実質1〜2時間。その1〜2時間に「今日のトレンドを集める」「昨日の投稿の反応を見る」といった**定型作業を詰め込むと、判断する時間が残らない**。

エージェント組織を作った目的は、私の時間を判断に集中させることだったはずだ。それなのに、私は毎晩「収集コマンドを叩く人」をやっていた。

現在、この層は19本のGitHub Actionsワークフローが引き受けている。私の在席と無関係に動く。

```
JST 4:13  neta-trend-daily      トレンド収集（はてブ/HN/Reddit/GitHub）
JST 6:13  neta-borders-daily    社内向けニュース収集
JST 7:00  x-follower-sprint     引用投稿候補の生成とダイジェスト送信
JST 8:00  x-daily-planning      当日の投稿計画
JST 8:00  weekly-x-mfg-ai-news  週次ニュース投稿（月）
JST 各時  x-auto-post           予約投稿の実行
JST 21:00 weekly-review         週次レビュー（金）
JST 22:00 x-engagement-analysis エンゲージメント分析（月・木）
JST 2:13  daily-routine         日次ルーティン
```

そして無効化されたワークフローが11本ある。**廃棄した数が、試した仮説の数だ。**

この章では無人層の作り方と、**無人化したからこそ起きた事故**を書く。後者のほうが価値がある。動くものを作るのは簡単で、動き続けさせるのが難しいからだ。

## 基本形──GitHub ActionsでClaude Codeを走らせる

構造そのものは単純だ。`anthropics/claude-code-action` にプロンプトを渡し、生成物をコミットして push する。

```yaml
name: Neta Trend Daily Collection

on:
  schedule:
    # JST 4:13 AM = UTC 19:13（前日）— 分をずらしてスケジューラ混雑を回避
    - cron: '13 19 * * *'
  workflow_dispatch:

concurrency:
  group: neta-trend-daily
  cancel-in-progress: true

jobs:
  collect-trends:
    runs-on: ubuntu-latest
    timeout-minutes: 45
    permissions:
      contents: write
      id-token: write
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 1

      - uses: anthropics/claude-code-action@v1
        with:
          claude_code_oauth_token: ${{ secrets.CLAUDE_CODE_OAUTH_TOKEN }}
          prompt: |
            トレンドネタ収集を実行してください。
            1. `.claude/skills/neta-trend-daily/SKILL.md` を読み込んでください。
            2. SKILL.mdの手順に従って実行
            ...
          claude_args: |
            --max-turns 60
            --allowedTools "Read,Write,Edit,WebFetch,WebSearch,Bash,Glob,Grep"

      - name: Push changes
        run: |
          git config user.name "github-actions[bot]"
          git add .
          git diff --staged --quiet || git commit -m "trend: $(TZ=Asia/Tokyo date +%Y-%m-%d) トレンド収集"
          git push || echo "Nothing to push"
```

ここに、実運用で刻んだ設計判断がいくつも埋まっている。順に解説する。

### 判断1: プロンプトに手順を書かず、スキルを読ませる

プロンプト本体は「SKILL.mdを読んで、その手順に従え」の3行しかない。実際の手順は `.claude/skills/neta-trend-daily/SKILL.md` にある。

理由は、**手順をYAMLに書くと、ローカル実行とCI実行で手順が二重管理になる**からだ。二重管理されたものは必ずズレる。ズレたことに気づくのは、片方が壊れたときだ。

スキルを唯一の正本にして、GHAはそれを呼ぶだけの薄い殻にする。この形にしてから、ローカルで直した修正が翌朝のCIにそのまま効くようになった。

### 判断2: CI環境であることを明示的に伝える

```
## CI環境での注意事項（必読）
- これはCI環境です。CLAUDE.mdは読み込まないでください（不要）
- プロキシ設定は不要です
- Agent, Skill, TodoWrite等のツールは使用不可
- Redditはcurlで取得（User-Agent必須、WebFetchではブロックされる）
- 一部ソースが失敗しても取得できたソースで続行
```

無人実行では**Claudeが困っても誰も答えない**。ローカルなら「これどうしますか？」と聞いて私が答える場面が、CIでは全部「勝手な判断」になる。

だから**分岐しそうな箇所を先回りして全部潰す**。「一部ソースが失敗しても続行」の1行は、これが無いと1ソースの404で全体が停止して、その日の収集がゼロになる。

最後の行は実際に踏んだ罠だ。RedditはWebFetchのUser-Agentをbotとして弾く。curlに `User-Agent` を付ければ通る。**この1行が無かった日、Redditだけ毎日空だった。**

### 判断3: ターン数の節約を明示的に指示する

```
## 効率化（重要 — ターン数節約）
- **データ収集フェーズではすべてBashで一括取得すること**。1ソースずつWebFetchを呼ばない
- はてブ6ページ: 1つのBashコマンドでcurl+ループ→1ファイルに結合
- Reddit 13サブレッド: 1つのBashコマンドでforループ→1ファイルに結合
- **目標: 収集は5-8ターン以内、分析+出力は3-5ターン以内**
```

無人実行にはターン上限がある。上限は「打ち切り」ではなく、後述するように**失敗**になる。だから収集系は「1リソース1ツール呼び出し」をやめさせ、Bashのループで一括取得させる。

ここは**指示しないと必ず律儀に1件ずつ取りに行く**。20ソースあれば20ターン使う。ループを1つ書けば1ターンで済む。

### 判断4: cronの「分」をずらす

```yaml
- cron: '13 19 * * *'   # :00 ではなく :13
```

GitHub Actionsのスケジュールは、**毎時0分に世界中のジョブが集中して、遅延やスキップが起きる**。ドキュメントにも「混雑時は遅れることがある」と書いてある。

私は最初、素直に `0 19 * * *` と書いていた。走らない日がぽつぽつ出た。エラーではない。**実行記録そのものが無い。** 分をずらしてから、この症状は消えた。

無人運用の初期に、いちばん時間を溶かしたのがこの種の「エラーが出ないまま動かない」だった。

### 判断5: concurrency で自分自身の多重起動を止める

```yaml
concurrency:
  group: neta-trend-daily
  cancel-in-progress: true
```

手動実行と定時実行がぶつかると、同じファイルを2つのジョブが書いてコンフリクトする。**エージェント組織のファイル所有権ルール（Ch.04）を、CIのレイヤーでもう一度やる**必要がある。

## 事故1: 成果物が完成しているのに、失敗扱いで消える

これは無人運用で最も高くついた事故だ。

### 何が起きたか

2026年8月9日と8月11日、社内向けニュース収集のワークフローが失敗した。ログを見ると、Claudeは**記事を最後まで書き終えていた**。それなのにジョブは exit 1 で終わり、その後の push ステップがスキップされ、**生成物はリモートに1文字も残らなかった**。

原因は `--max-turns` だった。設定が30、実際に使ったターンが31。

ここが直感に反する。`--max-turns` は「N ターンで打ち切って、そこまでの結果を返す」ではない。**「Nターンを超えて成功結果を返したこと」自体をエラーとみなす。** 完成していても失敗になる。

8月8日までは30ターン以内に収まっていた。収集ソースが1つ増えただけで越えた。**閾値ぎりぎりで動いているシステムは、いつか必ず越える。**

### 何を変えたか

3点セットで対処した。

**① max-turns に余裕を持たせる**

30 → 60 に上げた。収集系は50〜60が安全だった。ターン数を節約するプロンプト（判断3）と組み合わせて、実際の消費は10〜20ターンに収まっている。**上限は実測の3倍に置く。**

**② push ステップを、失敗しても走らせる**

```yaml
      - name: Push changes
        if: ${{ !cancelled() }}
        run: |
          git add .
          git diff --staged --quiet || git commit -m "..."
          git push || echo "Nothing to push"
```

`!cancelled()` を付けると、前のステップが失敗しても push が走る。`git diff --staged --quiet` のガードがあるので、生成物が無ければ空コミットにはならない。

**成果物があるなら、ジョブの成否と無関係に保存する。** これが正しい設計だった。ジョブの成否は「Claudeが規定ターン内に終わったか」を表しているだけで、「成果物ができたか」とは別の情報である。

**③ 失敗しても、ファイルは失われていない**

これは知っておくと救われる。GitHub Actionsのログには、Claudeが実行したツールの結果が**JSONエスケープされた文字列としてそのまま残っている**。

```bash
gh run view <run-id> --log-failed
```

このログの中の Write ツールの `tool_use_result.content` に、**生成したファイルの完全な内容**が入っている。Pythonで `json.loads` すれば復元できる。

私は実際にこの方法で、失われたはずの記事を1本まるごと復元した。**成果物は消えていない。pushされていないだけだ。**

### 正直な現状

この本を書きながら、自分のワークフロー19本を点検した。

**`!cancelled()` ガードが入っているのは1本だけだった。**

事故を踏んだ borders のワークフローは直した。**残り11本のClaude実行ワークフローには、同じ地雷が刺さったままだ。** トレンド収集も、週次レビューも、X投稿計画も、全部そうだ。

私は「その日困ったものだけ直して、同じ形状の他を放置していた」ことになる。これは仕組みの問題ではなく、**修正を横展開する工程が組織に無い**という設計の欠落だ。

無人運用は、壊れても誰も困らない時間帯に静かに壊れる。だから**「同じ形の場所が他にいくつあるか」を数える習慣**が、修正そのものより重要になる。

## 事故2: 予約したはずの時刻に投稿されない

### 何が起きたか

X.comへの予約投稿を cron で組んだ。指定時刻に投稿されるはずだった。

実測すると、**+43分から+1時間43分の遅延**が出た。

これは事故1と違ってバグではない。GitHub Actionsのスケジュール実行は**そもそも時刻を保証していない**。混雑時にはキューに積まれ、遅れて走る。分をずらしても、遅延そのものは消えない（消えるのは「完全にスキップされる」ほうだ）。

### 何を変えたか

**時刻が本質的な処理を、cronから外した。**

| 処理の性質 | 実行方式 |
|-----------|---------|
| 速報・時刻が意味を持つ投稿 | **pushトリガー**（ファイルを置いてpush→即実行） |
| 定型・多少ずれてよい収集 | cron（分をずらす） |
| 時刻厳守が必要なもの | そもそもGHAでやらない |

速報系は「予約ファイルを `@Doing` に置いて push すると、それを検知したワークフローが即座に投稿する」形に変えた。**cronで待つのをやめて、私のpushをトリガーにした。**

無人化を進めると「全部cronにしたくなる」が、これは間違いだ。**cronが向くのは「いつ動いてもいい処理」だけ**である。

## 事故3: 週1回・1件・狭い窓は、失敗が積み上がる

### 何が起きたか

メールマガジンを音声コンテンツに変換するパイプラインを、週1回のcronで組んだ。「直近数日ぶんのメールを検索して、あれば処理する」設計だ。

**3週間ぶん、無音で停止していた。**

原因は複合していた。検索窓が短すぎてメールを取りこぼした週があり、取りこぼすと次の週まで再試行の機会が無い。しかも1回の実行で1件しか処理しないので、一度落ちると**永久に追いつかない**。

そして何より、**失敗しても誰も気づかない**。毎週配信されるはずのものが配信されていないことに、私は3週間気づかなかった。

### 何を変えたか

無人ジョブの設計を3点変えた。

**① 頻度を上げる**: 週1 → **毎日**。失敗の回復機会を7倍にした。

**② 処理単位を「全件」にする**: 1件 → **未処理の全件**。1回落ちても次で追いつける。

**③ 検索窓を広げる**: 数日 → **60日**。取りこぼしを構造的に消す。

加えて、多重起動を防ぐ**直列ロック**を入れた（毎日走るようにしたので、前回が終わる前に次が始まりうる）。

まとめると原則はこうなる。

> **無人ジョブは「頻繁に・冪等に・全件を」処理させる。**
> 週1回・1件ずつ・狭い窓の組み合わせは、失敗が回復せずに積み上がる最悪の形状である。

冪等（何度実行しても同じ結果になる）にしておけば、頻度を上げることのコストはほぼゼロだ。逆に冪等でない処理を毎日走らせると、重複が積み上がる。**頻度を上げる前に、冪等にする。**

## 無人層に「気づく仕組み」を持たせる

3つの事故に共通するのは、**壊れたことに私が気づかなかった**点だ。

無人運用の本当の難しさはここにある。動いているものを作る難易度より、**動かなくなったことを知る難易度**のほうが高い。人間の作業なら、やらなければ自分でわかる。無人ジョブは、静かに何もしない。

私が置いている検知手段は3つだ。

| 手段 | 何を捕まえるか |
|------|--------------|
| 成果物ファイルの日付を見る | 「今日の収集ファイルが無い」= 昨夜落ちた |
| 週次レビューで実行履歴を集計 | 「先週このWFは0回しか走っていない」 |
| 出力が届く経路を人間側に寄せる | 毎朝メールで届く。**届かない日は気づく** |

3つめが実務的にいちばん効いた。**成果物を私の目の前まで運ぶ経路を作ると、経路が途切れたことが検知になる。** ダッシュボードを見に行く設計は、見に行かなくなった瞬間に死ぬ。

逆に、いまだに機能していない検知もある。エンゲージメント分析のように「出力が私に届くが、届かなくても困らない」ものは、止まっても気づかない。**困らない出力は、検知手段にならない。**

## アンチパターン3つ

### NG1: max-turnsを実測ぎりぎりに設定する

「20ターンで終わったから25にしよう」は必ず越える。ソースが1つ増えれば越える。**実測の3倍**を上限にして、代わりにプロンプト側でターン数を節約させる。

### NG2: 成果物の保存をジョブの成否に紐づける

ジョブの成否は「規定ターン内に終わったか」を表しているだけで、「成果物ができたか」とは別の情報だ。**push ステップは `!cancelled()` で必ず走らせ、差分ガードで空コミットだけ防ぐ。**

### NG3: 週1回・1件ずつ・狭い窓で組む

もっとも失敗が回復しない形状。**毎日・全件・広い窓**に倒す。そのために先に冪等にする。

## まとめ

- エージェント組織の稼働率は、無人層が無い限り**私の在席時間に従属する**
- GHAはスキルを呼ぶ薄い殻にする。手順をYAMLに書くと二重管理になり必ずズレる
- 無人実行では**Claudeが困っても誰も答えない**。分岐しそうな箇所を先回りして全部潰す
- `--max-turns` 超過は「打ち切り」ではなく**失敗**。成果物があっても消える。`!cancelled()` で push を守り、失敗ログから復元する道も知っておく
- cronは時刻を保証しない（実測+43分〜+1時間43分）。**時刻が意味を持つ処理はpushトリガーへ**
- 無人ジョブは**頻繁に・冪等に・全件を**。週1・1件・狭い窓は失敗が積み上がる
- いちばん難しいのは動かすことではなく、**止まったと気づくこと**。成果物を人間の目の前まで運ぶ経路が最良の検知になる
