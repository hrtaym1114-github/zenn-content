# 自己改善ループはなぜ暴走したか

## 理屈は正しかった

エージェント組織を作ると、遅かれ早かれ全員が同じことを考える。

**「出力の結果を測って、次の出力に反映させれば、勝手に賢くなるのでは？」**

私も考えた。そして組んだ。X.comの日次投稿でこういうループにした。

```
① 投稿を自動生成する
     ↓
② 数日後、エンゲージメントを取得する
     ↓
③ 「効いた投稿」「効かなかった投稿」に分けて、特徴を抽出する
     ↓
④ 学習結果を状態ファイルに書く
     ↓
⑤ 次の生成プロンプトが、その状態ファイルを読む
     ↓
①へ戻る
```

理屈は正しい。実装も難しくない。過学習のガードも入れた。**1投稿の偶然に引きずられないよう、サンプル数の下限を設けた。**

```python
# この件数に達しない特徴では指示を出さない（過学習の防止）
MIN_SAMPLES = 3
```

さらに、効果量の下限も入れた。差がわずかなものを「効いた」と言わせないためだ。

```python
# 差 -0.01（ただの誤差）でも「避けろ」と指示してしまうのを防ぐ
MIN_LIFT_ABS = 0.5
MIN_LIFT_RATIO = 0.25
```

教科書どおりだと思っていた。

**それでもループは暴走した。**

## 何が起きたか

2026年8月、投稿のリーチが崩れた。インプレッションの中央値が **548から36** に落ちた。15分の1である。

内容を読み返すと、投稿が明らかに変わっていた。以前は道具やニュースの話をしていたのに、いつのまにか**自分の運用プロセスの話ばかり**になっていた。「今日はこういうワークフローを組んだ」「エージェントの設計をこう直した」。

私がこれに気づいたきっかけは、システムのアラートではない。**人間に言われたからだ。**

> 「全然面白くない。運用が下手だと露呈しているだけ」

ぐうの音も出なかった。そして怖かったのは、**そう言われるまで気づく手段が一つも無かった**ことだ。

## 原因──ガードは「特徴量の側」しか守っていなかった

原因を追ったら、一箇所に収束した。

スコアの計算式はこうだった。

```
スコア = プロフィールクリック × 10 + ...
```

プロフィールクリック（PC）を主信号にしたのには理由がある。フォロワーを増やしたいのだから、「投稿を見た人がプロフィールを見に来たか」が最も近い指標だ。インプレッションはリーチであって、フォロー動機とは無相関だと実測で確認していた。指標の選び方は間違っていない。

問題は量だった。

**17投稿で、累計プロフィールクリックが2件しか無かった。**

PC×10 の重みで、原材料が2件。つまり**順位はたった2回の偶然でほぼ決まっていた**。

`MIN_SAMPLES = 3` は何をしていたのか。これは「特徴量」の側を守るガードだ。「この特徴を持つ投稿が3本以上あるか」を見ている。3本以上あれば通る。**その3本のスコアが全部ゼロでも通る。**

つまり私のガードは、こう配置されていた。

| 守っていた場所 | 見ていた内容 |
|--------------|------------|
| ✅ 特徴量の側 | この特徴のサンプルは3件以上あるか |
| ✅ 効果量の側 | 差は誤差の範囲を超えているか |
| ❌ **シグナルの側** | **スコアの原材料そのものが足りているか** |

**誰もスコアの原材料の量を見ていなかった。**

## 決定的な症状──同じものが1位と2位に同時に載る

このバグには、いま思えば明確な症状が出ていた。

出力レポートを見返すと、**同じ「製造業×AI」というカテゴリが、「効いた投稿」1位と「効かなかった投稿」2位に同時に掲載されていた。**

これは論理的にありえない。同じ特徴が、プラスにもマイナスにも効くことはない。**この矛盾は「その指標がノイズを測っている」ことの決定的な証拠**だった。

私はそれを読んで、矛盾に気づかなかった。レポートの結論だけ見ていたからだ。

いまはこれを自動検知させている。

```python
# 同じカテゴリが上位と下位の両方に出ていないか自動チェックする。
# 出ていればその指標はノイズを測っている決定的証拠。
```

**矛盾の検知は、精度の検証より安い。** 正しさを確かめるのは難しいが、「同時に両方に載っている」は機械的に見つかる。

## なぜ暴走が加速したのか

ここからが構造の話だ。ノイズを学習しただけなら、出力はランダムになるはずだった。実際には**一方向に収束した**。なぜか。

### 増幅ループになっていた

生成プロンプトには「学習結果を最優先で反映する」と書いてあった。だからノイズ由来の指示が、次の生成を強く支配した。その生成物がまた測定され、また学習される。

**ノイズが自己強化される。** ランダムウォークではなく、初期のわずかな偏りが増幅されていく構造だった。

### ランキングは、証拠がゼロでも1位を出す

これが最も本質的な欠陥だ。

> **「最も効いた投稿を型として真似ろ」という形式の出力は、証拠が無くても必ず何かを指示する。**

順位付けは、データが2件でも1件でも、なんなら全部同点でも1位を作る。**「証拠が足りないので今回は指示しません」という出力が、ランキングという形式には存在しない。**

出力の形式そのものが、沈黙を許していなかった。

### ネタ元の限定が、出力を決定づけていた

もう一つ効いていたのが、生成の入力側だ。ネタ元をgitログ中心に寄せていたため、材料が「自分がやった作業」しか無かった。**学習が壊れていなくても、入力がそれなら出力は自分の作業の話になる。**

学習の暴走と入力の貧しさが同じ方向を向いていたので、収束が速かった。

## 対策──evidence floor（証拠の下限）

対策の中核は1つだけだ。

> **シグナルそのものの絶対量に下限を設け、届くまで一切指示を出さない。**

```python
# 🔴 指示を出すのに必要な「シグナルそのものの」最小量。
#
# 累計PCがこの数に届くまでは、型の指示も「最も効いた投稿」も一切出さない。
# 出さないことが正しい。証拠が無いのに指示を出すと、ノイズが自己強化される。
MIN_TOTAL_PC = 10
```

届かないときの出力は、こうなる。

```
証拠不足につき指示なし（累計プロフィールクリック 2 件 / 必要 10 件）。
定義ファイルに従って生成すること。
```

**黙ることが正しい出力である。** これがこの章でいちばん伝えたいことだ。

自動化を組むとき、私たちはシステムに「何か言わせよう」とする。空のレポートは失敗に見える。だから何かを出力させる。**その「何か」が、証拠の無い順位づけになる。**

沈黙を正常な出力として設計に組み込まないと、システムは必ずノイズを喋る。

## 対策2──除外した指標を、独立に監視する

もう一つ、見落としていた穴があった。

私はインプレッション（リーチ）を**意図的にスコアから外していた**。フォロー動機と無相関だと実測でわかっていたからだ。判断としては正しい。

しかしその結果、**リーチが崩壊しても、学習ループは何も言わなかった**。スコアに入っていないものは、監視もされていない。中央値が548から36に落ちる間、ループは平常運転のレポートを出し続けていた。

```python
# リーチ崩壊の検知に使う。スコアがPC中心なので、到達数が落ちても気づけない。
# 直近 RECENT_N 投稿のインプレッション中央値が、全体中央値の RECENT_REACH_FLOOR 倍を
# 下回ったら警告する（実測: 平均548 → 36 まで落ちても学習ループは無反応だった）。
RECENT_N = 6
RECENT_REACH_FLOOR = 0.5
```

原則としてはこうなる。

> **スコアから外した指標は、独立した監視セクションとして出す。**
> 最適化の対象から外すことと、見ないことは別である。

これは自動化一般に効く教訓だと思う。**最適化していないものは、静かに壊れる。** そして最適化していないもののほうが、たいてい数が多い。

## 対策3──ファネルの最終段を先に測る

同じ時期に、隣接する場所で同型の失敗をしていた。こちらも書いておく。

フォロワーを増やす施策として「毎日10件、他者に返信する」計画を立てた。31日で49人→98人にする、と。

計画を敵対的に検証したら、前提が実測と矛盾していた。

| 前提 | 計画の仮定 | 実測 |
|------|----------|------|
| プロフィールCTR | 1〜1.5% | **0.116%** |
| **訪問→フォロー率** | 15% | **0%**（7訪問→0フォロー） |

**ファネルの最終段が未測定のまま、31日ぶん41時間を前払いする計画**だった。現実的な期待値を計算し直すと +4人。撤回した。

教訓は単純だ。

> **上流の流量を増やす計画は、最終段が0%なら何倍にしても0。**

測定を先に置き、小さく実測してから期間を語る。この施策は Phase 0（プロフィール整備）→ Phase 1（5日で50件）→ 獲得率で継続/撤収を判定、という形に組み直した。撤収条件も数値で決めた（`フォロワー増 ÷ 接触数 < 0.03` なら撤収）。

そしてもう一つ、より苦い教訓がある。組み直した計画は、**11日間で採用0件**だった。摩擦を減らす仕組み（候補の自動生成、承認フロー、メール配信）を作った**上で**、0件。

道具不足では説明できない。**施策を足すより、摩擦を消すほうを優先すべきだった。** そして摩擦の正体は案の質ではなく、「メールで届いたものをブラウザで手作業する」という媒体またぎだった。

自己改善ループの話をしているときに、いちばん改善が要るのは**人間が動く箇所**だったりする。

## 自己改善ループのチェックリスト

同じものを組む人のために、点検項目をまとめる。

- [ ] **シグナルの絶対量に下限があるか**（特徴量のサンプル数ではなく、スコアの原材料の総量）
- [ ] **証拠不足のとき、明示的に沈黙するか**（「指示なし」と出力できるか。ランキング形式は沈黙できない）
- [ ] **同一カテゴリが上位・下位に同時に載っていないか**を自動チェックしているか
- [ ] **スコアから除外した指標を、独立に監視**しているか
- [ ] 生成プロンプトが学習結果を「最優先」で読んでいないか（**増幅の主犯はここ**）
- [ ] ネタ元（入力）が偏っていないか。**レバーは生成の質ではなく入力側にある**
- [ ] ファネルの**最終段が実測されているか**。上流の流量計画はその後
- [ ] 施策が実行されなかったとき、**案の質ではなく摩擦を疑う**設計になっているか

## アンチパターン3つ

### NG1: 過学習ガードを「特徴量の側」だけに置く

サンプル数の下限は必要だが十分ではない。**スコアの原材料が枯れていれば、サンプルが何件あっても順位は偶然で決まる。** シグナル側の下限を必ず併置する。

### NG2: 学習結果を「最優先」で読ませる

これがノイズを増幅させる主犯だ。学習結果は**定義ファイル（変わらない方針）を上書きしない補助情報**として読ませる。証拠が十分に貯まってから優先度を上げる。

### NG3: 最適化から外した指標を監視からも外す

外した瞬間、その指標は壊れても誰も気づかない。**最適化しないことと、見ないことを分離する。** 除外指標こそ独立の監視セクションが要る。

## まとめ

- 自己改善ループの構造的欠陥は**疎なシグナル**にある。累計2件のクリックで「効いた型」を確定すると、順位は偶然で決まる
- ガードは3層要る。特徴量の側（サンプル数）・効果量の側（差の大きさ）・**シグナルの側（原材料の総量）**。3つめが抜けやすい
- **黙ることを正常な出力として設計する。** ランキング形式は証拠ゼロでも1位を出すので、形式そのものが沈黙を許さない
- 同一カテゴリが上位・下位に同時掲載されたら、その指標はノイズを測っている**決定的証拠**。矛盾の検知は精度の検証より安い
- **最適化から外した指標は、独立に監視する。** 外したものは静かに壊れる
- 上流の流量を増やす計画は、**ファネル最終段が0%なら何倍にしても0**
- 施策が実行されないとき、疑うべきは案の質ではなく**摩擦**

そしてこの章の最大の教訓は、技術ではないところにある。**リーチが15分の1になったことに、私は自分では気づけなかった。** 気づかせたのは人間の一言だった。

無人で回る組織を作るということは、**壊れたことを教えてくれる人を、どこかに残しておく**ということでもある。
